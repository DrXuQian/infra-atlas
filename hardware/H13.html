H13 / INTERCONNECT & HBM

片内互连与 DRAM/HBM

从 SM 到显存，究竟哪一个共享资源先饱和？

地址分布决定负载落点，互连和控制器决定请求排队，DRAM bank 状态决定哪些命令可以前进。

适用范围

地址映射、队列和调度使用已读 Accel-Sim 模型；DRAM 行状态为概念模型。HBM2 FPGA 论文只作为受控观察，不替代 NVIDIA HBM 控制器文档。

先备知识：H09 · H11 · H12

01

H13.01

地址如何分布到内存分区

#

一个地址怎样决定访问哪片显存资源？

最小状态
物理地址、模型映射函数、分区与 bank 数。
变化规则
地址经映射得到路由目的地，各目的地独立排队。

访存系统需要把物理地址送到目标分区、通道、bank、行和列。教学模型可用位段或哈希完成映射；正确映射既要保持不同地址可区分，也希望常见访问模式利用多个并行资源，避免所有请求集中一处。

已读 Accel-Sim addrdec_tlx 支持可配置的位提取、取模与分区索引方式。这是研究模型的选择，不是 NVIDIA 的完整公开映射。CUDA 虚拟地址还受页映射影响，因此从连续虚拟地址直接猜某个 HBM bank 一般证据不足。

具体例子

教学模型令 partition=(地址/32B)%4，连续四个 sector 分布到四个分区。换成步长 128B 会总落在同一分区；真实 GPU 未必使用这个公式。

先预测改变映射或基址可能在请求数不变时改变负载均衡。

容易混淆

把 simulator 配置中的地址位串当成真机固定地址译码。

检验理解虚拟地址相差固定步长就能确定物理 bank 吗？

通常不能，还要知道页映射和芯片地址分配方式。

H13.02

partition camping

#

什么是 partition camping？

最小状态
各分区请求比例、单分区服务率、整卡聚合带宽。
变化规则
局部队列因输入超过服务率而积压，上游受到反压。

Partition camping 指大量请求集中到少数内存分区，使这些资源繁忙而其他资源利用不足。整卡汇总带宽因此可能明显低于峰值；瓶颈来自负载分布，并不要求总请求数很少，也不等于某一个 warp 没做好合并。

合并效率与分区分布属于不同层次：warp 内地址连续，跨 block 的 tile 起点仍可能形成周期性热点。真机索引往往不公开，应把 camping 视为待验证假设，结合基址、stride、实例分布与 TLB/缓存对照逐步排除替代解释。

具体例子

四分区教学模型中 80% 请求落到分区0，它先达到上限，另外三处空闲也无法替它服务；将 tile 起点分散后总吞吐才可能提高。

先预测分散请求后局部峰值降低，整卡吞吐可能上升。

容易混淆

看到总带宽只有峰值四分之一，就直接宣判只有一个分区在工作。

检验理解warp 内访问完全合并，能否仍有分区热点？

可以，跨 warp 或 block 的地址落点仍可能偏斜。

H13.03

SM 到 L2 的互连竞争

#

L2 命中为何仍会争抢互连？

最小状态
SM 请求源、L2 服务入口、链路与返回端口。
变化规则
请求和返回分别争用有限网络资源。

SM 访问共享 L2 需要经过片内请求与返回网络。即使所有读取都在 L2 命中，地址请求、返回数据和端口依然消耗带宽；多个 SM 同时访问热点时，会竞争服务入口、路由链路或返回路径，而不必触碰 HBM。

网络拓扑、仲裁和分片结构依芯片而变，不能用一张简图宣称所有 SM 通过同一根总线。NCU 的 memory chart 可显示特定设备的路径和端口利用率，仍需配合绝对流量和时间才能判断哪里真正限制吞吐。

具体例子

让更多 SM 重读一个驻留 L2 的大表：初期吞吐增加，达到片内返回能力后继续增加 SM 主要增加排队，HBM 带宽仍可很低。

先预测消除冗余 L2 hit 可降低片内流量，即使 HBM 字节不变。

容易混淆

认为片内传输免费，只有到显存的字节值得优化。

检验理解L2 hit rate 近100%，还有必要减少重复 load 吗？

有必要，重复 hit 仍占用指令、端口和片内返回带宽。

H13.04

下游阻塞如何向上游传播

#

下游堵塞怎样传回 scheduler？

最小状态
逐级缓冲占用、下游接收条件与消费速率。
变化规则
下一级无空间则本级保留请求，满状态向上游传播。

有限缓冲网络需要在下一段有接收能力时才能继续转发。若内存控制器或返回队列停滞，上游缓冲逐渐占满，再阻止更上游的新请求。最后，LSU 入口可能无法接收，scheduler 看到的是发射受阻，而源头可能在更远的阶段。

这叫反压传播，不能从最靠前的 stall 名直接定位根因。增加某段队列能吸收短暂突发，却不能改变长期最低服务率。诊断要把请求进入、下游服务和响应返回连成链，观察哪段首先饱和以及变化如何传导。

具体例子

教学链有三级、各2槽；末级暂时不消费，先填末级，再填中级，最后入口停止。末级恢复服务后，也需要逐段腾空才能完全解除反压。

先预测恢复下游服务后，入口可能经过一段排空时间才恢复。

容易混淆

将入口 queue-full 当成入口本身计算能力不足的唯一证据。

检验理解把所有队列加深，稳定带宽一定提高吗？

不会，最低持续服务率未变时只是允许更多排队。

H13.05

channel / pseudo-channel / bank 的并行性

#

channel、pseudo-channel、bank 是同一种并行性吗？

最小状态
通道资源、pseudo-channel 约束、各 bank 行状态。
变化规则
不同 bank 的准备可重叠，共享传输资源仍需仲裁。

Channel 提供一组传输与控制资源，pseudo-channel 在 HBM 的相应模式中划分更细的访问域，bank 则有独立的行状态。更多 bank 可让准备行的时间重叠，但多个 bank 往往还共享数据通路、命令时序或控制器资源。

不同 HBM 代际的通道宽度、bank group 和共享约束并不相同。HBM2 FPGA 论文能展示一种具体配置及其交换网络，不能直接等同 NVIDIA GPU 的路由。估算并行性时先列共享资源，别把所有数量相乘成无限独立带宽。

具体例子

一个教学通道有4个bank：bank0准备新行时，bank1可有已就绪数据，但两者若共用一条数据总线，就不能在同一传输槽都返回完整数据。

先预测bank 并行性不足时分散访问有用，总线已满时收益有限。

容易混淆

把 DRAM bank 与 shared-memory bank 混为一谈，或认为每 bank 都有独立外部总线。

检验理解bank 数翻倍会让带宽必然翻倍吗？

不会，数据引脚或命令总线也可能已经饱和。

H13.06

row hit 与 row conflict

#

row hit、closed row 和 row conflict 有何区别？

最小状态
每 bank 的 open/closed 状态、当前行、请求行列。
变化规则
目标行不同则先关闭旧行并打开新行，时序允许后访问列。

DRAM 读取通常通过 bank 中已激活的行缓冲来服务列地址。请求目标就是当前打开行时称 row hit；bank 关闭时需先激活目标行；已经打开其他行时，要先满足关闭条件、预充电，再激活新行，这叫 row conflict。

这些是 DRAM 行状态，不是 GPU cache hit/miss。真实请求可能被控制器重排，且与其他 bank 的活动重叠，所以单次命令开销不等于整段 kernel 时间。要比较时须固定并发、地址映射和队列条件，并标明使用何种存储器。

具体例子

bank0 当前打开行 A。读 A 的另一列是 row hit；读 B 要换行。即使两个 GPU load 都 L2 miss，它们到 DRAM 后的服务代价也可能不同。

先预测相同行局部性可能减少 ACT/PRE，但未必改善总线已满的负载。

容易混淆

把 L2 miss 率直接当作 DRAM row-conflict 率。

检验理解row hit 是否代表数据已经在 SM 缓存？

不是，它只描述 DRAM bank 的行状态。

H13.07

ACT、READ/WRITE、PRE 的时序

#

ACT、READ/WRITE、PRE 能连续无间隔执行吗？

最小状态
bank 状态、各时序计数、命令和数据资源。
变化规则
只发出前提与时序均满足的命令，再更新状态及等待计数。

ACT 把目标行激活到行缓冲；READ/WRITE 选择列并传输；PRE 让 bank 回到可开启下一行的状态。它们之间存在最小等待与资源约束，例如激活到列访问、行保持、预充电恢复、写恢复和 bank-group 间命令间隔。

在模拟器中这些限制表现为状态与倒计时，只有前提满足的命令才可发出。将 tRCD、tRP 等参数改小是研究假设，不是软件能更改真机物理时序。多 bank 调度的作用是找可合法前进的其他命令，而非跳过等待。

具体例子

教学 bank 关闭时不能直接 READ；必须 ACT 后等允许窗口。若另一 bank 已有打开行，控制器可能趁这段等待服务它。

先预测单 bank 串行换行比多 bank 有可就绪命令时更易暴露空档。

容易混淆

把三个命令画成每周期无条件各走一步，或把 tRCD 视作完整 load 延迟。

检验理解tRP 结束就说明 load 数据已返回了吗？

没有，它只说明预充电相关限制解除，后续仍需激活、读取和传输。

H13.08

读写切换与 refresh

#

读写切换和 refresh 为什么影响持续带宽？

最小状态
读写服务模式、队列水位、刷新占用窗口。
变化规则
方向改变和刷新均需满足时序，并暂时改变可服务请求集合。

同一数据通路在读和写方向之间切换，需要满足方向转换与相关时序约束。控制器可批量服务读取或写入来摊薄切换成本，但会影响另一类请求等待时间。仅由读写总字节估计耗时，会漏掉访问顺序与突发形态。

DRAM 还需 refresh 保持存储数据。刷新占用哪些 bank、何时安排及重叠能力取决于器件与模式，不能把某个 FPGA HBM2 实验里的周期直接套到 GPU。它可形成延迟尾部和服务空档，持续性能通常低于理想引脚峰值。

具体例子

相同读写各50%，一种序列逐请求交替，另一种按短批次处理，方向转换频率不同。刷新恰好遇到目标 bank 时，还可能使少数请求显著变慢。

先预测增加连续同方向突发可能减少切换，但另一方向等待可能变长。

容易混淆

把偶发延迟尖峰唯一归因于 refresh，忽略排队、频率或页故障。

检验理解平均带宽相同，尾延迟会相同吗？

不会，批处理、切换和刷新可改变请求等待分布。

H13.09

内存控制器调度策略

#

控制器为什么不总按到达顺序服务？

最小状态
到达年龄、行就绪状态、读写模式与时序。
变化规则
从允许的候选请求中按策略选择，再更新队列和行状态。

最老请求可能要求换行或等待某个 bank，较新的请求却已可服务当前打开行。研究调度器可在满足时序的前提下优先利用就绪资源，提高有效吞吐。代价是完成顺序变化，某些老请求的等待变长，公平性与吞吐需要权衡。

已读 Accel-Sim 的 FR-FCFS 模型按 bank 和 row 组织队列，优先当前行并包含可配置读写模式水位。这个代码可用于对照 FIFO 与行局部性，不能据此断言 NVIDIA 控制器使用完全相同策略、年龄定义或饥饿防护。

具体例子

队列 X请求B行、Y请求已打开A行。模型可先返回Y再为X换行。若A行请求不断到来，不加年龄保护的策略可能使X长期等待。

先预测优先 row hit 可减少换行，同时可能增加最老非命中请求延迟。

容易混淆

把高吞吐的模拟器策略当作已逆向出的商用 GPU 调度算法。

检验理解调度重排会改变程序可见的同步语义吗？

不能破坏 ISA 和内存模型规定的关系；内部请求可在允许范围内重排。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

dram__throughput.avg.pct_of_peak_sustained_elapsed

设备显存资源相对 sustained peak、按 elapsed cycles 归一的吞吐概览，用于比较是否接近该计数器描述的服务上限。

avg 可能掩盖分区偏斜；这是综合吞吐指标，不能直接称作有效应用字节占峰值。先 --query-metrics。

[6]

dram__bytes_read.sum / dram__bytes_write.sum

观察收集窗口中设备显存读写总字节，与 CUDA event 时间及 L2 命中一起解释实际搬运。

它们不是源码 useful bytes；缓存、ECC、写分配和压缩等可能改变关系。

WorkloadDistribution + MemoryWorkloadAnalysis_Chart

在支持的设备上观察资源实例不均和片内链路/端口压力，检验总带宽低是否来自局部热点。

公开 NCU 没有跨架构通用的 row-hit、每 bank 队列深度或控制器调度策略指标；不可据此推测精确实现。

ONE VARIABLE, ONE HYPOTHESIS

地址步长与分区偏斜（实验设计，尚未执行）

只改变

在工作集足够大、缓存条件一致时扫描地址步长和基址偏移；使用多个独立访问流保持并发。

预计现象

若地址分布造成局部热点，某些步长或偏移会降低吞吐，资源实例分布可能不均；结论仍需排除其他原因。

记录什么

有效字节吞吐、L2/DRAM 字节、WorkloadDistribution 可用实例视图、SASS、sector/request 与 TLB 控制对照。

排除干扰

步长同时改变 coalescing、缓存复用、页数和行局部性；仅凭带宽谷值不能识别 NVIDIA 的物理地址哈希。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
