H08 / PIPELINES · LATENCY ≠ THROUGHPUT

执行流水线

一条指令要执行好几个周期，为什么管线还能不断接新工作？

先拆开结果延迟、接收间隔和共享资源，再讨论不同指令混合的真正吞吐上限。

01

H08.01

latency 与 initiation interval

#

latency 和 initiation interval 分别回答什么？

最小状态
结果可用时刻、入口下次允许接收时刻、在途操作。
变化规则
每条操作在接收时登记完成时刻；入口是否空闲由 II 单独控制。

latency 是一次操作从被接收到其结果可供指定消费者使用的间隔；initiation interval（II）是入口连续接收独立操作的最小间隔。一个多级管线可以同时保存多个操作，所以结果尚未完成不代表入口无法继续接收，反之结果延迟短也不保证吞吐高。

在理想单入口模型中，持续吞吐至多为 1/II，单条依赖链却受 latency 约束。要用独立工作覆盖延迟，还需足够发射能力、输入带宽和在途容量。这里的简单关系是教学上限；不同指标若分别以线程操作、warp 指令或周期计数，必须先统一单位。

具体例子

L=4、II=1：A 在 c0 接收、c4 可用；独立 B 可在 c1 接收、c5 可用。依赖 A 的 B 则不能照此安排。

先预测单链和多独立链会给出不同每条平均时间，这并不矛盾。

容易混淆

拿依赖链的每条耗时直接推算管线峰值，或把 32-lane 指令当成一拍完成。

检验理解L=8、II=2 的理想入口，每周期能长期接收多少条独立操作？

上限是 0.5 条；还需要其他资源持续供给。

H08.02

指令发射与执行入口接收

#

scheduler issue 是否已经意味着算术开始？

最小状态
候选指令、派发队列占用、执行入口接收能力。
变化规则
队列有空位才接收；下游取走后释放槽，满队列向上游施加反压。

发射是一个被选中指令跨过调度边界的事件，执行入口接收是另一处资源边界。两者之间可以存在缓冲、操作数收集或派发步骤；因此在真实系统和详细模拟器中，发射时刻不一定就是计算单元开始处理的时刻。

教学模型为了清楚，可以把两者合并，但必须明确这一假设。分析队列时则要分开入口排队与执行延迟：队列还有空位时可以继续接收，队列满时反压传回上游。用一项 issue 利用率无法证明每个下游单元同时满载，也不能代替结果完成计数。

具体例子

一个两槽队列接收 A/B 后，执行管线仍因操作数不足未取走它们；第三条 C 会受容量限制，虽然 C 自身数据已 ready。

先预测短时 issue 很忙但管线利用不高，可能来自缓冲、供给或统计窗口差异。

容易混淆

把 issue-active 直接解释为 ALU 每一条通路都在做有效计算。

检验理解如果删掉中间队列，教学模型需要改变哪些规则？

发射资格必须直接检查执行入口可接收，否则会凭空容纳指令。

H08.03

FP32 / INT 指令的资源映射

#

FP32 与 INT 指令是否使用独立资源？

最小状态
最终 FP/INT opcode、依赖关系及共享入口。
变化规则
只有依赖满足并有对应路径供给时，两个执行流才可能重叠。

资源映射是架构问题，不能仅由数据类型判断。NVIDIA 为 GV100 描述了独立 FP32 与 INT32 执行资源，因此一定条件下可以重叠相关工作；其他芯片的资源数量、共享关系和可同时执行组合需另查对应架构资料。名称同为 Ampere，也不应忽略具体芯片差别。

即使两类运算的执行单元独立，它们仍可能共享发射、寄存器供给或结果通路。把地址计算穿插在浮点计算之间可能利用空闲路径，但若地址生成依赖尚未就绪的数据，或公共入口已经饱和，就不能获得理想重叠。性能分析要追踪完整依赖图。

具体例子

在不改变算法的前提下，把下一迭代的指针更新提前到当前独立 FMA 之间；是否获益由目标机器的最终指令与供给情况决定。

先预测地址计算较多的 kernel，可能比纯 FMA 峰值基准更受共享路径影响。

容易混淆

见到两类 core 数量就把它们的理论吞吐直接相加当成 kernel 性能。

检验理解独立 INT 单元能让依赖浮点结果的整数转换提前完成吗？

不能；独立资源不消除数据依赖。

H08.04

SFU 指令的吞吐限制

#

为什么一个特殊函数可能压住整个内核？

最小状态
最终指令序列、相关管线供给能力、允许数值误差。
变化规则
候选在目标管线可用时进入；超过供给的请求必须等待。

特殊函数相关指令的处理能力与通用 FP32 加乘不一定相同。大量 warp 同时执行同一类低吞吐操作时，会把请求集中到有限路径；单个操作的延迟和该路径每周期能接收多少操作需要分别测量。增加 warp 只能提供更多候选，不能扩宽饱和的路径。

还要区分 CUDA 数学函数、intrinsic、PTX 和最终 SASS：一个高层函数可能包含范围规约、特殊输入处理和多个指令，并不等于一次 MUFU。使用近似版本或 fast math 前，应确定误差、舍入及边界语义是否满足需求，再比较相同有效工作量。

具体例子

expf 与某种近似计算路径可能生成不同指令序列；不能只数源码中出现了多少次 exp，就推定 SFU 指令数量。

先预测相同 FLOPs 的 kernel 也可能因特殊函数比例不同而性能差异很大。

容易混淆

把所有 transcendental 函数都视为一条固定时延、相同吞吐的硬件指令。

检验理解若对应路径已经持续饱和，warp 数翻倍是否保证提速？

不会；它可能只增加排队，甚至引入资源开销。

H08.05

多种指令如何竞争共享路径

#

不同 opcode 为什么仍可能相互拖慢？

最小状态
指令到资源的路径、各资源容量、混合比例。
变化规则
多类需求在共享资源相加，超过供给时引发排队或反压。

opcode 名称描述操作语义，并不保证拥有专属资源。不同指令可能在执行路径、发射端口、寄存器读写或中间队列汇合。若共同瓶颈只允许有限服务，单独测试都很快的两段代码混合运行，也不能简单把各自峰值同时实现。

建立最小模型时，先列出每条指令经过的资源及单位需求，再看哪一处总需求超过容量。真实 GPU 的内部映射不全公开，可用同工作量的混合比例扫描检验竞争假设；但是非线性曲线也可能来自寄存器使用、缓存或编译变化，不能只据曲线画出确定电路。

具体例子

模型中 A/B 用不同计算单元，却共用每周期一条的入口；各自单独可达一条/周期，混合后的总和仍最多一条/周期。

先预测混合指令的性能上限可能低于孤立峰值之和。

容易混淆

把不同管线名称理解成从取指到写回全程完全独立。

检验理解两个执行单元都有空闲，入口满了还会阻止发射吗？

会，端到端吞吐受经过的任何共享瓶颈限制。

H08.06

类型转换与数据解包的执行成本

#

低比特 kernel 的解包为什么不是免费操作？

最小状态
packed 输入、解包临时值、scale、最终计算片段。
变化规则
每种表示转换都要计入指令与依赖，只有真正复用才分摊成本。

压缩权重减少存储和搬运字节，但参与乘法前往往还需位提取、符号处理、类型转换、scale 或 zero-point 运算与布局重排。它们消耗指令、操作数和临时寄存器，可能走与主计算不同或共享的路径；节省内存不等于等比例减少总执行时间。

应把一块权重从 packed 形式到计算可用形式的实际 SASS 列出来，按 tile 复用程度分摊成本。若一次解包结果可以服务多次计算，开销容易摊薄；极小 batch 或低复用场景则可能让解包成为关键路径。比较方案时还要保持数值格式与输出正确性一致。

具体例子

读取一个 packed 字后拆成多个低比特值，需要额外操作；若每个值只用于一次乘法，这些操作可能比大 tile 重复使用时更显眼。

先预测小 batch 的瓶颈可能从权重搬运转移到转换和调度。

容易混淆

只用压缩率预测低比特提速，忽略解包、转换和寄存器压力。

检验理解把解包移到更早位置一定降低总时间吗？

不一定；它可能隐藏延迟，也可能延长变量活跃期并降低 occupancy。

H08.07

pipeline 饱和后增加 warp 的效果

#

流水线已经饱和后，更多 warp 带来什么？

最小状态
可发射候选数、入口空档、资源持续利用率。
变化规则
优先用新增候选填空档；没有空档时不能突破接收间隔。

更多 resident warp 增加调度器可选择的上下文，主要帮助填补依赖、访存或控制流造成的空档。如果目标管线已经每个允许接收时刻都有有效工作，那么额外 warp 无法提高该资源的物理供给上限，只会提供更多排队候选。

更高驻留还可能增加缓存工作集、同步等待和资源分配压力；为追求 occupancy 降低每线程寄存器，有时会引发 spill。因此要看有效吞吐与时间是否随 warp 数继续改善，而不是把 occupancy 百分比本身当目标。饱和也要结合合理的峰值口径判断。

具体例子

教学管线 II=2，已有独立指令填满每个可接收周期；再加入 8 个 ready warp，长期接收上限依然是每周期 0.5 条。

先预测吞吐随 warp 数上升后出现平台，可能标志已触及某资源上限。

容易混淆

把“延迟隐藏不足”和“资源已经满负荷”当成同一个增加 warp 就能解决的问题。

检验理解更多 warp 让 not_selected 增多但时间不变，可能说明什么？

可能已有足够候选覆盖延迟，竞争者变多而瓶颈容量没变。

H08.08

指令混合如何改变瓶颈

#

为什么优化一种指令后，热点会换地方？

最小状态
每单位有效工作量的资源需求、总时间、归一分母。
变化规则
改变一类需求后重新计算资源压力，识别新的关键路径。

kernel 的时间由实际关键路径与最紧张资源共同决定。减少某类操作的需求以后，原来被掩盖的另一处上限可能变得可见，例如搬运变快后解包占比上升，或计算变快后同步与启动成本更突出。这是瓶颈迁移，不意味着前一项优化无效。

分析指令混合应以同一任务为基准：看每输出元素所需的各类指令和传输，而不是比较原始指令总数。融合可能减少搬运却增加寄存器；展开可能增加 ILP 却增大指令体积。因此一次只改变一项主要因素，并重新检查总时间与新的限制路径。

具体例子

原先每 tile 搬运 100 单位、转换 30 单位；把搬运减半后，转换在剩余成本中的相对份额更大，但其绝对操作数可以完全没变。

先预测两项优化分别有效，组合收益也未必等于两者倍率相乘。

容易混淆

把百分比变大误判为该阶段绝对变慢，或认为指令数减少就必定加速。

检验理解优化后某类 stall 占比变高，首先还需要什么信息？

绝对时间、计数和归一分母，确认占比变化是否只是其他部分缩短。

H08.09

Core / CUDA Core 的计数口径与执行资源

#

CUDA Core 数量能直接预测一个 kernel 吗？

最小状态
资源计数定义、指令类型、有效 lane、频率。
变化规则
先把逻辑工作映射到对应资源，再讨论容量和持续供给。

CUDA Core 是架构资料对特定标量计算资源的计数口径，不是 CPU 意义上的完整独立核心，也不是同时运行的 CUDA 线程数量。warp 的逻辑宽度、scheduler 数、执行 lane 数、执行间隔和结果延迟属于不同层次，不能互相替换。

从资源数量推导理论峰值时，还要限定数据类型、指令、频率以及每条指令的运算计数，例如 FMA 常按乘加两个 FLOP 计。真实 kernel 还需数据供给、足够有效 lane 和兼容指令混合。Tensor Core 峰值、稀疏峰值也不能直接当作普通 FP32 代码上限。

具体例子

一张卡标注很多 CUDA Core，并不意味着任意相同数量的线程都能在一拍完成各自的指令；线程还通过 warp 调度和具体执行路径。

先预测core 数更高的设备，也可能在低并发或访存受限 kernel 中没有同比例收益。

容易混淆

把 CUDA Core 数除以 32 就当成实际同时完成的 warp 数。

检验理解比较两个 GPU 的 core 数之前，至少要统一哪些条件？

数据类型、指令与峰值计数、架构资源口径和频率，并最终测同一 workload。

ComputeWorkloadAnalysis（section）

比较目标设备上的实际计算管线利用率，识别指令混合是否集中压在一条路径。

按 section 报告的峰值和 active/elapsed 口径解读，不比较不同单位的百分比。

[2]

InstructionStats（section）

确认解包、转换和地址计算在最终指令流中的比重。

源码 FLOPs 不包含所有这些操作，且 PTX 一条也不保证只生成一条 SASS。

[2]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

实验设计：测一条链与多条独立链（尚未执行）

只改变

固定总操作数，扫描独立累加器数量；再比较以 FP32、整数、转换或特殊函数为主的指令序列。

预计现象

单链首先反映依赖限制，独立链足够时更接近资源吞吐上限；不同指令混合可能改变瓶颈路径。

记录什么

保留最终 SASS、寄存器数、正确性结果和有效工作量；测总时间及 ComputeWorkloadAnalysis、InstructionStats。

排除干扰

更换数学实现可能改变精度、特殊输入行为与指令数量；增加 ILP 可能降低 occupancy；所有数字必须绑定具体芯片和版本。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
