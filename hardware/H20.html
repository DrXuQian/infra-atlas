单个kernel已经优化，为什么应用仍然没有快起来？

适用范围

01

H20.01

kernel 提交与设备端开始执行

#

CPU 的launch调用返回，为什么GPU还可能没开始执行？

最小状态
CPU提交、stream队列、依赖条件和GPU实际执行区间。
变化规则
工作从已提交进入可调度，再开始设备执行，最后才产生完成事件。

通常的kernel launch先把工作提交到运行时/驱动管理的stream。API返回只表示主机侧提交已推进到相应阶段，不保证设备已经开始，更不保证已经完成；此前stream任务、依赖和设备调度都可能让工作等待。

所以主机API耗时、排队时间、设备kernel时间和端到端时间应分别测量。CUDA event可测设备时间段，但要放在正确stream并等待完成；Nsight Systems时间线用来关联CPU调用与GPU执行，避免把launch优化误认为kernel算术加速。

具体例子

CPU连续提交100个短kernel后才同步：前面的API可能很快返回，但最终同步仍要等GPU处理剩余队列。

先预测短kernel串联更可能暴露launch开销，长kernel更可能由设备工作主导。

容易混淆

只用包围launch语句的CPU计时器测kernel运行时间，却没有完成同步。

检验理解API时间降到一半，GPU kernel时间不变，应用一定快一倍吗？

不一定。取决于提交是否在关键路径，以及能否与设备工作重叠。

H20.02

grid 波次与 SM 分配

#

grid 的总block数如何影响整卡波次与尾部？

最小状态
grid CTA数、每SM可驻留CTA数、可用SM和CTA耗时分布。
变化规则
已驻留CTA结束释放资源，待执行CTA才能获得相应容量。

同时驻留的CTA数量由可用SM数及每SM资源上限决定；超过这个容量的grid分批推进。wave是有用的容量描述，不是CUDA保证所有CTA严格齐步开始和结束的硬件批次。真实调度会在资源释放后继续补入工作。

grid过小时，一些SM可能根本拿不到CTA；grid规模接近容量整数倍但有余数时，最后阶段也可能只剩少数SM忙碌。CTA耗时不均还会制造额外尾部，因此单个SM上的高occupancy不能证明整卡充分利用。

具体例子

教学模型2个SM、每SM1个CTA、5个等长CTA需要3轮容量时间，最后一轮只执行1个CTA。

先预测更多可独立CTA通常改善整卡覆盖，但粒度过小又增加调度和外围开销。

容易混淆

把launch__waves_per_multiprocessor当成精确记录每个SM实际执行顺序的时间线。

检验理解每个CTA很大且occupancy高，grid只有1个CTA，会怎样？

通常只能占用其被分配到的一个SM，其他SM无法分担这个CTA的普通执行。

H20.03

并发 kernel 的资源竞争

#

两个stream中的kernel为什么可能没有重叠，重叠了也可能更慢？

最小状态
各kernel资源需求、stream依赖、共享带宽与并发驻留空间。
变化规则
依赖满足且有资源时允许并发，执行中继续竞争共享资源。

不同stream允许独立工作并发，但不承诺同时执行。kernel可能受到资源容量、设备能力、依赖或默认stream规则限制；单个kernel若占满shared、寄存器或可用CTA槽，另一个就未必有位置进入。

即使并发驻留，两者也会竞争SM计算路径、L2、HBM和功耗预算。并发能填补互补资源的空隙，也可能让两项工作的尾延迟都上升。应比较总完成时间与各自服务时间，不能仅凭时间线上存在重叠就认定收益。

具体例子

一个低occupancy且计算少的kernel可能与另一个互补；两个同时饱和HBM的大流式kernel则通常争用同一带宽。

先预测互补负载可能改善吞吐；同瓶颈负载可能只增加排队和延迟。

容易混淆

认为使用不同stream就等于绑定不同SM，拥有独立缓存和带宽。

检验理解两kernel各自单跑1ms，并发后各需1.8ms，总体是否一定更差？

总完成1.8ms仍可能优于串行2ms，但每项延迟都增加；取决于优化目标。

H20.04

copy engine 与计算重叠

#

有copy engine，为什么拷贝不一定与计算重叠？

最小状态
copy engine、计算引擎、buffer所有权和stream events。
变化规则
搬运与独立计算可并行，消费必须等对应buffer传输完成。

copy engine可独立推进适用的数据传输，但重叠还需要异步API、合适的host memory、独立stream/依赖和设备能力。把拷贝与消费同一数据的kernel放在同一个stream，顺序依赖仍然必须被遵守。

常见做法是分块双缓冲：计算第i块时传输第i+1块，回传更早的结果。host内存通常需要pinned以满足有效异步传输条件；拷贝和kernel仍可能争HBM、链路或内存控制资源。先确认时间线真实重叠，再算端到端收益。

具体例子

B0已到GPU并计算，copy engine向B1传下一块；等B1拷贝event完成后，计算stream才消费B1。

先预测具备流水深度时总时间可接近最慢阶段吞吐，但启动和排空成本仍存在。

容易混淆

把cudaMemcpyAsync中的Async理解为任意内存、任意方向都保证后台重叠。

检验理解单buffer反复拷贝并计算，为什么容易串行？

producer不能覆盖consumer仍在用的数据，缺少独立buffer和正确依赖便没有可重叠工作。

H20.05

PCIe / NVLink 的延迟与带宽

#

PCIe/NVLink的标称带宽怎样转化成小消息和大消息表现？

最小状态
消息字节数、固定开销、有效单向带宽和拓扑路径。
变化规则
每次传输支付固定成本，再经共享链路搬运字节。

链路带宽描述大量数据持续传输时的能力，小消息却往往由提交、协议和往返延迟主导。用简化模型T≈固定开销+字节数/有效带宽，可以解释为什么同一链路上1KiB和1GiB的GB/s相差很大。

还需区分单向、双向合计、每link与整GPU聚合口径，核对实际拓扑和链路宽度。多个peer、CPU NUMA位置、PCIe交换层级或NVSwitch路由会改变可用路径；不能把产品宣传的聚合数直接分配给任意一对GPU。

具体例子

某链路假设固定开销5µs、持续100GB/s，1KiB主要耗在固定部分；100MB则主要受传输时间影响。这是示例模型，不是实测规格。

先预测消息增大时有效带宽往往上升趋于平台；小消息优化应重视次数与延迟。

容易混淆

把双向聚合带宽当成一次单向copy可达到的有效应用带宽。

检验理解为什么合并多个小传输常能提高GB/s？

它可以摊薄每次提交和协议固定开销，但也可能增加等待批次的延迟。

H20.06

P2P 远端访问路径

#

P2P load 看起来像读指针，为什么成本不像本地HBM？

最小状态
访问GPU、目标GPU、peer映射、链路与在途请求。
变化规则
地址被映射到远端路径，数据往返后才满足本地消费者依赖。

启用且支持peer access后，GPU可访问另一GPU的内存，但地址透明不代表物理路径相同。远端load/store需要通过设备间互连和目标内存系统，受拓扑、链路、缓存行为以及远端负载影响。

P2P能力和远端原子支持都应按设备对查询，统一虚拟地址也不自动授予访问。大量细粒度依赖load可能受往返延迟限制；先批量搬到本地再复用，或增加独立并发访问，是不同的算法选择，需计入复制和存储成本。

具体例子

从远端权重逐元素pointer-chase几乎没有并行度；将连续tile批量传入本地buffer后重复计算，可能更好地摊薄远端访问。

先预测低并发远端依赖链通常暴露延迟；可批量或复用的访问更可能利用带宽。

容易混淆

把能访问peer指针解释成两张GPU共享同一速度、同一一致性规则的显存。

检验理解cudaDeviceCanAccessPeer成功是否证明所有远端atomic类型都支持？

不能。访问能力与原子等具体操作能力需分别查询并遵循内存模型。

H20.07

MIG / MPS 的资源边界

#

MIG和MPS分别隔离或共享了哪些资源？

最小状态
GI、CI、MPS客户端及各自资源/地址空间边界。
变化规则
按配置分配或共享资源，调度并发工作时仍受对应共享边界约束。

MIG按支持的profile划分GPU实例GI，分配SM、内存相关资源和引擎，提供规定的隔离边界；一个GI还可拆成多个CI，这些CI拥有各自计算资源，但共享父GI的内存和部分引擎。不能把GI与CI的隔离强度混为一谈。

MPS主要让多个进程的CUDA工作更有效地并发，并可提供版本相关的资源配置能力；它不应直接等同于MIG硬件分片。较新MPS的特性还需查对应版本。选择方案时先明确目标是利用率、容量分配、延迟可预测性还是故障边界。

具体例子

两个CI位于同一GI内，即使SM分开，内存带宽仍可能互相影响；使用MPS的两个客户端也不能默认各自得到独立L2。

先预测隔离更强可能改善可预测性，但减少单任务可用资源；吞吐需按份额比较。

容易混淆

把MPS active-thread百分比当成固定独占的完整显存/缓存分区。

检验理解为什么只报告“使用了MIG”不足以解释性能？

还需说明GPU型号、GI/CI profile、资源份额与同GI内是否有其他工作。

H20.08

功耗、频率与持续性能

#

同一kernel同一指令，为什么连续运行后速度会变化？

最小状态
周期工作量、实际时钟、功耗/温度和观测窗口。
变化规则
设备策略调整频率，使相同周期工作映射到不同墙钟时间。

实际SM和内存频率受功耗预算、温度、负载类型和设备策略影响。代码即使执行相同指令和字节量，每秒可用周期也可能变化；短时间boost结果不能直接代表持续运行吞吐。

评估应记录预热、运行时长、时钟、温度和功耗限制原因，并在相近热状态下比较。NCU可能使用时钟控制和replay，使profiling环境不同于生产；计数器解释与最终时延测量需分开，不要把频率差异归功于算法改进。

具体例子

两个版本执行周期相近，但B测量时SM频率更低，墙钟时间可能更长；应先判断是否受power/thermal限制，而非马上增加warp。

先预测纯算术占比高时频率下降更可能拉长时间；内存受限负载的影响可能不同。

容易混淆

只用铭牌boost频率计算实测利用率，忽略持续时钟与profiling设置。

检验理解每次冷启动都更快而长跑变慢，首先补采什么？

补采频率、功耗、温度及clock event reasons，检查热稳态和限频。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

launch__waves_per_multiprocessor

每次launch的理论wave规模信息；不足一轮或存在部分wave时，提示整卡填充和尾部风险。

它不是逐时刻的实际SM分配轨迹；CTA时长不均、并发工作和cluster调度会改变真实行为。

[5]

LaunchStats / Occupancy（sections）

将grid/block、可用SM与资源限制对应，检查kernel是否提供了足够的可驻留工作。

NCU单kernel结果不能证明应用中copy与kernel重叠；并发分析应结合Nsight Systems时间线。

[5]

nvidia-smi / NVML（辅助观测，非NCU指标）

记录SM/内存时钟、功耗、温度及clock event reasons，区分kernel瓶颈与频率限制。

采样频率与支持字段依设备/驱动；监控样本不是单kernel精确归因，也不要擅自修改功耗或时钟。

[6]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

从kernel时间走到应用时间（实验设计，未执行）

只改变

固定总数据和计算：比较串行H2D→kernel→D2H与分块多stream流水；再改变grid大小观察尾部。

预计现象

有足够分块、异步拷贝能力和独立资源时可重叠；过小块受提交开销影响，过大块可能缺乏pipeline深度。

记录什么

用正确同步后的端到端墙钟计时和Nsight Systems时间线确认重叠；用NCU分析代表kernel，记录时钟、功耗及传输方向。

排除干扰

pageable与pinned host memory、默认stream隐式同步、NUMA位置、设备间拓扑、其他任务、热稳态与profiling序列化。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
