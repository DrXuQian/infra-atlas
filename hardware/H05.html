H05.01

PC 如何决定下一条指令

#

下一条指令地址从哪里来，为什么有寄存器数据也可能发不了？

最小状态
线程/线程组PC、分支条件、目标地址与当前指令缓冲。
变化规则
根据控制流更新PC，只有与当前合法路径匹配的指令才能进入发射候选。

PC描述执行接下来需要的指令位置。普通顺序路径向后推进，分支、调用和返回则选择不同目标。调度器即使有resident warp和已经准备的算术输入，若下一条指令尚未取回或控制流目标尚未确定，也不能凭空发射它。

Volta以前共享warp PC加mask的执行模型，与Volta及之后的每线程执行状态不同；但都需要把合适线程组的控制位置转化为可发射指令。模拟器中PC与指令缓冲内容不匹配会触发flush，这展示了控制路径如何改变取指流，不等于声明真实GPU采用同样的缓冲实现。

具体例子

教学指令序列A→B→C，B是条件分支。若条件选择D，已经按顺序准备的C不能作为该线程组的下一条有效指令直接执行。

先预测改变分支目标布局可能改变取指供给，即使算术操作数不变。

容易混淆

认为只要ALU输入ready，就与取指和控制流无关。

检验理解分支没有数据访存，为什么仍可能导致发射间隙？

目标路径确定、取指和指令供给也需要推进；具体成本依架构和代码布局而定。

H05.02

instruction cache miss

#

instruction cache miss 与 data cache miss 是一回事吗？

最小状态
PC访问序列、指令缓存工作集、miss返回与待取指warp。
变化规则
所需机器码不可用时等待取回，返回后才能恢复相应指令供给。

指令缓存保存将要执行的机器码，而数据缓存保存load/store访问的数据。大体积展开代码、频繁跳转到分散代码区域可能增加取指工作集；即使所有数据都在寄存器里，指令供给仍可能成为瓶颈。代码体积与动态执行次数也不同：短循环可反复执行很多次。

论文用逐渐增长的独立指令序列探测不同设备的指令缓存转折点；这些容量与延迟不能跨代直接套用。NCU的no_instructions表示等待取指选择或指令cache miss等情况，并不是专门计数I-cache miss。必须结合代码体积、SASS布局和单变量对照来验证。

具体例子

相同总FMA次数，一版用小循环反复执行，另一版完全展开为很长SASS。后者少了循环控制，但可能扩大取指工作集。

先预测展开体积跨过某个缓存有效容量后，取指等待可能出现转折。

容易混淆

看到no_instructions偏高，就直接声称L1数据cache miss很多。

检验理解算术与数据访问完全一样，还可能有取指性能差异吗？

可能。SASS静态体积、跳转布局和前端供给方式仍可不同。

H05.03

指令缓冲不足

#

instruction buffer 空了，与 instruction cache miss 有什么区别？

最小状态
指令缓存可用性、每warp指令缓冲和前端服务机会。
变化规则
取指/解码把合法路径指令放入缓冲；scheduler只消费已准备的下一条。

指令缓存是提供机器码的存储层次；指令缓冲则把已经取得并准备供给的指令暂存给执行前端。缓存命中不保证每个warp每个周期都有下一条指令可用，取指选择、解码供给、控制流改变以及有限缓冲都可能形成间隙。

所引GPGPU-Sim显式检查ibuffer_empty，因控制PC不符还会清空已准备内容。这是可读的前端模型，适合分离“代码存在于缓存”和“下一条指令已经进入可用缓冲”两种状态。真实硬件的缓冲深度与仲裁不可从一个NCU样本反推出精确数值。

具体例子

教学W0的下一条代码已在指令cache里，但本轮前端先服务W1；W0缓冲尚空，仍不参与发射，稍后取指完成才能变成候选。

先预测提高缓存命中后若供给带宽仍不足，空缓冲现象可能保留。

容易混淆

把no_instructions的全部样本都换算成指令缓存缺失次数。

检验理解缓存命中率100%是否足以证明前端从不限制发射？

不够。取指/解码带宽、服务顺序和buffer供给还可能限制。

H05.04

分支发散与活动掩码

#

一半线程走 A、一半线程走 B，代价来自哪里？

最小状态
分支条件、各路径参与mask、路径动态指令数。
变化规则
逐个推进合法路径，只更新该路径参与线程的状态。

同一warp在数据相关分支处分成不同控制路径时，各路径分别只激活对应线程。路径A执行时，选择B的线程不会代替A做另一条指令；所以有效lane利用可能下降。不同warp各自选择完整路径，则不构成同一warp内部的发散。

性能损失取决于两条路径的指令量、参与分布、重汇合方式及编译器是否改用predication。若只有少量线程走一条非常长的路径，它可能决定这个warp的总进展；但短分支的影响也可能被其他warp工作或管线资源掩盖。应看最终SASS而非仅看C++中的if。

具体例子

路径A有8条指令、B有2条，16个lane走各自路径。在简化串行路径模型中，两套路径都需推进，而不是只支付平均5条warp指令。

先预测保持总标量工作时，warp内交错路径通常需要更多低参与度的warp指令。

容易混淆

把不同warp之间的分支差异称作warp内branch divergence。

检验理解所有32线程都走A，与16/16分开相比，哪种更容易保持满lane？

所有线程同一路径时更容易；但端到端速度还取决于该路径工作量与其他瓶颈。

H05.05

分支汇合的机制与模型

#

分支汇合是所有线程自动同时到达下一行吗？

最小状态
各路径PC、参与mask、模型汇合点与必要的同步协议。
变化规则
教学栈模型在路径到达汇合点时收回路径记录；程序可见的通信顺序仍由同步契约保证。

汇合描述分离路径上的线程再次可以共同推进的执行组织。经典post-dominator模型保存路径PC、active mask与汇合点，待各条路径完成相应部分后合并集合。GPGPU-Sim的simt_stack::update是这种机制的可读示例。

这个模型不能直接当成Volta ITS的全部实现，源码的词法if结束位置也不自动提供线程间内存同步。算法若要交换shared memory数据，仍须使用满足参与条件的同步原语；需要所有指定lane共同参与的warp操作，也应遵守mask契约。将控制汇合与内存可见性分开非常重要。

具体例子

A路径写shared[0]、B路径读shared[0]，仅因为两段C++在同一个if后汇合，不能为任意未同步的跨线程读写建立正确的先后关系。

先预测控制流看似重新一致，不代表跨线程数据交换已被正确排序。

容易混淆

把SIMT stack动画画成现代NVIDIA每线程调度的完整电路，或把汇合等同memory fence。

检验理解代码重新到达同一行，是否就能省略所需的__syncwarp？

不能。应以同步原语与CUDA内存模型的保证判断，而不是词法位置。

H05.06

predication 与分支的取舍

#

predication 避免分支后，是否所有工作都免费消失了？

最小状态
活动集合、每lane谓词、predicated指令序列和副作用。
变化规则
对active且predicate=true的线程执行可见效果；假谓词不等于整条warp指令未被调度。

谓词化给指令附加每线程条件，控制哪些线程真正读操作数、计算地址并写结果。短条件块可能被编译器转为一串predicated指令，从而不走真正的分支路径切换；但这些指令仍会进入调度，因此并非零发射成本。

它常在少量操作时避免控制流开销，却可能对很长或昂贵的条件块浪费指令供给和发射机会。应分别观察active线程与pred-on线程，检查SASS里是否真的存在分支。不能把每个带if的源码片段都算作一次动态发散，也不能把所有predicated-off线程按正常load算流量。

具体例子

一条@P0 store仅有8个lane谓词为真：关闭的lane不应产生对应地址求值和写入，但这条warp指令本身仍占用调度过程。

先预测条件块变长后，谓词化的动态发射成本可能逐渐超过分支方案。

容易混淆

认为predicate=false的线程仍会发出相同的内存访问，或反过来认为整条指令完全没有成本。

检验理解有if却没有branch SASS，为什么仍可能有效线程比低？

编译器可能谓词化了条件块，很多线程在这些指令上pred-off。

H05.07

Independent Thread Scheduling

#

Independent Thread Scheduling 改变了哪些假设，又没有改变什么？

最小状态
每线程PC/调用状态、逻辑warp身份和显式协作mask。
变化规则
调度组织同warp内适合共同执行的线程；等待与汇合可在子warp粒度发生。

Volta及之后维护每线程执行状态，可在子warp粒度分歧、等待和重新组合，这使某些线程间协作模式更灵活。它打破的是“同warp线程在每一条指令上天然锁步”的旧假设，尤其影响未显式同步的shared memory交换和warp collective参与集合。

它没有把每个线程变成拥有独立发射器的CPU核，也没有取消32线程warp及共同指令执行的性能意义。代码仍应明确通信协议，使用*_sync intrinsics和合适mask，并通过racecheck/synccheck等工具检查错误。不要把某次观察到的线程推进顺序当作正确性保证。

具体例子

旧代码让lane0先写shared、lane1紧接着读，并仅依靠“同warp自然同时走”。在ITS下应显式建立同步与可见性，而不是赌编译和调度。

先预测依赖隐式锁步的程序可能不再可靠，显式合法同步应保持正确性。

容易混淆

认为ITS完全消除了分支发散代价，或任意warp内通信都不再需要同步。

检验理解ITS是否允许忽略__shfl_sync中的参与mask？

不允许。线程状态更灵活反而要求更明确地遵守参与和同步契约。

H05.08

循环展开导致的指令体积增长

#

循环展开为什么可能先变快，再变慢？

最小状态
展开因子、总工作量、静态指令体积和寄存器活跃区间。
变化规则
编译器复制循环体并重排；收益与代码/资源代价同时进入生成结果。

展开减少循环控制，也可能暴露更多独立指令供编译器交错安排。但它同时增加静态SASS体积和活跃值数量，可能带来更大指令缓存工作集、更高寄存器占用、spill或occupancy下降。这些变化之间存在竞争。

因此扫描展开因子时要记录至少三条曲线：实际耗时、生成代码与寄存器资源、取指及依赖相关观测。拐点不必只有一种原因；若寄存器数恰好跨台阶，应先排查驻留变化；若资源不变而代码体积增大后no_instructions上升，才更支持取指压力假设。

具体例子

把展开因子从1、2、4、8逐步提高，保持总迭代次数相同。若8时spill出现，性能回落不能只归咎于I-cache。

先预测适度展开可能改善ILP，过度展开则可能因前端或资源压力反转收益。

容易混淆

把#pragma unroll视为总是提升性能的开关，或一次改变展开与block大小后只归因于展开。

检验理解怎样区分I-cache问题和register spill问题？

检查SASS代码体积、寄存器报告、local load/store与取指采样，并做保持其中一项稳定的对照。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

smsp__pcsamp_warps_issue_stalled_no_instructions

PC采样显示等待取指选择或指令缓存缺失等情况；代码工作集扩大时可作为前端压力线索。

名称为no_instructions复数。它不是I-cache miss计数，短kernel也可能偏高。

[4]

SourceCounters / WarpStateStats

将采样定位到SASS并查看线程参与分布，区分分支与谓词化。

使用 ncu --list-sections核对标识；采样位置与原因不能独自还原控制流硬件。

[4]

InstructionStats

比较展开前后的动态指令组成，配合静态SASS体积判断前端与执行工作变化。

动态指令数和静态代码字节数不是同一指标；同时检查寄存器和local memory。

[4]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

实验设计：展开因子与控制路径（未执行）

只改变

固定总工作量，扫描循环展开因子；另做warp一致条件与warp内交错条件的独立对照。

预计现象

适度展开可能减少控制开销并提升ILP；过度展开可能增加代码和寄存器压力。交错条件可能降低每条指令有效线程数。

记录什么

反汇编判断branch/predication，记录静态代码尺寸、动态指令、寄存器、local流量、no_instructions和普通耗时。

排除干扰

编译器删除或化简循环、工作量变化、cache热状态、occupancy台阶及不合法同步。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
