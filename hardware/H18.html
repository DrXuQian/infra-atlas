H18 / ASYNCHRONOUS PIPELINES

异步搬运与流水化

“提前发起”何时才会变成真正的计算与搬运重叠？

用缓冲区所有权和完成条件理解cp.async、group、mbarrier与跨proxy顺序；异步不意味着可以提前消费。

适用范围

cp.async以SM80+经典global→shared路径为主；tx-count及TMA相关mbarrier以SM90范围说明。图为显式同步的双缓冲教学状态，不给真实延迟或重叠比例。

先备知识：H06 依赖 · H10 Shared memory · H15 同步与顺序

CHANGE ONE THING

缓冲区什么时候可以再次写入？

4 个 tiles，1 个搬运引擎和 1 个计算引擎；搬运 3 周期、计算 4 周期，同一引擎一次处理一个 tile。先完成旧操作，再启动最早 ready 的计算，最后向空闲缓冲提交新搬运。没有模拟 cp.async / TMA 指令的全部细节。

01

H18.01

普通 load/store 与 cp.async 的数据路径

#

cp.async 改变了 global→shared 的哪一段路径？

最小状态
global源、shared目的、地址/对齐信息和未完成拷贝。
变化规则
发起请求后目的数据仍不可消费，完成并同步后才能读取。

普通线程代码经常先把global数据load到通用寄存器，再store到shared。SM80+的经典cp.async允许发起global到shared的异步拷贝，避免把整份搬运数据先作为普通寄存器中间值持有，线程可在完成前做独立工作。

它不取消地址生成、对齐、缓存和带宽限制，也不保证一次API调用必然编译成该路径。目标类型、拷贝尺寸、编译目标和库实现都要检查。RF压力下降与重叠改善是两种可能收益，应分别验证，不能只比较源码行数。

具体例子

一个线程将16字节搬到shared用于后续计算：普通路径可能占用中间数据寄存器；cp.async完成后消费者直接从shared读取。

先预测如果原先中间值压力显著，异步路径可能减小RF占用并增加重叠机会。

容易混淆

把cp.async解释成完全不使用任何寄存器或不经过缓存/内存子系统。

检验理解用异步API后寄存器数没下降，是否一定没有优化？

不一定。寄存器分配可能由其他活跃值决定，且收益也可能来自重叠；需检查SASS和耗时。

02

H18.02

async copy 的发起与完成

#

指令已经发出去，为什么还不能读 shared 目的地址？

最小状态
发起者、目的buffer、pending拷贝与消费者范围。
变化规则
完成事件使数据可交付，范围正确的同步再允许消费者使用。

异步发起意味着提交工作与工作完成分离。执行线程继续前进时，数据可能仍在访问global或写入shared；目的地址即使存在，也不代表其中的新数据已对消费者可见，必须使用对应的完成机制。

经典cp.async group默认由发起线程跟踪。若tile由多个线程共同搬运并由其他线程读取，各线程等到自己的拷贝完成还不够，通常还需CTA或正确作用域的协作同步。不要把线程局部完成错误扩大成全block完成。

具体例子

线程0的copy完成，但线程1的copy仍在途；线程0若直接读取整个tile，会提前消费线程1负责的区域。

先预测过早读取可能偶尔看似正确，但加负载或变时序后会暴露数据竞争。

容易混淆

只加普通__syncthreads而不先建立async拷贝完成条件，或只wait自己的copy就消费所有线程数据。

检验理解消费者与producer不同线程时，要检查哪两类条件？

异步工作是否完成，以及完成结果是否通过正确的跨线程同步交给消费者。

03

H18.03

commit group

#

commit_group 是把数据搬完，还是给工作划分边界？

最小状态
每线程未提交copy集合、已提交group序列与buffer映射。
变化规则
commit把未提交集合封装成新group，不改变copy已经完成与否。

cp.async.commit_group把当前线程此前已发起但尚未提交的cp.async组成一个新group。它建立的是完成跟踪边界，不等待数据返回；空group也有定义，组内多个copy之间并没有因为commit就形成逐条内存顺序。

组的粒度决定后续wait能够保留多少新工作在途。工程上常按tile或stage组织，但程序必须自行建立group与buffer的关系。CUDA高层pipeline还存在warp entanglement，分歧commit可能造成过度等待，不能简单把逻辑线程批次当成独立硬件队列。

具体例子

线程先发起copyA和copyB，再commit形成G0；随后copyC再commit为G1。G0/G1都可能在途，commit本身没有消费任何数据。

先预测把commit推迟或分歧化可能改变等待行为，但不自动提高有效重叠。

容易混淆

把commit当作flush或完成barrier，并认为同组对同一目的地址多次copy有确定覆盖顺序。

检验理解commit之后pending group数量是否一定为零？

不是，它通常增加一个已提交group；完成要由后续wait或barrier确认。

04

H18.04

wait group

#

wait_group 1 是等待第1组吗？

最小状态
已提交group的时间顺序、N和buffer所属group。
变化规则
等待较早group完成，保留最多N个最近group在途。

cp.async.wait_group N的N不是组编号；它限制仍允许pending的最近group数量。执行线程要等到更早的group完成，直到最多只剩最近N组尚未完成。N=0表示等待此前已提交的所有group完成。

这只建立相应cp.async工作的完成和可见性，不替代对任意普通load/store的内存排序。它也不会把未提交copy自动纳入已提交group；wait_all才包含commit加wait0的语义。多线程共同供数还必须建立合适的线程间同步。

具体例子

已提交G0、G1、G2，wait_group 1返回时G0/G1必须完成，G2仍可能pending；此时只能消费对应已完成buffer。

先预测适当保留新group在途可创造重叠；过早wait0会把流水线串行化。

容易混淆

把N当作group ID，或wait_group后读取一个尚未commit的copy目的地。

检验理解G0、G1两组之后wait_group 1，G1数据保证可读吗？

不保证；它允许最新的G1仍pending，保证的是较早group按规则完成。

05

H18.05

双缓冲的所有权切换

#

双缓冲的核心是两个数组，还是两套所有权？

最小状态
每buffer的EMPTY/FILLING/READY/READING状态和代次。
变化规则
空闲→填充→完成→消费→释放，复用必须经过完整生命周期。

两个buffer只有在生命周期分离时才形成流水：producer只能写EMPTY/FREE的buffer，consumer只能读READY且完成同步的buffer。consumer结束最后一次使用后释放所有权，producer才可覆盖旧数据。

因此“拷贝已完成”和“buffer可复用”不是同一事件。前者允许开始消费，后者要求所有消费者已停止读取；异步MMA可能在发起后仍读取shared操作数，所以不能仅以MMA发射作为释放时刻。应由该家族规定的完成协议判定。

具体例子

B0供当前tile计算，B1填充下一tile；当前计算完成且不再读B0后，B0才用于下下个tile。

先预测缺少释放握手的双缓冲可能在某些尺寸正确、另一些尺寸出现随机误差。

容易混淆

在异步MMA刚发起时立即覆盖其shared输入，认为已发射等于已消费完。

检验理解READY buffer能立即交还producer吗？

不能。READY表示可消费，只有consumer完成全部读取后才可FREE。

06

H18.06

多 stage 的延迟隐藏与资源代价

#

把stage从2加到4，为什么可能更慢？

最小状态
stage数、每stage字节、计算间隔、搬运延迟和驻留上限。
变化规则
增加stage扩大可在途窗口，同时提高每CTA资源需求。

更多stage增加可在途的tile数量，理论上给较长搬运延迟提供更大的计算覆盖窗口。但稳态吞吐上限仍由计算或搬运资源决定；如果现有stage已经足够供数，继续增加不会提高该上限。

每个stage消耗shared、barrier状态，有时还延长寄存器活跃区间。资源占用增加可能减少驻留CTA、加重尾部或增加prologue/drain成本。因此stage数应结合tile耗时与资源台阶测量，不能用固定公式替代实际验证。

具体例子

每tile占用24KiB shared，2 stage为48KiB，4 stage为96KiB；在某设备上这可能跨过驻留台阶，损失其他CTA提供的并发。

先预测在依赖等待下降之前可能受益，超过覆盖需要或资源台阶后可能退化。

容易混淆

认为stage越深越接近峰值，忽略容量和短K循环的启动成本。

检验理解只有2个K tile时，设计6-stage流水通常有什么问题？

大部分容量无法形成稳态重叠，初始化、等待和资源占用可能得不偿失。

07

H18.07

mbarrier 的 arrival、phase 与完成条件

#

arrival 已经归零，mbarrier 为什么还没完成？

最小状态
phase、expected/pending arrival计数、tx-count与等待token。
变化规则
到达和事务完成分别减少对应计数，两者归零后原子切换phase。

mbarrier跟踪当前phase的到达条件；从Hopper起还可通过tx-count跟踪异步事务完成量。以TMA字节完成机制为例，expect-tx增加期望字节，硬件完成相应搬运后complete-tx减少它；线程arrival与字节完成是两种独立条件。

一个phase需要pending arrivals和tx-count都归零才能完成并进入下一phase。消费者必须等待正确phase/token；buffer循环复用时还要同步更新代次。错误的期望字节数、漏到达或等待旧phase都可能导致死锁或提前消费。

具体例子

barrier等待1次arrival与4096字节：线程arrive后arrival=0，但仍有4096字节pending；搬运完成令tx=0，phase才结束。

先预测漏报或多报完成量会破坏等待协议，即使线程都已到达也可能卡住。

容易混淆

把arrival次数与搬运字节数混为一个计数，或认为phase变化本身表示buffer已被消费完。

检验理解arrival=0、tx=1024时消费者可以继续吗？

不可以，该phase仍有异步事务未完成。

08

H18.08

不同访问 proxy 之间的顺序

#

普通 shared store 和异步单元读取之间为什么还需要 proxy 顺序？

最小状态
generic写、async读、对应proxy及完成/线程同步机制。
变化规则
先建立跨proxy顺序，再发异步工作，最后等待完成并移交所有权。

PTX把不同访问机制区分为proxy。普通线程的generic访问与异步操作对同一shared位置的访问，并不总能仅靠程序顺序建立所需可见性；适用场景要通过fence.proxy.async等规定机制连接两种proxy。

proxy fence建立访问顺序，不等价于等待异步操作完成，也不自动让不同线程彼此到达。正确协议要同时解决三个问题：producer数据如何发布给async单元、异步工作何时完成、consumer线程如何得知并安全复用。不同指令家族需按各自文档组合。

具体例子

线程普通store写入WGMMA的shared操作数后，按要求做async proxy fence，再发MMA；在消费MMA结果前仍需该家族的完成等待。

先预测删除必要fence可能产生时序相关错误，而不是仅仅改变性能。

容易混淆

把一个proxy fence当成“所有线程、所有拷贝和所有MMA均完成”的万能屏障。

检验理解已有__syncthreads时，是否总能删除proxy fence？

不能。线程同步与跨proxy排序承担不同职责，必须按访问组合检查文档。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

MemoryWorkloadAnalysis（section）

比较普通load/store与async路径的global/shared流量和请求，确认优化没有额外搬运或重复读取。

相同字节量也可能因更好的重叠而加速；不能只靠流量减少判断async是否有效。

[5]

Occupancy / LaunchStats（sections）

增加stage后检查shared memory和寄存器占用、理论与实际驻留变化。

更深流水会增加资源需求；occupancy下降不自动表示更慢，应与总时间和等待对照。

[5]

SourceCounters（section）

检查消费者等待点及相关stall样本，结合SASS确认是否用了预期的异步搬运指令。

采样比例不是所有SM共同损失的时钟；未提供跨GPU通用的“async overlap百分比”。

[5]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

stage数与等待位置（实验设计，未执行）

只改变

对同一tile算法比较1、2、3个stage；保持输入、输出和每tile搬运字节不变，记录实际资源使用。

预计现象

搬运与计算相当且存在可重叠窗口时，多stage可能缩短稳态时间；供数已够或驻留骤降时不再受益。

记录什么

先做数值和race检查，再记录CUDA event时间、SASS、shared/RF占用、NCU内存流量与等待位置；单独看prologue和drain。

排除干扰

错误的barrier phase、等待太早、buffer提前复用、边界清零、编译器生成同步拷贝、计时窗口过短。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
