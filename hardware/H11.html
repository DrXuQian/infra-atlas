H11 / CACHE HIERARCHY

缓存体系

命中缓存以后，为什么还可能很慢？

把驻留、命中、请求量、服务带宽和依赖延迟分开。缓存优化要减少关键路径代价，而非孤立地追求命中率。

适用范围

官方缓存语义与 NCU 统计口径；set/way 示例采用显式教学模型。物理几何、索引和替换算法不跨 GPU 代际外推。

01

H11.01

cache line 与 sector

#

line 与 sector 各决定什么？

最小状态
标签、4 位 sector 有效位、目标地址。
变化规则
匹配标签后检查目标 sector 是否有可用数据。

Line 通常关联标签、替换与地址分组，sector 是更细的有效数据和传输统计单位。以当前 NCU 内存表的 128B line、32B sector 模型为例，一条 line 可分四份；标签存在，不表示每份数据都已被取回。

需区分 tag miss 与 tag hit 但目标 sector 无效，二者都会产生 sector miss。论文推测的缓存几何、模拟器配置和工具记账单位可能不同；做跨架构比较时，应说明采用哪种定义，不能从一次小 load 推出实际显存总线流量。

具体例子

line 基址为 0，仅 [0,31] 有效：读取地址 8 命中，读取地址 72 仍请求 S2；两次 line 标签相同。

先预测同标签改读未填充 sector，仍增加 sector miss。

容易混淆

将一次 4B load、一个 sector 和一次 DRAM 传输当作同一数量。

检验理解tag hit 保证不访问下一级吗？

不保证，目标 sector 还必须有效。

02

H11.02

tag 查找与数据访问

#

查到标签后为何仍要等待？

最小状态
命中结果、数据服务队列、端口可用性。
变化规则
完成数据服务和返回后才解除消费者等待。

标签查找回答地址是否由当前缓存持有，数据阵列访问才取出内容。两者各有请求、端口与返回路径；即使逻辑上命中，仍可能因数据端口占用、内部处理波次或返回带宽而排队。Hit 不是免成本的完成事件。

分析时分开是否命中、何时开始服务、何时到达消费者。NCU 的 tag/data 阶段和端口图可辅助定位，但图中分段不是任意相加的固定周期；真实管线会重叠，同样地址的响应时间也会随并发压力变化。

具体例子

两个请求都命中，教学数据端口每步只能服务一个。第二个请求的命中结果不变，返回却晚一步。

先预测并发先提升吞吐，饱和后主要增加排队。

容易混淆

把 100% 命中率等同于没有内存等待。

检验理解增加命中请求可能使延迟变长吗？

可能，排队和共享端口竞争会延后返回。

03

H11.03

set / way 与冲突失效

#

总容量有空余，为什么也会驱逐？

最小状态
明确 set 映射、每组 way 数、替换策略。
变化规则
miss 只在目标 set 中选择替换项。

组相联教学模型先把地址映射到 set，再占用该组某个 way。总容量有空闲不代表目标组有空位；多个热地址集中到一个组，会反复替换彼此，这叫冲突失效，区别于整个工作集超出缓存容量。

真实 GPU 的组或分区选择可能包含哈希，不能简单照搬地址取模公式。模拟器可固定映射对照；真机应扫描地址间隔，同时排除 TLB、合并效率和内存分区变化。微基准观察支持的是特定装置下的假设。

具体例子

假设 4 组、每组 2 way，A/B/C 都映射 set 0。LRU 下 A,B,C,A 会驱逐并重新读取 A，另外三组仍可为空。

先预测将一个热地址分散到别组可在总容量不变时降低 miss。

容易混淆

把教学 modulo 索引和 LRU 写成 NVIDIA 通用实现。

检验理解翻倍总容量必然消除冲突吗？

未必；目标组的 way 数和映射不变时，冲突可继续。

04

H11.04

容量失效与工作集

#

容量失效只取决于数组大小吗？

最小状态
工作集、重用间隔、有效容量、冷热状态。
变化规则
新数据改变驻留集合，重读已驱逐数据产生 miss。

工作集是重用时间窗口内必须保留的数据，不等于程序分配的总数组。大数组的一次扫描未必有缓存复用需求；一个小热集合也可能被中间插入的大量一次性访问驱逐。重用距离把访问顺序和保留容量联系起来。

容量扫描应控制地址模式、读取字节与初始冷热状态，并区分冷启动和稳态。阈值不一定锐利：组冲突、sector 分配、共享客户端、替换优先级与 carveout 都可能使有效容量小于标称容量。仅凭一个拐点不足以重建缓存结构。

具体例子

缓存仅保留 4 条 line；A 重用前只访问 B/C/D，可能仍驻留。插入 E/F 后，A 就可能在下一次使用前被驱逐。

先预测缩短重用间隔且不增加搬运时，下级流量可能减少。

容易混淆

把申请的 1GB 内存直接当作每个阶段的 1GB 活跃工作集。

检验理解相同总读取量，tile 化为何可能减少 miss？

它缩短重用距离，降低需同时保留的数据量。

H11.05

L1 与 shared memory carveout

#

给 shared 更多空间会付出什么？

最小状态
统一存储容量、carveout 档位、每 block 需求。
变化规则
驱动选择可满足需求的配置，L1/shared 容量随之变化。

许多 NVIDIA 架构让 L1 数据缓存和 shared memory 共用统一片上存储，通过 carveout 选择共享内存容量档位。更大 shared 可支持更大 tile，但可能压缩 L1 容量。具体可选档位和最大值依架构，不是任意整数容量。

PreferredSharedMemoryCarveout 是偏好，驱动还须满足 kernel 的 shared 需求。它与每 block 动态 shared 申请量、超过默认限制时的 opt-in 是不同概念。评估时同时检查 L1 命中、驻留 block 数与最终执行时间。

具体例子

扩大共享 tile 减少全局重读，却使每 SM 从驻留 3 个 block 降到 2 个，并可能减少 L1 容量；最终收益需计时验证。

先预测扩大 carveout 可能降低 L1 命中，而 shared 用量未增加。

容易混淆

认为 carveout 百分比精确对应任意字节数，或直接等于每 block 分配量。

检验理解shared 申请量不变，carveout 还会影响性能吗？

可能，L1 容量及缓存行为仍可改变。

06

H11.06

L1、L2 命中分别省掉哪段路径

#

L1、L2 命中分别省下哪段路径？

最小状态
访问类型、数据位置、L1/L2 命中状态。
变化规则
本级无法供数才继续请求，命中返回也消耗资源。

普通 global read 的简化路径中，L1 hit 可避免本次请求继续访问 L2；L1 miss 而 L2 hit 可避免从设备显存取数，但仍需走 SM 与 L2 间的请求和返回路径。两类命中节省的服务、互连和排队成本不同。

还需确认数据位于本 GPU、系统内存还是 peer GPU，L2 miss 的下一跳不一定是本地 HBM。逐层比较时保持访问类型一致；store、atomic 与异步搬运可能有不同路径，不能把普通 load 的图机械套到所有操作。

具体例子

128B 的四个 sector 全部 L1 miss、L2 hit，HBM 读取可以很少，L1↔L2 却仍承载数据；很多 SM 同时如此可打满片内链路。

先预测L2 命中上升可减少 HBM 流量，片内返回压力仍很高。

容易混淆

显存带宽低就断言没有访存瓶颈。

检验理解同样 L2 命中率为什么耗时不同？

请求量、依赖关系、片内带宽或分区分布可不同。

H11.07

cache operator 的作用边界

#

cache operator 能替代同步吗？

最小状态
缓存限定符、复用模式、已合法建立的同步。
变化规则
策略提示改变缓存处理偏好，不创造 happens-before。

PTX .ca、.cg、.cs 等限定符表达缓存或驱逐偏好，例如 .cg global load 以绕过 L1、在 L2 及以下缓存为目标，.cs 面向流式使用。它们改变性能路径，不替代 atomic、release/acquire 或 barrier 的语义。

先保证程序无数据竞争，再比较缓存策略。绕过 L1 可能避免污染，也可能丢失复用；应核查最终 SASS、目标指令及架构的支持。源码多一个修饰词并不意味着某种缓存计数或性能一定按预想改变。

具体例子

流式 B 挤掉反复使用的 A 时，改变 B 策略可能保住 A；若 B 下一步还要重读，同样修改又可能变慢。

先预测避免污染有效时 A 命中可上升；程序正确性不应依赖该提示。

容易混淆

只加 .cg 或 volatile，就假定另一个 SM 的读取已同步。

检验理解.cg 是否自动消除跨线程 data race？

不会，缓存提示不建立线程间的先后关系。

H11.08

L2 persistence 与驱逐优先级

#

persisting 会把数据永久锁在 L2 吗？

最小状态
保留预算、窗口范围、属性比例、并发窗口。
变化规则
请求获得优先级但仍可因容量竞争被驱逐。

CC 8.0+ 的 L2 persistence 通过 set-aside 和 access-policy window 给选定访问更高保留优先级。窗口描述地址范围，hitRatio 是让访问获得相应属性的比例提示，不是执行后测出的真实缓存命中率。

数据仍竞争有限容量，并发 stream 的窗口也会互相影响。总需求超预算时比例全设为 1 反而可能抖动；阶段结束应重置不再需要的保留属性。MIG 与 MPS 还有配置限制，应用前必须核对运行模式。

具体例子

教学保留预算 12KB，两个 stream 各有 12KB 热窗口；双方都试图保留全部数据会互相挤占，降低属性覆盖比例可能减少抖动。

先预测总需求过大时缩小窗口可能比继续扩大属性覆盖更有效。

容易混淆

把 hitRatio=1 解释成未来每次读取都 L2 hit。

检验理解persisting 窗口越大一定越好？

不一定，容量竞争和其他热点驱逐可能更严重。

09

H11.09

constant cache 的广播与地址分散

#

同一个常量地址为什么特别合适？

最小状态
参与 mask、lane 地址、唯一地址集合。
变化规则
相同地址可共享服务，分散地址需要更多服务。

常量路径适合 warp 内相同地址的读取。若一条指令中各 lane 请求多个不同地址，可能按唯一地址分批服务；即使命中常量缓存，地址分散也会增加工作。因此统一系数与每 lane 随机查表是两类不同负载。

应区分源码 __constant__、kernel 参数和 SASS immediate constant 读取。它们不能仅靠一个 stall 名称混为一谈。需要同时检查 SASS、同指令的唯一地址数与时间，容量命中率无法单独解释地址分散造成的服务代价。

具体例子

32 lane 同读 c[3] 与分别读 c[lane]，逻辑字节数都为 128B，但唯一地址分别为 1 和 32，服务代价可能不同。

先预测缓存驻留不变时，唯一地址数增加可能降低吞吐。

容易混淆

常量在片上，所以任意随机索引都像寄存器一样快。

检验理解32 lane 只读两个地址时，应关注什么？

同一 warp 指令的唯一地址数 2，以及是否命中缓存。

10

H11.10

命中率高但性能仍差的原因

#

命中率高而性能差先看哪里？

最小状态
请求总量、并发数、依赖图、服务能力。
变化规则
关键路径由等待和资源竞争决定，命中只改变部分路径。

命中率是比值，不说明绝对请求量、服务速率或依赖。一串 pointer chase 即使大多 L2 hit，仍需上次返回后才能产生下次地址；大量独立 hit 则可能打满 L2 数据端口或返回链路。这两种情况都与缓存相关。

把判断改成可验证假设：延迟限制下增加独立链应先提高吞吐；带宽已满时增加并发主要增加排队。同步、计算和 grid 尾部也可能主导，所以应伴随发射活动和时间观察，不能只调缓存容量或追求最高 hit rate。

具体例子

两个 kernel 都 95% 命中：A 逐 load 依赖，带宽低却慢；B 大量独立 load，因片内带宽饱和而慢，优化方向相反。

先预测消除重复 hit 读取可保持命中率不变而缩短时间。

容易混淆

把 long scoreboard 一律解释成 HBM miss，或认为高命中率表示缓存已经最优。

检验理解命中率提高但时间不变，必然测错吗？

不一定，瓶颈可能在片内带宽、串行依赖或其他阶段。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

MemoryWorkloadAnalysis_Tables：L1/TEX、L2 的 Hit Rate / Sectors / Throughput

按访问类型比较 sector 命中率、绝对请求量和每秒字节；减少 miss 应伴随下游流量下降。

先用 ncu --list-sections 确认版本；分母不是源码 load 数量。记录缓存控制和 replay 设置。

[1]

MemoryWorkloadAnalysis_Chart：Ports 与 L1↔L2 链路

比较请求、返回路径与端口峰值占比，区分 miss 延迟和片内带宽限制。

高 L2 命中仍可占满端口；可用指标及图中模型依设备而变。

[1]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

工作集与重用距离扫描（实验设计，尚未执行）

只改变

固定线程映射与每次访问字节，只改变循环工作集；另做同工作集、不同重用间隔对照。

预计现象

若容量或冲突驱逐主导，第二轮访问的下级请求量会随工作集或重用间隔变化。

记录什么

CUDA event 时间、L1/L2 sector hit rate、Sectors 与下级字节；检查 SASS，记录预热及 NCU cache-control/replay。

排除干扰

工作集也改变 TLB 压力；并发 kernel、频率、carveout 和地址映射都会影响结果。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
