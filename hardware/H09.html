H09 / GLOBAL MEMORY · ADDRESS SETS

LSU 与全局访存合并

32 个线程执行同一条 load，究竟产生多少访存工作？

从参与 lane 的字节区间出发计算 sector 集合，再把请求、cache 命中和下层流量分别统计。

适用范围

地址算例限定为 CC 6.0+ 常见 32-byte sector 模型、32-lane warp、自然对齐的每 lane 4-byte load，除非单点另行声明。不是 HBM 总线逐拍仿真。

01

H09.01

从线程地址生成访存请求

#

合并访存看的是线程顺序，还是地址集合？

最小状态
参与掩码、每 lane 地址、访问宽度、sector 粒度。
变化规则
展开每个字节区间，映射到 sector 后对编号去重。

一次 warp 访存指令携带参与线程的地址与访问宽度。硬件需要服务的是这些字节区间的集合；把区间按支持的访问粒度分组，可以计算本次需要触及多少 sector。源码中线程编号连续，只是容易生成连续地址，并不保证实际地址也连续。

在本模块 32-byte sector 模型下，对每个参与 lane 求所有触及 sector 的编号，再去重计数。这个几何步骤先不考虑命中与否，也不把多个 warp 的请求自动合并为一个指令请求。请求数、sector 数和实际到达下层的流量属于不同统计层次。

具体例子

lane l 读 A+4l 时通常连续；lane l 读 A+4×index[l] 时，需要看到 index 的分布才能判断合并。

先预测相同 active lane 数也可能产生完全不同的 sector 数。

容易混淆

把“32 个线程一起执行”当成“一次 128-byte 连续读取”的保证。

检验理解把同一 warp 的 lane 地址顺序打乱但集合不变，sector 数会变吗？

在这里的集合模型中不会，覆盖的字节区间仍相同。

02

H09.02

对齐访问需要多少 sector

#

对齐的 32 个 float 为什么只覆盖 4 个 sector？

最小状态
A 的对齐、32 个 4 B 区间、32 B sector。
变化规则
连续区间按每 32 B 分段；全部所需字节必须落入所计 sector。

设起点 A 是 32-byte 对齐，lane l 读取 A+4l 开始的 4-byte float。32 个 lane 的区间正好连续覆盖 128 B；每 8 个 float 占一个 32-byte sector，所以共覆盖 4 个。这里的“4”来自明确的宽度与掩码，而不是 warp 的永恒常数。

如果每 lane 改成 8 B 或 16 B，并且地址仍构成连续无重复区间，总有效数据就变为 256 B 或 512 B，需要重新计算。若只有部分 lane 参与或多个 lane 重复同一地址，也会改变基线。因此 NCU sector/request 必须与那条实际 SASS 访存的访问宽度一起看。

具体例子

A=0：lane 0…7 触及 sector 0，8…15 触及 1，16…23 触及 2，24…31 触及 3。

先预测对齐与完整参与下，标量 float load 的平均比值应接近几何基线 4。

容易混淆

把 sector/request 超过 4 一概判为差访问，忽略 64-bit 或向量化 load。

检验理解32 lane 各读连续 8 B，起点仍对齐，需要多少个 32 B sector？

共 256 B，覆盖 8 个 sector。

03

H09.03

跨边界访问增加多少流量

#

只偏移一个 float，为什么可能多一个 sector？

最小状态
起点偏移、访问末端、sector 边界。
变化规则
计算首尾触及编号及中间区间，而非只看首地址是否对齐到元素宽度。

起点从 32-byte 边界后移 4 B，32 个 float 的联合区间变成 [A+4,A+131]。首尾跨过了原本四个 sector 的范围，需要第五个 sector 才能覆盖末尾。每个 float 仍可自然对齐，因此这种例子不需要制造非法的类型对齐访问。

多触及一个 sector 表示本条请求的几何工作增加，不意味着 DRAM 必须同比例多读、时间一定增加 25%。邻接 warp 可能复用多取到的区间，缓存可能早有数据，其他路径也可能限制吞吐。把 sector 计数与时间并列测量才能分辨影响停留在哪一层。

具体例子

A=0 时连续读 [0,127] 是 4 个 sector；从 4 开始连续读 [4,131] 是 5 个，覆盖容量 160 B、独特有效数据仍为 128 B。

先预测offset 按 32 B 周期扫描时，几何计数会出现规律性变化。

容易混淆

用非法未对齐的 float4 指针强行测试，或把 5/4 直接当作 kernel 耗时倍率。

检验理解偏移 32 B 后仍读取 128 B 连续数据，sector 数是多少？

仍是 4，只是覆盖的 sector 编号整体移动。

04

H09.04

stride 对请求数量的影响

#

stride 增大如何降低一次请求中的有效密度？

最小状态
元素 stride、lane 地址集合、去重后的 sector 编号。
变化规则
stride 只改变地址；请求粒度与去重规则不变。

在每 lane 读 4 B 的模型中，地址为 A+4×s×lane，s 是以元素为单位的 stride。s=1 时邻居共享 sector；s 增大后，参与地址之间留下未使用空洞，一条请求可能覆盖更多 sector，而有效数据仍是 32×4 B。

计数应该对实际 sector 编号去重，不能无限使用“sector 数等于 4s”这一局部关系。比如 s 足够大时，每 lane 各落不同 sector，最多触及 32 个 sector；继续增大 stride 还可能改变缓存和 TLB 行为，但不会让这条自然对齐 4-byte load 超过每 lane 一个 sector。

具体例子

A=0：s=1 得 4 个 sector，s=2 得 8 个，s=8 得 32 个；s=16 仍是 32 个，但地址跨度更大。

先预测有效字节不变而 sector 数增多时，几何有效密度会下降。

容易混淆

用 stride 乘一个固定带宽损失因子，忽略上限、缓存与页跨度。

检验理解s 从 8 增至 16，sector 数不变，耗时是否必定不变？

不必；工作集跨度、缓存命中和翻译行为仍可能变化。

H09.05

gather 的地址分布

#

gather 一定是不合并访问吗？

最小状态
索引值、独特元素、sector 集合、地址跨度。
变化规则
把间接地址算出后，仍按普通区间覆盖规则合并。

gather 只说明每个 lane 的地址来自索引，并不说明这些索引分散到哪里。若索引只是把一个连续小区域重新排列，地址集合仍紧凑；若索引遍布大工作集，则可能让每个 lane 触及不同 sector。判断需要看分布而非操作名称。

对一次 gather，可以同时记录独特元素数、sector 数和地址跨度。它们分别帮助区分重复利用、局部合并与潜在缓存/TLB 压力。同样 32 次逻辑读取，重复读少数位置与读 32 个遥远位置产生的工作完全不同，也不应使用相同的理论有效字节定义。

具体例子

index=[31,30,…,0]，从同一个对齐的 32-float 区间反向读取，仍覆盖 4 个 sector；不因 lane 顺序反转变成 32 个。

先预测重排计算顺序让索引聚类可能改善局部性，但必须计入重排成本。

容易混淆

把索引访问统一判为随机，或只用平均 stride 描述带聚类的分布。

检验理解两组 gather 都触及 8 个 sector，就能断言时间一致吗？

不能；sector 是否命中、地址生成开销和依赖链都可能不同。

H09.06

向量化 load 改变了什么

#

向量化 load 减少的是字节数还是指令工作？

最小状态
相同数据量、每 lane 向量宽度、对齐、最终指令数。
变化规则
合并相邻元素后重新计算每条请求的理想 sector 数，再比较总工作量。

向量化通常让一个线程一次取得更多相邻元素。在总数据相同且布局正确时，必要的独特字节并不会减少；收益可能来自更少的访存指令、地址计算或队列请求，以及更好的请求组织。必须查看编译器是否真的生成对应宽度的机器指令。

向量类型有对齐要求，边界还需合法处理。对于同样 512 B 数据，32 lane 各读 16 B 的一条向量 load 与多条标量 load，sector/request 不能拿同一个理想值比较；向量指令覆盖 16 个 sector 本身可以完全高效。增加宽度也可能延长寄存器活跃期。

具体例子

32 lane 各连续读取 float4，且 A+16×lane 对齐，总计 512 B、16 个 sector。这里比值 16 并不意味着比标量基线 4 差四倍。

先预测若瓶颈在访存指令供给，向量化可能在 DRAM 流量不变时获益。

容易混淆

只看到 sector/request 增大就否定向量化，或假设 float4 必定生成一条宽 load。

检验理解向量化后 DRAM bytes 不变，但时间减少，合理吗？

合理；减少的可能是指令/请求/地址生成成本而非必要数据量。

H09.07

部分 lane 参与时的请求效率

#

只有少量 lane 参与时，怎样计算有效密度？

最小状态
本条指令实际参与 mask、每 lane 地址与宽度。
变化规则
剔除未参与 lane 的区间，再求 sector 并集。

访问掩码决定哪些线程真正提交地址。若只有连续 8 个 lane 各读一个 float，并落在同一个 sector，1 个 sector 就足够；若相同 8 个 lane 的地址散在 8 个 sector，传输粒度工作会大得多。参与线程少本身不等于访问低效，布局仍是关键。

比较请求效率时，分母应匹配 active 或 predicated-on 的访问集合。不能因为完整 warp 的理想值是 4，就把只需一个 sector 的请求误判成异常；也不能把 32 个逻辑线程当成都读了数据。边界 tile 中常见这种情况，应区分必要尾部与可避免布局浪费。

具体例子

lane 0…7 读 A+4×lane，A 对齐时有效 32 B、1 个 sector；若读 A+32×lane，仍只有 32 B 有效数据，却触及 8 个 sector。

先预测相同 active lane 数，集中布局通常比分散布局需要更少 sector。

容易混淆

用 blockDim 或 warp 宽度代替该条指令实际参与线程数。

检验理解一个 lane 读 4 B，最少覆盖一个 32 B sector，意味着程序必定差吗？

不意味；可能是必需的边界或标量工作，要看频率和总成本。

H09.08

useful bytes 与实际传输字节

#

useful bytes 为什么不能直接当作 DRAM bytes？

最小状态
逻辑消费字节、独特字节、各层计数与时间窗口。
变化规则
在每个层级分别统计，再用一致单位比较，不能跨层直接替换。

“有用字节”必须先定义。可按独特有效数据计算，也可按各线程逻辑消费量累计；重复读同一值时二者不同。访存系统按缓存及传输粒度工作，可能过取、复用或命中，因此逻辑消费量、L1 请求字节和 DRAM 实际字节不会普遍相等。

用独特数据作为几何效率分子时，分母可选本条请求覆盖的 sector 容量；这只评价地址分布，不是端到端 HBM 利用率。报告带宽必须同时写清 byte 来源、时间窗口、读写是否相加以及缓存条件。否则“超过峰值”可能仅意味着重复数据被缓存服务。

具体例子

32 lane 都读同一个 4 B 值：逻辑消费累计 128 B，独特数据仅 4 B，覆盖一个 32 B sector；不能把它宣称为 400% DRAM 传输效率。

先预测改善时间局部性可能降低 DRAM 流量，即使单条指令的合并几何完全不变。

容易混淆

混用 requested bytes 和硬件实际读字节，或把缓存带宽报告成 HBM 带宽。

检验理解L1 sector/request 不变而 DRAM bytes 降低，可能发生了什么？

更多请求在缓存层得到服务，或下层流量被复用；需保持同一工作量与测量条件。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum / l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum

L1TEX global load 的平均 sector/request。32 个 lane 各读对齐连续 4 B 的基线是 4。

这是两个 sum 的比值；64-bit、128-bit、部分 lane 或重复地址应重算基线，不等于 DRAM 放大倍数。

[3]

dram__bytes_read.sum

设备内存读字节，用来检查源级 sector 增长是否真正传到 DRAM。

缓存命中、其他设备活动和 replay 会影响结果；不能用 L1 sector 数直接替代它。

[4]

smsp__pcsamp_warps_issue_stalled_lg_throttle

采样 warp 因 local/global 指令队列压力等待的观察线索。

队列压力不是合并效率的直接测量；先看实际指令数、sector/request 和访存路径。

[2]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

实验设计：只扫描 offset 与 stride（尚未执行）

只改变

对相同数量的输出，分别扫描自然对齐的 4-byte 起点偏移和相邻 lane 间 stride；防止越界并保留输出校验。

预计现象

按 sector 集合预测 L1TEX sector/request；缓存复用可能减弱 DRAM 流量和耗时的同比例变化。

记录什么

记录最终 load 宽度、active lane 数、L1TEX requests/sectors、L2 与 DRAM bytes 和总时间。执行前查询目标 GPU 指标支持。

排除干扰

邻接 warp 重用同一 sector、预取/缓存、编译器向量化、边界线程和 profiler replay 都可能改变结果；不能用理论几何直接替代实测带宽。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。

来源与边界

官方文档约束编程语义；论文记录特定设备上的观察；模拟器源码定义模型行为。三种证据不能相互替代。

  2. 官方文档Nsight Compute：L1/TEX Cache Memory Table ↗

    官方计数口径；区分 request、sector、wavefront 和命中，核对于 2026-11-07。

    官方指标名来源；比值基线需结合访问宽度和参与线程数，不能把 4 当成全部指令的统一阈值。核对于 2026-11-07。

  4. 官方文档CUPTI：PerfWorks Metrics Mapping ↗

    官方指标映射；用于核对 DRAM bytes、global load requests/sectors 等具体名称，实际可用性以目标设备查询为准。核对于 2026-11-07。
