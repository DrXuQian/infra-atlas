H04 / ONE ISSUE AT A TIME

Warp scheduler

这一周期，谁有资格发射，谁最终被选中？

将驻留、就绪、仲裁、发射与完成拆开；再用LRR/GTO、跨warp并行和warp内ILP解释不同的时间线。

适用范围

静态归属以Volta官方说明为参照；LRR/GTO来自已固定commit的GPGPU-Sim模型。所有演示时延均为教学参数，不代表NVIDIA通用调度算法或实测周期。

先备知识：H02：warp和scheduler归属 · H03：resident warp的来源 · H01：latency、吞吐及计数器口径

CHANGE ONE THING

逐周期观察候选、发射与完成

一个 scheduler 固定管理 1 或 4 个 warp；每周期最多发射一条、按 warp 内程序顺序；LD 延迟 6、FMA 延迟 3、ADD 延迟 1，所有执行单元可流水接受。周期开始先完成旧操作，再判就绪、仲裁、发射。c 发射、L 延迟的结果在 c+L 可用。LRR 初始指针为 W0，仅成功发射后移动；GTO 优先上次发射的 warp，否则选择最老的 eligible warp，所有 warp 都在 c0 入场，同龄按 W0、W1、W2、W3 排序。其他未列出的输入初始就绪。LRR/GTO 是教学策略，省略取指、RF/队列反压及内存层次。

01

H04.01

scheduler 管理哪些 warp

#

scheduler 的候选池包含整个 SM 的 warp 吗？

最小状态
固定scheduler ID、其所属warp集合与局部执行入口。
变化规则
只对所属warp进行有效性、依赖、资源检查和仲裁。

先确定所有权，再讨论选择。Volta官方说明每个scheduler管理静态的一组warp，发射到其对应算术资源。一个scheduler空闲，不意味着它能把另一个scheduler的ready warp直接拿来使用。只看全SM总数会忽略局部供给不足。

模拟器也需显式建模归属：所引shader.cc按warp slot编号对scheduler数取模分配。这个取模规则是模型代码的定义，不等于所有芯片、所有运行阶段都使用相同可见映射。比较策略时应保持归属不变，否则测到的是调度与迁移机制的混合变化。

具体例子

教学模型S0持有W0/W2、S1持有W1/W3。若W0/W2都等数据，S0保持空闲；即使W1/W3就绪，也只在S1内部竞争。

先预测ready warp集中在同一所有权分区时，其他scheduler可能空闲。

容易混淆

为了让动画看起来更满，允许scheduler随意偷取别的分区warp。

检验理解全SM有两个ready warp，是否一定可以同时发两条？

不一定。它们可能属于同一scheduler，且相应发射或执行资源也有限。

H04.02

resident 到 eligible 的条件

#

resident warp 到底还缺什么，才能成为 eligible？

最小状态
resident状态、队首指令、依赖、同步状态和目标入口。
变化规则
所有必要条件满足才进入eligible集合；任一条件失败都不能发射该指令。

resident只说明warp已有片上状态和资源。要成为可发射候选，至少需要下一条指令已准备、输入依赖满足、同步条件允许，并且目标执行路径可接纳。单独增加resident warp，若它们一起等同一数据或barrier，eligible仍可能很少。

所引模拟器把这些检查分散在ibuffer、waiting、scoreboard和执行入口容量中；NCU提供的是硬件观测术语，不应把某一个模拟器布尔变量直接当作NCU的精确实现。定位时先区分取指不足、依赖等待、同步等待和资源throttle，再决定增加并行性是否有效。

具体例子

W0驻留且下一条是使用load结果的FMA，load还未返回，所以不eligible。W1同样驻留但输入齐全、入口可用，可以参与仲裁。

先预测只增加等待同一条件的warp，eligible数量可能不变。

容易混淆

把active/resident画成ready，忽略在途依赖和barrier。

检验理解所有resident warp都已分到寄存器，为什么可能零发射？

寄存器容量只解决存放问题，寄存器中的待生产值、取指或执行资源仍可能未就绪。

03

H04.03

eligible 到 selected 的选择

#

eligible 的 warp 为什么还可能没有发射？

最小状态
候选集合、仲裁顺序和每周期发射容量。
变化规则
从eligible集合选择不超过容量的warp，其余保留下一轮候选资格。

eligible表示具备发射条件，不等于已经占有这一周期的发射机会。多个候选需要仲裁，选择受到scheduler容量、policy、指令类型和其他内部约束影响。selected指本次被选中；issued还需明确发射边界，而不是把候选数量直接当成已完成工作。

专业分析应把“没有合格候选”和“候选很多但每次只能服务有限个”分开。前者可能需要更多TLP/ILP或缩短依赖；后者在发射持续繁忙时并非需要修复的空泡。真实NVIDIA完整policy未公开，教学可使用LRR/GTO比较机制，但不能据此宣称硬件严格照办。

具体例子

教学scheduler每周期发射1条，W0/W1/W2都eligible；本次选W1，另外两个是not_selected，而非发生新的数据依赖。

先预测eligible继续增加会增加落选者，未必增加同一周期发射数量。

容易混淆

把所有未被发射的warp都归为同一种stall原因。

检验理解有3个eligible但只发1条，issue-active会是多少？

在每周期最多1次发射的教学模型中，该周期issue-active是100%；两个落选不代表两周期损失。

H04.04

issue 与完成的区别

#

为什么发射了 load，却还不能立刻使用结果？

最小状态
指令发射时刻、到期时刻、目标值有效标记和消费者依赖。
变化规则
只有完成阶段才更新值和释放相应依赖；issue仅登记在途工作。

issue是把指令交给后续执行路径的事件，completion是操作完成并满足消费条件的事件。两者之间可能经过操作数收集、流水阶段、请求队列、缓存或内存返回。已经issued的指令仍可以在途，依赖它的后续指令必须等待。

教学时要规定时间相位：先完成到期操作，再更新依赖，之后分类、仲裁和发射。若定义在周期c发射、延迟L，则结果在c+L开头可用。对真实硬件，发射入口与执行管线接受还可能由中间队列解耦；这里只在明确简化时把它们合并。

具体例子

load在周期0发射，教学延迟6，则消费者最早在周期6的完成阶段之后变就绪；周期1到5都不能把数据当作已经返回。

先预测固定指令流下，把依赖结果提早标为ready会产生不合法的虚假加速。

容易混淆

一点击“下一周期”就同时发射并完成所有指令，导致依赖在同周期被提前释放。

检验理解执行管线里还有指令时，能不能接收下一条独立指令？

可能。只要入口和资源允许，in-flight不等于不能继续接收。

H04.05

LRR 策略

#

LRR 是每个 warp 固定轮流占一个周期吗？

最小状态
固定环形warp顺序、上次成功发射位置与本周期候选。
变化规则
从上一成功发射者之后扫描，选择第一个满足发射条件的warp。

在所引GPGPU-Sim实现中，Loose Round Robin从上次成功发射warp之后开始建立循环优先序。scheduler随后按这个顺序检查候选，跳过已退出、等待或不具备资源的warp。它不是严格要求每个warp无论ready与否都占一个空白时间片。

因此实际发射序列还取决于依赖、队列和指令供给。比较LRR时应记录上次成功发射者以及候选集合，并明确没有任何warp发射时指针是否改变。这里依据固定commit的模型规则解释，真实NVIDIAscheduler不被此策略名称所约束。

具体例子

上次发射W0，下轮检查顺序W1→W2→W0。若W1等数据、W2就绪，则选W2；下次从W0开始，而不是给W1强留一个空周期。

先预测暂时阻塞的warp会被跳过，避免无谓空槽。

容易混淆

把LRR演示成不看ready状态的机械时间片轮转。

检验理解LRR总能让每个warp获得完全相同的发射次数吗？

不能。不同warp就绪时间、退出时刻和指令需求都可能不同。

H04.06

GTO 策略

#

GTO 的“oldest”到底按什么排序？

最小状态
上次发射warp、动态年龄、候选集合与退出状态。
变化规则
先尝试greedy对象；失败后按模型规定的年龄顺序寻找可发射者。

Greedy Then Oldest先尝试继续服务上次发射的warp；它不能发射时，再偏向更老的候选。所引GPGPU-Sim用dynamic warp ID表达动态进入次序，已退出或处于waiting状态的warp被降低优先级，最终仍需通过scheduler中的依赖和资源检查。

“年龄”不是静态threadIdx、blockIdx或某条指令等待的时间。模型中新的warp复用一个物理slot时，slot编号与动态年龄不同。GTO可能促进某些局部性，也可能改变跨warp进展分布；没有哪种policy对所有访存和同步模式都必然更优。

具体例子

W2是上次发射者，只要其下一条独立指令仍可发射，GTO可继续选W2；W2阻塞后，再从其余候选中检查dynamic ID更老者。

先预测同一依赖图用GTO与LRR可产生不同交错顺序，但都必须保持结果正确。

容易混淆

把GTO理解成永远选静态编号最小的warp，或把它称为所有NVIDIA GPU默认算法。

检验理解如果一个老warp不eligible，GTO应强行发射它吗？

不应。policy改变优先顺序，不绕过依赖与资源约束。

H04.07

跨 warp 隐藏延迟

#

更多 warp 是怎样隐藏延迟的，而不是缩短延迟的？

最小状态
同一scheduler的多个独立warp、各自依赖与发射入口。
变化规则
本warp不可发射时，其他eligible warp可占用该周期。

某个warp等待结果时，scheduler可以发射另一个所属warp的就绪指令。这样把空闲发射周期填入有用工作，改善整体吞吐；原先那个操作的结果延迟并没有因此缩短。TLP的收益来自在等待间隙找到独立工作。

需要的warp数量取决于依赖延迟、每warp可暴露的独立指令、发射宽度与资源归属。简单的“延迟乘吞吐”只给出在特定稳态假设下所需并行量，不能替代测量。若所有warp同步等待或某条资源已经饱和，继续增加驻留warp会失去收益，甚至增加缓存竞争。

具体例子

教学模型每warp只有一条依赖链、latency=3、每周期发1条；3个总能轮流ready的warp可覆盖空隙，单warp则每3周期才推进一次。

先预测只要新增warp提供不同的就绪时机，空闲发射周期可能减少。

容易混淆

说增加occupancy能让一条HBM load的物理延迟变小。

检验理解更多warp后not_selected增多、耗时下降，是否相互矛盾？

不矛盾。候选供给更充足，同时带来更多落选者和更少无候选空泡。

H04.08

warp 内 ILP

#

warp 内 ILP 能否让 scheduler 越过阻塞指令找后面的工作？

最小状态
按程序顺序排列的指令、每个目标寄存器及活跃区间。
变化规则
只检查下一条允许发射的指令；独立工作必须已被合法安排到队首。

ILP要求在实际指令顺序中暴露独立操作，通常由编译器或开发者安排多个累加器、提前地址计算和加载。GPU的顺序发射模型不会任意跳过一个依赖未满足的队首指令，再从后面动态挑一条独立指令。

因此源码中存在独立性还不够：要检查最终SASS把独立操作放在何处，以及寄存器生命周期是否明显增加。更多ILP可减少需要的resident warp数量，但若寄存器压力使occupancy下降或产生spill，最终效果可能反转。TLP与ILP应分别改变，避免无法归因。

具体例子

A写R0；B读R0；C与A无关。顺序A,B,C时B会挡住C；改为语义合法的A,C,B后，C才可能填进等待间隙。

先预测在不spill且资源未饱和时，适度增加独立链可能提高eligible供给。

容易混淆

把ILP画成CPU式动态乱序窗口，允许跳过任何未ready的指令。

检验理解把独立累加器从2个增至8个需要检查哪个副作用？

检查寄存器数量、spill与驻留变化，不能只看依赖链缩短。

H04.09

多发射的资源约束

#

两条独立指令为什么不一定能在同一周期发射？

最小状态
可用发射槽、指令配对规则、输入依赖与各执行入口。
变化规则
每次接受一条后更新资源，再检查下一条是否仍满足所有约束。

数据独立只是必要条件之一。多发射还可能要求多个发射槽、不同执行路径、入口缓冲容量、操作数带宽以及架构允许的指令配对。不同代际、不同指令类别的发射规则不能用“有两个执行单元”简单推导。

所引模拟器用每warp最大issue数和是否要求不同execution unit等配置控制这类行为，说明policy和资源限制是分开的。硬件分析应先确认官方代际说明或经过验证的微基准，再判断是入口发射限制还是下游执行限制；不要把模型参数当作真实硬件保证。

具体例子

两条FMA即使读写不同寄存器，若只共享一个每周期接收1条的入口，本周期仍只能发1条；增加第二种管线也不会自动增加发射槽。

先预测下游资源增加但发射槽不变时，峰值发射次数可能不变。

容易混淆

认为两条指令没有RAW，就一定支持dual issue。

检验理解同时存在FP32与INT32资源，能推出任意一对指令同时发射吗？

不能。还需要发射、操作数、配对和目标资源条件都满足。

H04.10

not_selected 应如何解释

#

not_selected 高，是不是说明 scheduler 在浪费机会？

最小状态
eligible集合、被选中warp、采样窗口和issue-active。
变化规则
每次选择后，其余当时eligible的warp保持就绪但被记为未选中状态。

NCU把not_selected定义为已经eligible、但这一周期另一个warp被选中的状态。它表明存在候选竞争，不能直接当作依赖等待，也不能把它的样本比例解读为同样比例的全局空闲周期。一个持续发射的scheduler完全可能产生很多not_selected样本。

判断好坏要同时看issue-active、eligible数量、执行管线利用率和kernel时间。高not_selected可能意味着并行量已经足够，可以尝试减少warp换取更少寄存器压力或更好缓存局部性；也可能只是正常仲裁。优化目标是更快完成有用工作，不是把每种带stalled字样的计数都降为零。

具体例子

每周期4个warp就绪、只选1个，其他3个落选；连续100周期都有发射时，scheduler没有因此空闲300周期。

先预测增加无依赖候选可能提高not_selected，同时保持或改善发射活跃度。

容易混淆

把not_selected与long_scoreboard一并相加，声称总共损失了这些执行时间。

检验理解not_selected降低但时间变慢，可能发生了什么？

候选不足让scheduler出现无eligible空泡，减少竞争并不等于提高吞吐。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

smsp__warps_active.avg.per_cycle_active

每个SMSP在活动周期内平均resident warp数，是候选供给的上游。

高值不代表这些warp可发射；avg也可能隐藏子分区不均。

[4]

smsp__warps_eligible.avg.per_cycle_active

活动周期内平均eligible warp数；依赖被隐藏后，在相同工作量下可能增加。

需与issue-active和管线负载联合看，不存在跨架构通用最佳阈值。

[4]

smsp__issue_active.avg.per_cycle_active

观测scheduler发射活跃程度，区分无候选空泡与正常竞争。

它不是有效FLOPS比例；完整支持以目标芯片 --query-metrics 为准。

[4]

smsp__pcsamp_warps_issue_stalled_not_selected

PC采样中eligible但落选的warp状态；增加就绪供给可能使样本上升。

这是采样状态而非依赖stall，不可直接换算成全GPU损失周期。

[2]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。
