H14 / ADDRESS TRANSLATION

地址翻译与虚拟内存

地址有效、数据已分配，为什么访问仍可能等很久？

分开虚拟映射、TLB 缓存、页故障和数据位置。统一地址空间解决可寻址性，不消除远端访问或迁移成本。

适用范围

CUDA 虚拟内存及 Unified Memory 契约；TLB 层次和容量以具体微基准为观察。示例地址、页大小与条目数量是教学假设，不是默认 NVIDIA 配置。

01

H14.01

虚拟地址到物理地址的路径

#

虚拟地址怎样找到真实存储位置？

最小状态
虚拟页号、页内偏移、映射和权限。
变化规则
取得有效映射后组合物理页框与偏移，再走目标存储路径。

地址翻译把虚拟页映射为物理页框，再保留页内偏移得到物理位置。映射还关联访问权限和所处分配，虚拟连续不代表物理连续，也不代表在本 GPU 显存中。地址统一与数据本地化是两个不同问题。

CUDA VMM 将保留虚拟范围、创建物理分配、映射和设置访问权限分开。仅成功保留地址空间不表示地址已可读写。实际缓存与翻译可能重叠，教学中的顺序图只表达逻辑依赖，不宣称所有芯片在 L1 查询之前先查完整 TLB。

具体例子

教学页大小4KiB，VA 0x1234 的页号1映射到物理页9，则页内偏移0x234不变，得到PA 0x9234。

先预测同样虚拟布局在不同物理放置下可以有不同性能。

容易混淆

把连续 CUDA 指针范围当作物理 bank 连续，或把 reserve 成功当作可安全解引用。

检验理解两个连续虚拟页必须放在连续物理页框吗？

不必，页表可以把它们映射到不相邻位置。

02

H14.02

TLB 命中与失效

#

TLB miss 是否意味着要把页面搬进显存？

最小状态
TLB 内容、页表项有效性、数据当前位置。
变化规则
TLB miss 先寻找有效映射；只有普通翻译无法完成才进入相应故障处理。

TLB 缓存最近使用的地址翻译。TLB hit 复用映射；miss 需要从更低层翻译缓存或页表查找。若页表项已经有效且数据就在可访问位置，查到映射后可继续读取，完全不需要用户数据迁移。

Page fault 是翻译、权限或驻留条件无法按普通路径满足时的另一类事件，可能需要驱动介入。不要把数据 cache miss、TLB miss 和 page fault 合成一种 miss。论文可用控制缓存与页覆盖的微基准分离它们，但真机内部层次仍需谨慎归因。

具体例子

已在 GPU 的数组第一次被某个翻译缓存覆盖时可能出现 TLB miss；随后缓存映射后更快。这个过程并未从 CPU 再复制整页数据。

先预测预热翻译可减少部分等待，即使数据搬运字节没有变化。

容易混淆

把所有 long scoreboard 或首次访问慢都解释成 Unified Memory page fault。

检验理解数据 L2 hit 能否同时遭遇翻译等待？

可以，数据驻留与地址翻译缓存是不同状态，具体重叠依架构。

03

H14.03

TLB reach 与工作集

#

TLB reach 为什么与工作集有关？

最小状态
TLB 条目与页大小、活跃页集合、访问顺序。
变化规则
新页映射占用或替换条目，超出覆盖后的重用可能 miss。

简化情况下，某级 TLB 的覆盖范围可用条目数乘每项覆盖的虚拟页大小估算。若活跃访问涉及的页远多于可缓存映射数，翻译会频繁替换；即使每页只读几个字节，页覆盖压力仍可能很大。

真实 TLB 可支持多页大小、多层和组相联结构，覆盖不是单一常数。依赖链扫描中的延迟台阶可能来自翻译，也可能混有数据缓存或物理放置变化；应固定有效数据量并改变页分布，结合文献方法构造对照。

具体例子

教学 TLB 有128项、每项4KiB，名义 reach 为512KiB。访问1024页各4B，只读4KiB数据，却涉及4MiB地址覆盖。

先预测在数据缓存行为接近时，增加访问页数可能增加延迟。

容易混淆

以实际读取的数据字节很少，推断不会有翻译瓶颈。

检验理解每页读1个字节，TLB 占用也按1字节计算吗？

不是，TLB 跟踪页映射，关键是涉及多少不同页。

H14.04

跨页访问的影响

#

跨页访问增加的究竟是什么？

最小状态
lane 地址集合、所跨页数、各页翻译状态。
变化规则
按页寻找映射，再由访存系统处理对应数据请求。

一条 warp 访存涉及多个虚拟页时，需要相应页的有效映射。跨页不是必然故障，只是可能需要更多翻译；数据 coalescing 还按访问地址与传输单位处理，是另一层机制。同样 sector 数的两组地址也可能有不同页分布。

一个自然对齐且不超过页内边界的标量通常只需一页；分散 gather、跨页 tile 或连续大范围访问会涉及更多页。为了孤立翻译成本，应保持读取字节、sector 效率及并发尽可能相同，避免把跨 sector 的额外流量误认成跨页代价。

具体例子

教学中32个lane各读4B，全部落在同一4KiB页与各落在32个不同页，逻辑字节同为128B，但翻译覆盖需求不同。

先预测TLB 未预热时，更多独立页可能增加翻译服务需求。

容易混淆

跨页就等于未对齐，或跨页就必然需要 CPU page-fault 服务。

检验理解32页都已在 TLB 中时，仍会产生32次 page fault 吗？

不会。有效翻译可复用，page fault 不是按跨页数量自动发生。

H14.05

页大小与翻译压力

#

更大的页为什么有收益，也有代价？

最小状态
可支持的虚拟页大小、TLB 覆盖、迁移粒度和访问稀疏度。
变化规则
换页大小改变映射覆盖和管理粒度，未改变算法真正需要的字节。

更大虚拟页让同一 TLB 条目覆盖更多地址，可降低大范围随机访问的翻译压力，也减少某些页表管理工作；代价可能是碎片、较粗的保护/映射粒度，以及在按页迁移的系统中一次移动更多无用数据。

支持哪些页大小取决于 GPU、操作系统、分配机制和映射方式。CUDA VMM 的 allocation granularity 描述分配与映射的约束，不可直接当成每级 TLB 实际页大小。调优应针对可控的虚拟映射配置，不硬编码未公开的物理页假设。

具体例子

假设相同128项 TLB，4KiB页覆盖512KiB，2MiB页覆盖256MiB；但只改动一个4KiB热点时，大页迁移可能搬运远超真正需要的数据。

先预测大范围稳态随机访问可受益，稀疏首次触碰可能增加搬运代价。

容易混淆

把大页视为没有任何代价的通用加速开关。

检验理解页更大为何可能使首次访问尾延迟更差？

某些系统需要迁移或管理更大的粒度，单次开销可能增加。

H14.06

page fault 与数据迁移

#

page fault 后一定发生同一种迁移吗？

最小状态
内存类型、有效映射、数据位置、系统 UM 能力。
变化规则
普通访问不能满足时进入系统处理，条件恢复后重试。

故障处理可能需要建立或更新映射、调整权限、等待相关访问或迁移数据。具体路径由内存类型、位置、系统能力与驱动决定。软件一致性 Unified Memory 常借助页面管理；硬件一致性系统可能直接远端访问并在更细粒度保持一致性。

因此必须记录 concurrentManagedAccess、pageableMemoryAccess 和 host-page-table 使用等能力，并区分 Linux HMM/ATS 与受限模式。Nsight Systems 的 fault 和迁移事件可说明某次运行发生了什么，但单凭 fault 数不能算出全部搬运字节或耗时。

具体例子

在支持按需迁移的系统上，CPU先触碰 managed数组，GPU首次读可能触发迁移；预取后再读可减少这种首次停顿。另一种系统则可能直接读远端存储。

先预测冷访问与预取后访问可能差很多，稳态结果不能代表首次触碰。

容易混淆

把某台 PCIe Linux GPU 的 UM 行为写成 Windows、WSL、Tegra 和 Grace 系统的统一规则。

检验理解一个 page fault 与一个固定大小 memcpy 一一对应吗？

不保证，驱动可能合并处理、预取、重映射或采用远端访问。

H14.07

Unified Memory 中数据位置的影响

#

同一个 managed 指针为什么时快时慢？

最小状态
数据位置、访问者、重用次数、迁移与计算时间线。
变化规则
访问模式影响放置，放置决定后续数据走本地或远端路径。

Unified Memory 让指针在适用的处理器间可用，不使所有物理位置的延迟与带宽相同。数据在本地显存、CPU内存或其他GPU时，实际路径不同；第一次访问还可能伴随迁移，之后重复访问则利用本地缓存或本地内存。

放置策略要围绕谁访问、访问多少次、是否与 CPU 交替写以及是否超量分配来选择。prefetch 和 advise 提供指导，不是免费的预加载。总收益要包括搬运、等待与计算重叠，不能只截取已迁移后最快的一段 kernel。

具体例子

一次CPU初始化后GPU重复读取100轮，可摊薄一次迁移；若每轮CPU和GPU都改同一页，软件一致性平台可能出现往返迁移，成本完全不同。

先预测反复GPU使用可摊薄迁移；频繁跨处理器写共享页可能变慢。

容易混淆

UVA/UM 等同共享物理显存，或把预取后的 kernel 加速当成端到端同等加速。

检验理解预取时间从 kernel 里消失后，总时间一定下降吗？

不一定；它可能只是移动了开销，只有重叠或减少重复搬运才带来净收益。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

MemoryWorkloadAnalysis_Tables：Sector Misses to System / Peer / Device

区分 L2 miss 后请求的数据位置，检查读取是否走系统内存或 peer 路径。

位置流量不是 TLB miss 数，也不说明某次传输必然由 UM 迁移引起。先确认 section 支持。

[6]

SourceCounters / WarpStateStats：内存依赖等待

在页数或放置对照中观察消费者等待变化，结合时间线提出翻译或远端访问假设。

long scoreboard 不是 TLB miss 的唯一证据，不能用它反推页表层数或 TLB 条目数。

[6]

Nsight Systems：UM page-fault 与迁移事件（NCU 的补充）

用时间线区分首次触碰、迁移和稳态 kernel 服务，检查预取是否把搬运移到关键路径外。

按 GPU/OS/toolkit 查询是否可采集；fault tracing 会带来额外开销，时间需与无 profiler 运行对照。

[5]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

页覆盖与数据位置分离（实验设计，尚未执行）

只改变

先固定 GPU 驻留数据，在相同有效读取量下改变访问页数；另独立比较 managed 内存的冷访问、预取后访问和重复访问。

预计现象

页数增加可能暴露翻译压力；预取有机会减少首次触碰的迁移，但不能保证所有平台相同。

记录什么

无 profiler 的 CUDA event/端到端时间；NCU cache/traffic 对照；支持时用 Nsight Systems UM fault 与迁移时间线。

排除干扰

跨页 stride 也改变 cache 冲突、HBM 分布和预取行为；驱动、OS、ATS/HMM、超量分配和测量 replay 都需记录。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
