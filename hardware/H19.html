01

H19.01

TMA tensor map 与地址生成

#

TMA tensor map 帮线程省掉了哪些工作？

最小状态
tensor map、tile坐标、shared目标和合法布局参数。
变化规则
发起坐标式搬运，TMA按描述生成对应地址与数据传输。

tensor map描述global张量的基地址、维度、步幅、类型和tile布局等信息。线程发出坐标与目标shared位置后，TMA按描述计算并搬运一块数据，使大量逐元素地址算术与搬运发射不必由每个lane分别完成。

它是有约束的张量传输机制，不是任意指针gather的万能加速器。descriptor的步幅、对齐、swizzle与目的布局必须相容；构建或更新descriptor本身也有成本和可见性要求，需结合tile复用与kernel长度判断收益。

具体例子

同一个二维矩阵的多个tile共用一个tensor map，每次只给出不同起始坐标，而不是为每个元素重新算完整地址。

先预测若原本地址计算和搬运发射开销高，TMA可能降低这些开销；小tile未必划算。

容易混淆

把TMA描述符当成数据本身，或认为更换任意stride后原descriptor仍然有效。

检验理解输入张量leading dimension改变时，为什么要检查tensor map？

它编码了地址计算规则；旧stride可能把正确坐标映射到错误地址。

H19.02

TMA 完成与消费者等待

#

TMA load 的完成如何传递给消费者？

最小状态
tile字节、barrier phase、arrival与tx-count。
变化规则
搬运完成递减事务计数，完整phase完成后消费者获得输入。

global→shared的TMA tensor load可采用mbarrier complete_tx字节完成机制。producer在正确初始化和phase中登记预期事务量并发起搬运；只有到达计数和事务计数都完成，消费者对该phase的等待才能成功。

不要把TMA load的barrier协议与shared→global的bulk-group完成机制混为一谈。消费者还必须保护buffer的代次和复用时机；它得到“输入已到齐”的许可后，后续异步MMA仍有自己独立的完成条件。

具体例子

tile有8192字节，barrier按这轮协议期待8192字节。仅线程arrive完成时不能开算，TMA写完并完成对应事务后才可交付。

先预测错误的期望字节或phase会表现为等待卡住或读错轮次，而不是普通性能抖动。

容易混淆

只等待producer线程执行到某一行，就认为TMA已经把tile写完。

检验理解TMA输入ready后，MMA输出是否同时ready？

不是。输入搬运完成只允许启动计算，计算还有另一条完成链。

H19.03

TMA multicast

#

TMA multicast 是给多个CTA共享一个指针吗？

最小状态
cluster参与mask、各CTA shared目的buffer和完成状态。
变化规则
一次tile传输向选定接收者复制数据，接收者按协议等待后消费。

TMA multicast可把一次请求的输入tile送到同一cluster内被mask选择的多个CTA各自的shared目的位置。它面向数据复制和复用，接收CTA仍拥有自己的shared空间与完成协议，并不是把它们变成一个普通共享指针。

收益来自减少重复的外部供数或发起开销，但具体流量下降取决于缓存状态和硬件路径。接收方的buffer位置、barrier设置、参与mask和存活条件必须满足指令要求；不能推广成任意SM之间的跨cluster广播。

具体例子

一组CTA计算不同N切片但复用同一A tile，可研究把A送往多个接收shared buffer，再各自消费不同B。

先预测复用程度高时可能减少重复供数，但新增协作和驻留限制也可能抵消收益。

容易混淆

把multicast的接收数量直接乘成固定带宽加速倍数。

检验理解发送CTA完成后，接收CTA能否忽略自己的同步协议直接读？

不能，必须按该multicast指令的完成与可见性规则等待正确buffer。

H19.04

WGMMA 的发起、提交和等待

#

WGMMA 的 fence、commit、wait 分别解决什么？

最小状态
warpgroup、寄存器/共享操作数、pending MMA groups。
变化规则
建立顺序→一致发起→提交group→等待指定旧组完成→消费。

Hopper sm_90a的WGMMA由warpgroup协作发起。wgmma.fence建立规定的寄存器访问顺序；涉及generic shared写时还需相应async proxy顺序。mma_async发起计算，commit_group把已发起操作划入完成跟踪组。

wait_group按允许的pending组数等待旧组完成，之后才可按规范消费结果或复用仍被读取的输入。wgmma.fence不是完成等待，commit也不是结果ready。四个warp及其参与线程必须满足collective一致性要求。

具体例子

发起一组MMA后先做不依赖结果的地址计算，随后wait_group 0再把accumulator用于epilogue；这样才保留异步窗口。

先预测延后等待到真正依赖点可能提高重叠，但必须保持操作数生命周期。

容易混淆

发完mma_async立刻读取累加器，或者把wgmma.fence当成结果完成barrier。

检验理解为什么“commit后马上wait0”可能正确却没有重叠收益？

它立即关闭了可做独立工作的窗口，计算与其他工作仍趋于串行。

H19.05

warp specialization

#

warp specialization 解决的是分支发散，还是职责分离？

最小状态
warp角色、stage所有权、full/empty完成信号。
变化规则
producer发布ready tile，consumer消费并释放，双方在不同stage推进。

warp specialization让不同warp承担不同阶段，例如producer准备TMA，consumer执行矩阵计算，epilogue处理结果。它利用异步引擎和不同资源需求，让阶段在不同warp上同时推进；不是把一个warp里的lane随意拆成不同MMA参与者。

职责分离带来跨warp的buffer所有权、到达计数和phase管理。producer过少会供数不足，过多又占用驻留和发射资源。WGMMA consumer还必须保持完整warpgroup；角色应随tile、数据类型和设备改变，不能固定套一个比例。

具体例子

一个producer warp负责发下一tile的TMA，consumer warpgroup计算当前tile；用full/empty信号控制每个stage的交接。

先预测平衡职责可改善重叠；不平衡会把等待集中到某一角色。

容易混淆

认为不同warp执行不同代码天然获得独立资源且无同步成本。

检验理解consumer一直等full barrier，应该只增加consumer吗？

不应盲目增加。先检查producer供数、TMA流量和barrier协议，可能是供给不足。

H19.06

setmaxnreg 的寄存器资源调整

#

setmaxnreg 能把空闲SM的寄存器借给另一个block吗？

最小状态
每warp额度、CTA寄存器池、活跃尾部值。
变化规则
dec归还额度，inc从同CTA池申请；分配不足时等待。

PTX setmaxnreg调整执行warp的每线程最大寄存器额度，并通过同一CTA的寄存器池释放或申请额度。dec可把不用的尾部寄存器归还池，inc请求更多；若池里不够，inc会阻塞，不是凭空增加物理容量。

同一warpgroup必须一致执行并遵循后续同步规则，编译和launch也要提供适用的资源配置。新增寄存器内容未定义，需要初始化；释放前还要保证对应值已不再使用。它适合producer/consumer不同需求，不是跨CTA或跨SM资源迁移。

具体例子

低寄存器需求的producer释放一部分额度，consumer在同CTA池中申请更多accumulator空间；若双方先inc而无人释放，可能无法推进。

先预测职责差异大时可改善资源分配，但错误的申请/释放顺序可能阻塞。

容易混淆

把setmaxnreg当成改变整个SM寄存器总数的动态扩容指令。

检验理解inc一定立即成功吗？

不一定；它等待CTA池里有足够额度，且调用必须满足规定的参与与配置条件。

H19.07

cluster 驻留与 DSM

#

cluster 的 DSM 是“更大的shared”，还是一种受约束的远端访问？

最小状态
cluster成员、shared分片、准备/退出同步及可驻留cluster数。
变化规则
成员共同准备后进行DSM访问，全部远端使用完成后才结束生命周期。

Thread Block Cluster保证成员以协作方式调度到规定的硬件范围，使CTA能够访问cluster成员的shared memory。DSM仍由各block的shared分片组成，远端访问需要正确寻址和同步；数据的生命周期依赖拥有它的CTA。

cluster尺寸会影响可同时驻留的cluster数，不能把单SM occupancy简单相加。开始远端访问前要保证成员及其存储已准备，成员退出前要保证远端使用已结束。可移植最大尺寸与特定GPU的opt-in尺寸要分开处理。

具体例子

两个CTA各有一份局部直方图，先完成初始化和cluster同步，再访问彼此分片；所有远端访问结束后再允许成员退出。

先预测扩大cluster可能增强复用，也可能降低并发与负载均衡。

容易混淆

把DSM当成全GPU共享且在block退出后仍有效的低延迟内存。

检验理解某成员早退后，其他成员还能安全使用它的shared分片吗？

不能依赖这种行为；必须在生命周期结束前完成所有远端访问。

H19.08

SM100 Tensor Memory

#

SM100 Tensor Memory 为什么不能当普通寄存器或shared数组使用？

最小状态
TMEM分配区域、列数、许可、未完成使用者。
变化规则
按规定分配→计算/读回→完成同步→释放，不能在仍使用时复用。

TMEM是SM100类Tensor指令使用的专用片上存储，tcgen05的accumulator直接位于其中；部分A操作数也可以来自TMEM。它有专门的地址、分配和搬运指令，不是可用普通global/shared指针随意load的内存。

程序要按规则分配列、使用、等待相关操作完成并释放。TMEM alloc/dealloc是warp协作操作，和单线程发起MMA不同；分配许可与释放存储也有不同含义。容量和生命周期可能限制并发，不能因RF压力降低就忽视TMEM预算。

具体例子

同一CTA先分配accumulator的TMEM区域，MMA在其中累加，之后tcgen05.ld读入寄存器做epilogue，最后合法dealloc。

先预测大accumulator可减轻RF压力，但TMEM容量和读回成本可能成为新约束。

容易混淆

把“释放allocation permit”当成已经释放所有TMEM存储，或用普通ld.shared读TMEM。

检验理解为什么一个线程能发MMA，却不能据此让一个线程执行所有TMEM管理操作？

不同tcgen05操作具有不同执行粒度；alloc/dealloc有明确warp参与要求。

H19.09

tcgen05.mma

#

tcgen05.mma 单线程发起，是否只做一个线程的计算？

最小状态
instruction descriptor、A/B地址、TMEM D、完成barrier。
变化规则
单线程提交tile操作，异步完成后通过规定协议允许结果读取。

SM100类tcgen05.mma的发起语义是单线程，但它触发的是整个M×N×K矩阵操作。指令描述符指定形状和类型，A可来自shared描述符或TMEM，B来自shared，累加结果在TMEM；工作规模不由发起lane数决定。

它是异步操作，结果消费需按tcgen05的commit、mbarrier和顺序fence协议建立完成关系；TMEM load也有自己的等待规则。CUTLASS的对应fma封装用elect_one_sync选发起线程，但外围分配、供数和同步仍由协作线程完成。

具体例子

源码只看到一个被选中的lane发tcgen05，并不表示其他lane浪费；它们可能负责供数、读回或epilogue，Tensor控制路径在执行整块工作。

先预测发起指令很少仍可能驱动大量计算；发射率与FLOPs不能直接等同。

容易混淆

将warp-level mma.sync的32线程发起方式原样复制到tcgen05，使同一操作被重复发起。

检验理解发起线程的active-thread计数很低，是否可以直接判定Tensor没有吃满？

不能，要看指令家族、Tensor吞吐和整体流水；单线程发起是规定语义。

证据与适用边界 [2] [4] [6]对照观测指标 ↑

H19.10

支持的双 CTA 协作模式

#

cta_group::2 表示任意两个block都能一起做MMA吗？

最小状态
peer CTA对、cluster配置、双方TMEM/SMEM布局和存活状态。
变化规则
双方资源准备完成后，按支持模式发起协作MMA并遵守双CTA管理协议。

tcgen05的双CTA模式使用规定的peer CTA协作，操作可涉及两者的shared输入和TMEM结果。它依赖合法cluster、配对、形状及布局，不能把两个任意block的指针拼到描述符里就获得跨SM矩阵乘法。

操作的发起粒度与资源管理也不同：MMA仍由规定的单线程发起，双CTA TMEM分配/释放需要双方对应warp协作，peer必须已启动且仍存活。更大tile增加复用机会，也可能加重边界浪费、同步和驻留约束。

具体例子

CUTLASS v4.2.1的SM100_MMA_F16BF16_2x1SM_SS限制M为128或256，并生成cta_group::2；这些是该封装的约束，不是所有类型通用形状表。

先预测适合的tile可获益；小或不规则问题可能因更大tile与协作成本退化。

容易混淆

认为cta_group::2自动把任意两个CTA拼成两倍算力，且无需处理peer生命周期。

检验理解双CTA模式结果错，为什么除了MMA参数还要查TMEM allocation与cluster？

因为输入/结果布局、配对驻留及协作分配共同构成合法操作条件。

H19.11

Cluster Launch Control

#

Cluster Launch Control 抢走的是正在执行的block吗？

最小状态
当前工作者、尚未启动任务、取消结果和完成barrier。
变化规则
异步请求→等待结果→成功则消费被取消索引，失败则走合法结束路径。

CC10.0的CLC允许运行中的CTA尝试取消一个尚未开始的CTA或cluster，并在成功后取得它的索引，由当前工作者执行这份工作。它改变了逻辑任务的归属，不是强行接管另一个正在运行block的寄存器和shared状态。

取消请求异步完成，必须等结果可用后解析成功标志和索引；失败可能表示没有可取消工作，也可能与调度条件相关。程序需正确退出或按协议处理，避免重复任务和无限自旋。其价值是兼顾工作窃取与kernel调度弹性。

具体例子

某CTA提前做完自己的不规则tile，try_cancel成功获得待启动tile7，于是复用已有初始化状态计算tile7；若失败则结束该轮工作。

先预测任务耗时不均且初始化可复用时可能改善尾部；均匀小任务未必划算。

容易混淆

把CLC视为任意抢占正在运行CTA，或者不检查成功标志就使用返回索引。

检验理解为什么取消成功后必须把索引交给任务映射逻辑？

只有该索引标识被取消的工作；继续用原blockIdx会重复旧任务并遗漏被取消任务。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

ComputeWorkloadAnalysis / InstructionStats（sections）

确认使用WGMMA还是tcgen05，以及Tensor计算路径是否忙碌；把逻辑MMA次数和warp级指令计数分开。

Hopper warpgroup逻辑操作和Blackwell单线程发起的计数含义不同；不能按活跃线程数低就判定浪费。

[6]

MemoryWorkloadAnalysis（section）

对照预期tile字节检查TMA供数、shared路径及目标设备提供的TMEM相关观测。

TMA/TMEM指标支持随设备版本变化；先query，不假定一个计数器能证明所有proxy与barrier正确。

[6]

Occupancy / LaunchStats（sections）

结合寄存器、shared、cluster尺寸与TMEM分配评估可驻留工作，比较shape/CTA-group取舍。

SM占用率不能代替cluster可驻留数；tmemory容量、tile布局与架构专属限制需另核对。

[6]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

按设备分开比较供数和MMA（实验设计，未执行）

只改变

Hopper比较相同shape的同步供数与TMA+WGMMA流水；SM100单独比较合法1CTA/2CTA tcgen05方案，保持精度与输出一致。

预计现象

只有形成实际重叠或复用、且资源代价可接受时才会受益；跨架构不能用单个百分比归因于某条新指令。

记录什么

记录设备CC、CUDA/PTX/CUTLASS版本、SASS、布局和stage；先验证误差及边界，再测时间、供数字节、Tensor与资源占用。

排除干扰

不同tile有效算量、TMEM/SMEM驻留台阶、不同epilogue、初始化/descriptor成本、短K尾部与不正确的完成协议。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
