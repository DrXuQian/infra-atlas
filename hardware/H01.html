H01 / MEASURE BEFORE EXPLAIN

测量与证据

你测到的是指令、工作负载，还是测量工具？

建立从源码到 SASS、从微基准到计数器、从模型到真机的证据链。先定义测量对象，才讨论硬件机制。

适用范围

01

H01.01

PTX 与最终 SASS 的关系

#

源码里的一次乘加，为什么不能直接数成一条硬件指令？

最小状态
固定源代码、目标 SM、编译选项和运行镜像。
变化规则
PTX 经目标相关编译变为 SASS，SASS 经真实控制流产生动态指令流。

CUDA 源码、PTX 和 SASS 是三层不同的表示。PTX 描述虚拟线程和指令语义；ptxas 或驱动 JIT 再为目标 SM 选择机器指令、分配寄存器并安排控制信息。一次 PTX 操作可能消失、融合或展开，因此 PTX 行数不能直接代替动态发射次数。

分析延迟时先固定目标架构与工具链，保存实际运行的 cubin，并用 cuobjdump 或 nvdisasm 检查 SASS。还要区分静态代码里的指令条数与循环实际执行次数。若程序含多个架构的 fatbin，必须确认设备选择了哪个镜像。

具体例子

同一段 x=a*b+c，在不同浮点语义或编译选项下可能得到融合乘加或分离乘法、加法；应比较最终 SASS 和数值结果。

先预测若改变编译选项，先预测 SASS 是否改变，再解释性能差异。

容易混淆

看见 PTX 的 mad 或 fma，就宣称所有 GPU 都只发射一条同名机器指令。

检验理解两次实验 PTX 相同、SASS 不同，还能只归因于硬件吗？

不能。目标架构、编译器调度、寄存器分配都可能改变测量对象。

H01.02

用依赖链测指令延迟

#

怎样让测到的时间主要暴露结果依赖延迟？

最小状态
一条结果链、链长 N、输入、终值和计时边界。
变化规则
仅当前生产者结果可用，下一条消费者才允许推进。

构造串行 RAW 依赖链：后一条指令必须消费前一条的输出，避免它们重叠执行。用多种链长 N 测周期，考察 T(N) 的斜率，比把单条指令夹在两次计时读取之间更能压低计时开销的比例。

这个斜率接近该指令序列的依赖受限成本，并非无条件等于某个内部流水级数。循环控制、时钟读取、编译器重排及其他 warp 的发射竞争仍会进入结果。需要保留最终输出、检查 SASS，固定数据类型和依赖操作数。

具体例子

教学数据若 T(100)=430、T(200)=830 周期，则增量斜率为 4 周期/操作；常数 30 周期不应重复算进每一条。

先预测若依赖链是唯一瓶颈，增加 N 后时间应近似线性增加。

容易混淆

把吞吐倒数、kernel 总时间除以线程数，或有并发干扰的时钟差当作纯指令延迟。

检验理解为什么至少测多个 N，而不是只测一次？

可以分离固定开销，识别非线性区间，并检查循环或缓存效应是否改变。

03

H01.03

用独立指令流测吞吐

#

独立指令为什么能比一条依赖链更快完成同样工作？

最小状态
独立链数 K、每链依赖、入口接收间隔和有效工作量。
变化规则
按程序顺序轮流推进不同累加器，不越过阻塞的队首指令。

多个独立累加器把结果依赖分散开：在 a0 等待时，可以发射 a1、a2 的指令。流水线允许新操作进入的间隔称为 initiation interval，它与一个结果变得可消费的 latency 不同；吞吐实验需要足够多独立工作让入口持续忙碌。

增加独立链数后，单位时间完成的操作数通常先升后趋于平台。平台可能由发射、操作数读取或执行管线限制造成，不一定就是某种 ALU 数量。必须按 warp 指令、线程指令或 FLOP 统一计数，并把每次 FMA 的两个浮点运算明确写出。

具体例子

教学流水线 latency=4、每周期接收1条。单依赖链只能约每4周期发射；四条交错的独立链可在稳态每周期发射。

先预测K 增加到足以覆盖延迟后，继续增加 K 不应突破同一管线吞吐上限。

容易混淆

把一条指令需要4周期，理解成整个执行管线4周期只能处理一条。

检验理解增加到八条独立链后吞吐不再涨，说明什么？

已有足够并行性，某个容量或速率瓶颈成为上限；还需计数器和对照定位。

H01.04

编译器优化如何破坏微基准

#

微基准里写出的计算，为什么可能根本没有执行？

最小状态
输入来源、终值可见性、SASS 指令序列、寄存器活跃区间。
变化规则
只有对可观察结果有贡献的操作才被编译器要求保留。

编译器按可观察行为保持语义，而不是按研究者的意图保留每行操作。无外部用途的结果可被删除，常数输入可能被折叠，循环可能被化简，独立操作可能被重排。源代码看起来很长，并不保证产生相同长度的依赖链。

应让输入来自运行时，把最终结果写回并核对正确性，记录编译选项、寄存器数和反汇编。必要时用受控内联 PTX 表达特定依赖，但 volatile 或内联 PTX 也不自动冻结全部后端优化；必须查看实际 SASS 的操作数关系与计时位置。

具体例子

计算循环的结果若从未写回，整个循环可能被移除。加上输出后仍需检查：编译器是否把重复加常数替换成另一种等价计算。

先预测删除输出用途可能显著缩短生成代码和测量时间。

容易混淆

使用 volatile 就认为测量已经免疫所有编译优化。

检验理解计时变快一百倍时，应先检查哪个对象？

先看 SASS 与输出正确性，确认工作仍存在，再调查硬件优化。

H01.05

时钟、预热和缓存状态如何影响结果

#

同一个 kernel 重复跑，为什么第一遍和后面不一样？

最小状态
代码加载状态、频率、温度、工作集和缓存预置。
变化规则
预热改变初始条件；测量只在声明的初始状态之后开始。

首次执行可能包含模块加载、JIT、页映射和冷缓存；随后 GPU 频率、温度、功耗状态与数据缓存又会变化。纳秒时间和设备周期不是可随意互换的量，尤其频率在运行间变化时。预热必须明确是在预热代码、设备状态还是特定数据。

把冷启动、稳定热运行和应用真实上下文分别测量。记录时钟控制、缓存控制与输入工作集；NCU 为可复现性采用的时钟和缓存策略可能与不带 profiler 的程序不同。若问题是相邻 kernel 的缓存复用，应保留应用上下文，而不能只测被冲洗过的孤立 kernel。

具体例子

研究权重 L2 复用时，先执行生产热缓存的访问，再测消费者；若 profiler 在消费者前清缓存，这个实验已经换了问题。

先预测工作集能驻留缓存时，冷与热运行可能出现明显差异。

容易混淆

只报告最快一次，或把 NCU 的默认缓存状态当成应用长期运行状态。

检验理解热缓存实验用什么作为对照？

同一输入和代码下的显式冷状态，并保持其余时钟、工作集和测量边界一致。

H01.06

NCU 的 active / elapsed 归一口径

#

为什么两个看似相同的利用率百分比不能直接比较？

最小状态
计数值、单元实例、活动周期和总经过周期。
变化规则
先按指定实例聚合，再按该指标定义的周期与峰值归一化。

NCU 指标名包含硬件作用域、聚合方式和归一化口径。.avg 通常聚合多个同类单元实例；per_cycle_active 以单元活动周期为分母，per_cycle_elapsed 则包含测量窗口中的空闲周期。两者回答的是忙时效率和整个窗口的平均效率。

因此 active 口径很高，仍可能只有少数 SM 或很短一段时间在工作。分析前先看指标详情和支持的实例分布，再把发射率、驻留 warp、pipeline 活动与整卡耗时分开。不要把一个平均值解释成每个 scheduler 都处于相同状态。

具体例子

简化例：某单元100个窗口周期里只活跃25周期，活跃时每周期执行1次；active 速率为1，elapsed 速率为0.25。

先预测同一计数值在包含更多空闲周期的窗口中，elapsed 速率会下降。

容易混淆

把 pct_of_peak_sustained_active 当成整张卡在整个 kernel 时间内的有效 FLOPS 百分比。

检验理解某指标 avg=50%，能证明所有 SM 都50%吗？

不能。可能来自单元间不均衡，也可能来自时间上的空闲；需看实例或时间分布。

H01.07

采样、replay 与测量扰动

#

性能分析工具为什么会改变正在分析的程序？

最小状态
replay 模式、采样间隔、采集 passes、被观察的执行上下文。
变化规则
每次重放按工具策略恢复状态；采样只记录被抽中的观察时刻。

硬件计数器不能总在一次运行里收集全部指标，NCU 可能重放 kernel 或应用，也可能保存恢复设备内存。PC 采样只是以一定间隔观察 warp 状态；它不是完整逐周期日志，某个 stall 的样本比例也不是整个 GPU 损失时间的直接分解。

应先以普通运行测端到端时间，再用最少必要指标验证假设。对依赖并发、缓存预置或主机交互的代码选择合适 replay 模式；比较两次结果时保持采集方法相同。短 kernel 样本少时，应报告波动或扩大代表性工作窗口，不能凭单个样本下结论。

具体例子

两个并发 kernel 在应用中重叠，孤立重放一个 kernel 时竞争消失。所得计数器适合解释局部行为，却不能直接还原应用吞吐。

先预测增加指标可能增加 passes 和工具开销，但不代表原 kernel 变慢。

容易混淆

将全部 stall 样本加和后，当作可逐项相加的端到端时间损失。

检验理解采样显示某行等待很多，应该查生产者还是只改这行？

两者都要看；等待通常出现在消费者，根因可能是更早的生产者访问。

H01.08

模拟器结果如何与硬件校准

#

模拟器和真机时间接近，就能认定内部机制完全一致吗？

最小状态
模型版本、配置、trace、真机测试集和独立验证集。
变化规则
单变量微基准约束参数，再以独立工作负载检查预测。

模拟器把已知机制与可调参数组合成一个可执行模型。总时间相近可能由不同误差抵消：管线过快与访存过慢恰好相抵。校准因此应拆成指令、缓存、吞吐、并发和整程序多个层次，用未参与调参的工作负载检验泛化。

记录 simulator commit、配置、trace 生成方式、真实设备和驱动工具链。先比较有明确预期的微基准，再比较指令量、cache miss、带宽与调度等待等可观察量。代码中的队列大小、仲裁策略和子分区组织是模型定义，不能仅因匹配一个 benchmark 就称为芯片实物。

具体例子

若模型和真机都用1毫秒完成某 GEMM，但模型 DRAM 流量多一倍、计算吞吐也高一倍，时间吻合仍暴露出错误的瓶颈解释。

先预测正确的机制模型应能解释趋势和转折点，而不只是一个总耗时数值。

容易混淆

把 Accel-Sim 的默认 GTO 策略写成 NVIDIA 硬件的官方调度策略。

检验理解校准后换一个工作集大小就严重偏差，优先怀疑什么？

先怀疑缓存、并发或工作集转折点的建模与配置，而非继续只拟合总时间。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

InstructionStats / SourceCounters

检查动态指令种类、SASS 与源码关联，再判断测量链是否真实存在。

section 可用性先用 ncu --list-sections 查询；源码映射依赖编译调试行信息。

[3]

.avg.per_cycle_active 与 .avg.per_cycle_elapsed

分别理解活动周期与经过周期上的平均速率；结合实例分布判断空闲或不均衡。

这是指标后缀口径，不是可单独执行的 metric 名；完整名称用 ncu --query-metrics 核对。

[3]

launch__registers_per_thread

检查微基准改变 ILP 后寄存器占用是否也发生变化。

LaunchStats 元数据，不表示动态 RF 读取带宽。

[3]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

实验设计：依赖链斜率与独立链扫描（未执行）

只改变

先固定一个依赖链并改变 N；再固定总操作数，改变独立累加器数量。

预计现象

依赖链时间随 N 近似线性；独立链增加后吞吐先提升，再受发射或管线容量限制。

记录什么

保留输出并验值；反汇编 SASS，记录资源用量、普通运行耗时和必要 NCU section。

排除干扰

编译器化简、循环开销、register spill、频率、warmup、replay 和缓存状态。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
