H15 / SYNCHRONIZATION & ORDER

同步与内存顺序

一个线程说“完成了”，另一个线程何时才能安全读取？

把参与者、执行进度和内存顺序分别画清楚：barrier 处理集合到达，release / acquire 建立数据发布关系，scope 限定谁能依赖这份保证。

适用范围

CUDA C++ 与 PTX 的公开同步契约；warp 示例针对支持相应同步指令的现代 CUDA GPU。普通内存访问模型不代替 TMA / async proxy 专用完成与排序规则。逐步图是事件顺序，不是真实 GPU 时钟或缓存刷写过程。

01

H15.01

warp 内同步及参与掩码

#

同一个 warp 的线程为什么仍需要显式同步？

最小状态
状态是参与掩码、各 lane 的到达标记及待共享的内存值。
变化规则
全部规定参与者到达后，后续协作读取才能越过该同步点。

同属一个 warp 不等于任意时刻都已完成彼此依赖的访存。__syncwarp(mask) 为掩码指定的参与线程建立集合等待和内存顺序，使屏障前写入可用于屏障后的协作读取；它只覆盖指定集合，不能把另一个 warp 的线程一并同步。

掩码描述协议参与者，不只是调试时观察到的活跃 lane。每个调用者必须在掩码中，指定且未退出的线程必须按规则以相同掩码参加；不要在分歧路径内用一次 __activemask() 就假定得到完整逻辑分组。需要子组时，应先明确组成员与控制流约束。

具体例子

lane 0–3 各写一个 shared 元素，四者都以 0xF 同步后，再互读邻居的值。其余 lane 不读写这组数据，也不参加这次同步。

先预测先数出 mask 中需要到达的线程，再判断谁可以读取邻居的值。

容易混淆

shuffle 交换寄存器值不等于对任意 shared memory 访问加屏障；满掩码也不能补救有参与线程漏到达。

检验理解仅 lane 0–3 调用时，能用 0xFFFFFFFF 等待仍在运行的整个 warp 吗？

不能。掩码中其他未退出线程也必须按规则参加，否则同步行为不成立。

02

H15.02

CTA barrier 的到达与等待

#

CTA barrier 怎样把到达与继续执行联系起来？

最小状态
最小状态是本轮参与集合、已到达集合与 barrier 代次。
变化规则
本轮到达条件满足后释放等待者，再开始下一代的到达记录。

__syncthreads() 是 block 内的集合屏障：线程到达后等待该次同步所需的其余参与线程，完成时为这些线程的前后访存提供相应顺序。教学模型可画成一代 barrier 的到达集合，但真实硬件的记录方式与吞吐不能由这张图推断。

每一次动态执行的 barrier 都是一轮协议。线程不能跨轮借用别人的到达，也不能让部分未退出线程绕过必需的屏障。条件分支中的 __syncthreads() 要满足 block 一致的条件；需要仅一部分线程协作时，应该选合法的子组或专用 barrier API，而非任意删参与者。

具体例子

128 线程 block 装载 shared tile，所有线程到达屏障后才读取其他线程填入的位置；即使边界线程不装载有效元素，也要依协议参与并提供定义好的边界值。

先预测如果还有一个需要参与的 warp 在装载数据，先到的 warp 仍应停在屏障前。

容易混淆

一次 __syncthreads() 不同步整个 grid，也不自动替代异步拷贝所要求的完成等待。

检验理解最后一个 warp 已到达，是否说明下一轮 barrier 也已经完成？

没有。屏障属于特定动态轮次，下一轮必须重新满足到达条件。

03

H15.03

到达时间不均造成的等待

#

barrier 等待高，是否说明 barrier 指令很慢？

最小状态
状态是各 warp 的剩余工作与抵达同一屏障的时刻。
变化规则
早到者等待；最后的必要参与者到达才结束本轮集合等待。

等待常来自抵达时间不同。一个 warp 很快完成工作并到达 barrier，另一个 warp 仍在处理长路径或等待内存，前者的停留会记在同步位置。于是采样热点指向屏障，却不代表延迟主要由屏障本身产生；根因可能在更早的工作分配。

可以先固定总工作和同步语义，只改变每个 warp 分到的工作量，比较早到者等待是否下降。NCU 的 barrier 样本还会在其他 warp 正常发射的周期出现，因此消除样本并不等于节省同量运行时间。要同时检查发射活动、完成时间与尾部 CTA 的负载。

具体例子

四个 warp 的准备时间为 4、4、4、20 个教学时间单位，前三个各等待约 16；均衡到 8、8、8、8 可消除这部分到达偏斜，不涉及真实硬件周期。

先预测在总工作不变时加大工作偏斜，预计 barrier 等待增加，但先不预测等比例变慢。

容易混淆

把 barrier 删除后变快，不证明同步多余；可能只是把数据竞争隐藏在偶然正确的输出中。

检验理解三条快路径的 barrier 样本多，应该先检查屏障后还是屏障前？

先检查屏障前的工作偏斜、访存依赖和最慢参与者，并保留必要的同步语义。

H15.04

原子性、可见性、顺序性的区别

#

原子更新为何不能自动发布旁边的数据？

最小状态
状态是共享对象、访问是否原子、内存序与双方间已建立的关系。
变化规则
对 flag 的原子更新只改变该对象的原子状态；其他数据的发布需要额外排序关系。

原子性保证在规定 scope 内对该对象的操作不可被并发访问撕裂；顺序性约束不同内存操作之间的先后关系；可见性讨论某次读取能依协议观察哪个写入。三个问题相关但不同，原子计数器正确递增，并不自动说明此前写入的另一个数组已安全发布。

relaxed 原子适合只需要该对象原子性的场景。若消费者据 relaxed 标志读取与生产者并发访问的普通 payload，却没有其他 happens-before 关系，CUDA C++ 程序可能构成数据竞争并产生未定义行为；此时不能把“偶尔读到旧值”当作它唯一且受保证的语义。

具体例子

只统计事件数量时，充分 scope 的 relaxed fetch_add 可以满足计数需求；用同一个计数通知别人读取刚填好的记录，则要另行建立发布与消费顺序。

先预测只看到 atomic 字样时，先不要推断相邻普通写已对消费者安全可读。

容易混淆

volatile 既不等于 atomic，也不提供完整的线程间同步协议；缓存命中率更不能证明可见性正确。

检验理解把 flag 改成原子变量，能否独立证明普通 payload 的并发读取安全？

不能。还要证明覆盖双方的同步与先行关系，且没有复用或其他写者造成的竞争。

H15.05

block / device / system scope

#

scope 指的是数据在哪里，还是谁能同步？

最小状态
状态包括线程所属 block、device、同步域，以及对象的分配类型和原子能力。
变化规则
只有 scope 与平台支持条件覆盖实际参与者，才能应用对应原子及同步保证。

scope 限定同步保证覆盖的线程关系，并非内存地址空间的别名。block scope 面向同一 CTA，device scope 面向同设备且同一 memory synchronization domain 的线程，system scope 面向系统参与者。global 地址里的原子对象，也可能只选了 block scope，不能因此支持跨 block 协议。

双方的操作都必须具有足以包含对方的 scope，且内存对象本身支持所需原子访问。CPU/GPU 交互还受 managed、mapped 或 system allocation 类型及设备能力限制；只写 system 字样不会凭空提供平台不支持的原子性。跨同步域通信也不能简单套用同一域的 device 保证。

具体例子

两个不同 CTA 用 global flag 通信时，block scope 不足；同域单 GPU 可考虑 device scope。若消费者改成 CPU，则需系统 scope 并核对该分配类型的支持条件。

先预测把消费者从同 CTA 移到 CPU 前，预计需要重新审查 scope 与对象支持条件。

容易混淆

scope 更大不代表参与线程会自动被调度，也不代表数据自动迁移到对应处理器附近。

检验理解GPU 与 CPU 使用同一个 UVA 指针，能否直接假定系统原子操作受支持？

不能。相同地址不等于相同原子能力，必须核对内存类型、设备属性与访问方式。

06

H15.06

release / acquire 的发布—消费关系

#

release 与 acquire 之间必须发生什么，数据才算发布成功？

最小状态
最小状态是 payload、原子 flag、读到哪个写入，以及缓冲区当前所有者。
变化规则
release 写入被相容 scope 的 acquire 读取后，先前写与后续读之间建立同步链。

单次消息中，生产者先写普通 payload，再对原子 flag 作 release store；消费者作 acquire load，并且确实读到这次 release 写入的值，才建立所需同步。结合线程内顺序，payload 写先于消费者之后的读取，前提是双方 scope 相容、对象有效且没有另一个并发写者。

关键是“读到对应发布”，不是双方各执行过一次带 acquire 或 release 的指令。读到初值的 acquire 不会接收尚未发布的消息。循环复用缓冲区还必须安排所有权交还与代次，否则生产者可能在消费者读取时覆盖 payload；一次正确握手不能证明任意次数复用都正确。

具体例子

初始 flag=0。生产者写 payload=42 后 release 写 flag=1；消费者 acquire 读到 1 后读取 payload。此例只发一次消息，生产者不再修改该位置。

先预测先确认 acquire 实际读到哪个发布，再预测 payload 读取是否被顺序关系保护。

容易混淆

release 不保证消费者马上运行；acquire 也不是把所有缓存清空。这里建立的是有条件的内存顺序关系。

检验理解消费者的 acquire 读到 0，它能以“已经 acquire”为理由读取本次 payload 吗？

不能。这次读取未观察到生产者的发布值，因此没有建立本次消息所需的同步。

H15.07

fence 与执行同步的职责

#

fence 能让另一个线程停下来等我吗？

最小状态
状态是每线程内存操作顺序、fence scope，以及是否存在连接双方的原子通信。
变化规则
fence 加入排序约束；只有满足正式同步模式时，才能经由通信边影响另一线程。

fence 约束调用线程前后内存操作的顺序，不是等待一群线程抵达的执行屏障。消费者什么时候可以开始读取，仍需由完整的通信协议决定。不能只在生产者写完后放一条 fence，就假定任意时刻启动的普通读取都已安全。

fence 可以参与正式的同步模式，但需要符合内存模型的原子读写连接、读到关系与 scope；不是任意两个 fence 都能组成握手。通常用明确的 release-store / acquire-load 更容易审查。执行 barrier 也有参与范围和内存保证，要按 API 契约使用，而不是把 fence 与 barrier 当作可随意互换的同义词。

具体例子

生产者写好记录再执行 device fence，却没有让消费者观察的原子就绪标志，消费者仍无法判断何时读取。采用正确发布握手后，才有可解释的开始条件。

先预测如果图中没有任何就绪信号或合法集合等待，先预测 fence 不会让消费者自动等待。

容易混淆

在存在普通数据竞争的 C++ 例子里插入孤立 fence，不能把未定义行为自动修复成受保证的“旧值或新值”。

检验理解所有线程各执行一次 __threadfence()，是否等于一次 __syncthreads()？

不等于。它没有 CTA 集合到达与等待语义，也未单独建立所需的线程间通信关系。

H15.08

跨 block 自旋同步的进展与死锁问题

#

跨 block 的自旋等待为什么可能永远等不到？

最小状态
状态是有限 CTA 槽位、已驻留 block、待调度 block，以及谁等待谁。
变化规则
只有驻留者退出或协议提供受保证的共同进展，等待链中的生产者才可能执行。

普通 grid 的 block 不保证全部同时驻留，也不保证按 block 编号执行。若已驻留的消费者占满可用资源，并一直等待尚未获得驻留机会的生产者，它们不退出就无法释放资源，生产者也无法推进。这是进展问题，即便 flag 的原子性和内存顺序完全正确也仍可能发生。

真正的 grid 集合同步应使用受支持的 cooperative launch，并满足设备支持、资源与共同驻留条件。另一种清楚的阶段划分是前一 kernel 完成，再借同 stream 顺序或显式 event 依赖启动下一阶段。__nanosleep() 可降低轮询压力，但不能作为释放 CTA 驻留资源的保证。

具体例子

教学模型只有 2 个 CTA 槽位，先驻留的 A、B 都等 C 发信号，而 C 仍排队。A、B 不退出便没有空位；把轮询间隔加长不改变这个资源环。

先预测先画等待图与驻留槽位；若信号源在排队且所有槽位都被等待者占住，预测无法依协议推进。

容易混淆

两三个 block 的小测试能结束，不说明扩大 grid 后也有进展保证；scope、原子性、内存顺序和调度进展是四项独立检查。

检验理解把等待 flag 改成 system-scope acquire，能否修复生产者始终无法驻留的问题？

不能。更大的同步 scope 不增加资源，也不提供 block 调度与共同驻留保证。

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

smsp__warp_issue_stalled_barrier_per_warp_active.pct

按 active warp 归一化的 CTA barrier 等待占比，用于观察同一 block 内到达时间不均。

不是整卡空转时间或每条 barrier 的固有周期；先用 --query-metrics 确认目标支持，再和实际运行时间、issue 活动一起解释。

[6]

smsp__warp_issue_stalled_membar_per_warp_active.pct

按 active warp 归一化的内存屏障相关等待占比，帮助定位排序操作附近的等待。

不能据此证明内存协议正确，也不能认为所有 release/acquire 都生成同一种 fence；检查目标 SASS 和访存量。

[6]

SourceCounters：smsp__pcsamp_warps_issue_stalled_barrier

把 CTA barrier 等待样本映射到指令与源码，寻找等待位置和前面的慢路径。

这是采样数；同周期其他 warp 可能发射，不能把样本直接相加当作 kernel 延迟。它不覆盖所有现代异步同步类型。

[5]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

到达偏斜与 barrier 等待（实验设计，尚未执行）

只改变

固定一个 CTA 的 4 个 warp、内存访问与总算术工作，只把 barrier 前每 warp 的工作单位从 8/8/8/8 改为 2/2/2/26；每个线程均正确到达同一次 barrier，计算结果写出以防被优化删除。

预计现象

偏斜组的早到 warp 应积累更多 barrier 等待；如果其他 CTA 足以填满发射槽，等待样本增加也未必等比例拉长整体时间。

记录什么

先校验输出和参与规则，再对照 CUDA event 时间、barrier metric、SourceCounters 的等待位置和 scheduler issue 活动；确认 SASS 中两组总工作确实可比。

排除干扰

循环代码生成、寄存器用量、CTA 驻留、时钟与 cache 状态均会影响结果。不要删除必要 barrier 作“优化”对照；NCU 计数器和压力测试都不能证明不存在数据竞争。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。

EVIDENCE & SCOPE

来源与边界

官方文档约束编程语义；论文记录特定设备上的观察；模拟器源码定义模型行为。三种证据不能相互替代。

  1. 官方文档CUDA：同步函数、参与掩码与 fence ↗

    核对日期 2026-11-07。§5.4.4 与 §5.4.6.6；__syncthreads、__syncwarp 和 warp collective 参与规则。

  2. 官方文档CUDA C++ Memory Model ↗

    核对日期 2026-11-07。scope、memory synchronization domain、系统原子支持条件、data race 和 fence 同步关系。

  3. 官方文档PTX ISA 9.5：Memory Consistency Model ↗

    核对日期 2026-11-07。§8.8 release/acquire patterns、§8.9 observation 与 causality order；PTX 与 CUDA C++ 的数据竞争规则须区分。

  4. 官方文档CUDA 12.8.1：Grid Synchronization ↗

    固定版本 §8.7，核对日期 2026-11-07。cooperative launch、设备支持与 co-residency 限制；只引用单 GPU grid sync，不引用已移除的多设备 API。

  5. 官方文档Nsight Compute：Warp Stall Reasons ↗

    核对日期 2026-11-07。barrier 与 membar 的采样解释；barrier 样本经常由到达不均引起，不能直接当硬件 barrier 延迟。

  6. 官方文档CUPTI 13.2.1：PerfWorks metric 映射 ↗

    §2.15 metric mapping 核对 barrier / membar 精确名称；实际 GPU 和 NCU 版本仍需查询支持。
