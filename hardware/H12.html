H12 / MEMORY IN FLIGHT

访存并发、队列与反压

带宽没有跑满，是请求太少，还是某段队列先满了？

用在途请求、合并等待者和有限队列理解访存并发。发出 load、等到返回、释放跟踪项是三个事件。

适用范围

01

H12.01

load 发射与数据返回

#

发出 load 等于拿到数据了吗？

最小状态
目标寄存器待完成标记、独立指令、在途请求。
变化规则
数据返回交付后解除依赖，再重新判断消费者资格。

Load 发射只表示指令进入访存处理路径，后面还可能有地址合并、翻译、缓存查询、互连和返回。目标寄存器在数据可用前不能被合法消费者使用；warp 可以执行程序顺序中允许的其他独立指令，并不需要所有工作一起停住。

必须区分请求入口接收、请求在途、返回交付和消费者重新 eligible。实际管线可能把这些步骤分成更多队列。NCU long scoreboard 指向等待 L1TEX 结果的消费者，但其根因可能是缓存延迟、返回拥塞或独立工作不足。

具体例子

顺序为 load r0、独立 add r7、使用 r0 的 add。第二条可能在等待期间执行，第三条必须等 r0 可用；不能跳过第三条去任意乱序执行后面的工作。

先预测把独立计算放在 load 与使用之间，可能减少暴露的等待。

容易混淆

把 in-flight load 当成 warp 完全空闲，或假定线程指令动态乱序。

检验理解load 已 issued，下一条使用结果的指令一定 eligible 吗？

不一定，需等待目标数据真正可用。

02

H12.02

未完成 miss 的跟踪项与 MSHR 模型

#

MSHR 跟踪的是数据还是尚未完成的工作？

最小状态
MSHR 地址键、等待者列表、entry 与合并上限。
变化规则
新 miss 分配 entry，返回交付完成后释放其跟踪资源。

在常见非阻塞缓存模型中，MSHR 保存未完成 miss 的地址键、请求状态与等待者，使缓存能继续接受其他访问。它不等同于缓存的数据容量，也不等同于每个 warp 的寄存器依赖记录，三个资源可能分别形成限制。

已读 Accel-Sim mshr_table 用地址键索引，并限制总 entry 数和每项合并列表长度。这里的实现说明如何构建模型，不证明 NVIDIA 真机照此组织；真实未完成 miss 跟踪资源可能分层、分区，并与回填队列有耦合。

具体例子

教学缓存有 64 条数据 line，却只有 2 个 miss 槽。A、B 都 miss 后，C 即使有空数据位置，也可能等不到新的跟踪槽。

先预测只扩大跟踪表而不改数据容量，可在模型中提高并发上限。

容易混淆

用 cache size 除以 line size，就得到硬件可并发 miss 数。

检验理解扩大缓存容量必然提高最大在途 miss 数吗？

不会，数据容量与 miss 跟踪资源是不同限制。

03

H12.03

多个请求如何合并等待

#

两个请求同一数据，为什么不必向下游读两次？

最小状态
miss 地址键、已挂等待者、允许合并数。
变化规则
同键且未达合并上限则追加等待者，不重复分配下游 miss。

若后到请求与一个正在处理的 miss 对应相同可合并块，缓存可把它加入现有等待列表，共享下游返回。这样减少重复外发流量，却没有让数据提前出现；所有等待者仍要等到同一生产数据准备好。

合并有粒度与容量边界。已读模型按 mshr_addr 生成键，并检查合并列表上限；相近地址不一定属于同一键。原子、读写先后或不同 sector 状态也不能仅按地址相近就任意合并，需遵守模型和内存语义。

具体例子

A 的 miss 已挂 w0，再来同键 A 的 w1：下游仍一个请求，但表里两个等待者。若两者属于不同键，就需两项或等待空槽。

先预测同键并发可能减少下游请求数，但消费者仍等待返回。

容易混淆

把 MSHR hit 当成缓存数据 hit，认为请求已可立即返回。

检验理解合并减少外发请求，是否消除了 load 延迟？

没有，只共享等待；数据返回和交付仍需完成。

04

H12.04

miss 跟踪资源耗尽

#

miss 跟踪资源满了会发生什么？

最小状态
新 entry 数、合并数、请求类型和返回进度。
变化规则
失败请求保持待处理，相关资源释放后再次尝试。

非阻塞缓存也有有限并发预算。没有可用跟踪项时，新 miss 不能安全进入，因为系统无法记录它应返回给谁；请求被阻止或重试，压力可能继续传回上游。此时下游带宽未必已经打满，可能是长延迟占槽过久。

区分新地址 entry 满与同地址合并列表满。已读 mshr_table::full 对已有键检查等待者数，对新键检查 entry 数，因此总表满时仍可能接受同键合并。NCU 并没有可跨所有设备直接读出的通用 MSHR 容量计数器。

具体例子

两槽都被 A、B 占据，C 被拒；A 的等待列表还有空位时，第二个 A 却可进入。所谓满，必须说明是哪类资源满。

先预测降低 miss 延迟会缩短占槽时间，可能提高同容量表的吞吐。

容易混淆

看到 lg_throttle 就唯一断定 MSHR 已满，并反推精确条目数。

检验理解总表满时，所有访存都必须被拒绝吗？

不是；cache hit 或允许的同键合并可能仍能前进。

H12.05

LSU 队列满如何阻止后续发射

#

LSU 队列满如何阻止后续发射？

最小状态
入口队列占用、每步接收数、下游服务速率。
变化规则
队列无空位即停止接收，消费释放位置后恢复。

从 scheduler 到 L1TEX 之间存在有限入口和处理资源。队列满时，新的 local/global 操作无法继续送入，warp 会受到入口反压。大量窄访存、local spill、请求展开过多或下游返回慢，都可能让入口服务赶不上输入。

队列压力是整条链条的结果，不能只通过扩大队列解决。若下游吞吐不变，更深队列最多吸收短暂突发；长期仍会满。应检查 SASS 的访存数量、合并效率、local 流量和各级带宽，寻找具体服务率失衡的位置。

具体例子

每步产生 2 个请求、入口每步只能消费 1 个，深度 4 的队列最终填满。改成深度 8 只延后满的时刻，稳定吞吐仍为每步 1 个。

先预测减少重复小 load 可能同时降低 throttle 和总耗时。

容易混淆

把 throttle 当作内存延迟，或认为加入更多 warp 总能改善。

检验理解入口满但 HBM 利用率低，矛盾吗？

不矛盾，瓶颈可能在指令入口、地址展开或片内路径。

H12.06

一个 warp 如何提供多条独立访存

#

一个 warp 怎样提供更多独立访存？

最小状态
独立地址表达式、目标寄存器、当前在途数。
变化规则
按程序顺序发射独立 load；使用各结果前分别等待完成。

一个 warp 可以在程序顺序中先发出多个互不依赖的 load，再使用结果。前提是后续地址不依赖前一个返回值，而且目标寄存器、队列与发射资源可用。这种内存级并行来自合法指令安排，不是跨越依赖的任意乱序。

同时保留更多返回结果会增加活跃寄存器，可能降低驻留 warp 数。对指针链，单链下一地址必须等待，可通过多条独立链增加并发；但要比较相同有效字节和缓存条件，否则只是换了另一个工作负载。

具体例子

先 load A[i] 到 r0、load B[i] 到 r1，最后计算 r0+r1，可让两次读取重叠；p=next[p] 的单链无法用同一办法提前知道下一地址。

先预测独立链增加可先提高带宽，随后受寄存器或队列限制。

容易混淆

把循环展开本身当成并发保证，不检查是否仍是同一依赖链。

检验理解四倍展开的单一 pointer chase 会获得四倍并发吗？

不会，地址依赖仍串行；需独立链或其他独立请求。

07

H12.07

需要多少在途字节才能填满带宽

#

要填满带宽，至少要多少在途字节？

最小状态
同一层的平均吞吐 B、平均响应 L、在途量 Q。
变化规则
增加可持续在途工作直到服务能力或其他资源封顶。

稳定状态下可用平均在途量约等于吞吐乘平均响应时间来估算：Q≈B×L。若选定层的目标带宽为 B、从请求进入到响应完成平均时间为 L，就需要数量级为 B×L 的在途字节，才能在等待期间持续提供工作。

这是单位一致的排队关系，不是直接给出所需 warp 数的硬件公式。一次 warp 请求可能展开成多个 sector，延迟会随拥塞变化，各级的有效字节也不同。应明确所选层、稳态窗口、是否排除启动和排空，再用实测数据检验。

具体例子

教学目标 1TB/s、平均响应 500ns，需要约 500KB 在途量。若当前只有 50KB，其他条件不变时无法持续达到该目标；这些数字不是某型号测量值。

先预测并发低于 B×L 的数量级时，可能出现低带宽而长等待。

容易混淆

把 useful bytes 的带宽乘上全路径延迟，再当成某级精确 MSHR 数量。

检验理解B 的单位为 GB/s、L 为 ns 时应先做什么？

先统一十进制/二进制与时间单位，再计算字节量，并注明统计边界。

H12.08

store 排空与 kernel 尾部

#

最后一条指令执行后，为何还会 drain？

最小状态
退出状态、未完成访存、可回收资源。
变化规则
相关访问满足完成要求后释放 warp 资源；缓存驻留可继续存在。

Warp 到达退出位置时，部分访存仍可能在途。硬件需按执行与内存语义完成相关工作，才能安全回收资源。NCU drain 状态描述 EXIT 后等待未完成访存的情形，集中写结果的 kernel 尾部尤其值得观察。

完成不能简单翻译成把所有脏缓存行写回 HBM。后续同 stream 的任务或显式同步需要获得规定的可见性，但数据可留在一致性允许的缓存层。分析应区分 warp 释放、kernel 完成、主机观察和物理显存写回。

具体例子

许多 warp 同时在末尾写出大块结果，最后几个 warp 的在途 store 延迟会影响资源释放；即使前段计算很快，尾部仍可能拉长 kernel 时间。

先预测将分散写出改成合并写出，可能降低 drain 与尾部延迟。

容易混淆

用 drain 的百分比直接当作可以全部消掉的 kernel 时间，或认为 kernel 完成必须清空 L2。

检验理解改善尾部 store 合并可能有什么效果？

减少请求和排空压力，从而缩短尾部；须用时间验证。

ONE VARIABLE, ONE HYPOTHESIS

独立链数量扫描（实验设计，尚未执行）

只改变

固定工作集与有效读取总量，将每线程独立 pointer chain 从 1 增至 2、4、8；保持每条链自身依赖。

预计现象

并发不足时吞吐上升；资源饱和后时间改善趋缓，可能出现队列压力。

记录什么

CUDA event、SASS、寄存器数/occupancy、L1/L2/DRAM 流量、eligible warp 及 long_scoreboard/lg_throttle。

排除干扰

增加独立链会增加寄存器和地址计算，可能降低驻留；编译器删除、缓存复用和分区分布也会改变结果。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
