H06 / DEPENDENCIES · BEFORE ISSUE

依赖跟踪与 SASS 控制

寄存器名已经出现，为什么下一条指令还不能发射？

把数据相关、依赖跟踪与指令控制信息分开：正确性决定什么必须等待，实现决定怎样等待。

01

H06.01

RAW 依赖

#

RAW 为什么是“等正确版本的数据”？

最小状态
生产者目标、消费者源、待写寄存器集合。
变化规则
目标预留后，消费者只有在完成事件释放目标后才通过 RAW 检查。

RAW（read after write）表示后面的指令要读取前面指令产生的值。依赖不来自两个操作时间接近，而来自它们使用同一个数据版本。只要生产者结果尚不可用，消费者即使获得计算单元，也不能拿寄存器里的旧值继续执行。

在教学 scoreboard 中，发射生产者时预留目标寄存器；检查后续指令时，将其源寄存器与待写集合求交。相交就等待，不相交只说明通过这一道检查，还需要取指、资源及仲裁条件。真实 SASS 可以通过不同控制机制表达相同正确性约束。

具体例子

A：R4=load[p]；B：R8=R4+1。A 已发射不代表 R4 已更新，B 必须等返回后的新值。

先预测把独立指令放在消费指令之前，可能利用等待窗口。

容易混淆

把 RAW 等同于 long_scoreboard；依赖类别还取决于生产者所在路径。

检验理解A 的目标是 R4，B 只读 R7，B 一定能立即发射吗？

不一定；只排除了这条 RAW，还可能有其他依赖或资源限制。

H06.02

WAW 依赖

#

顺序发射为什么仍要处理 WAW？

最小状态
两条指令的目标寄存器及各自完成时刻。
变化规则
若候选目标与待写集合相交，该模型阻止第二次写的发射。

WAW（write after write）发生于两条指令写同一寄存器，而程序要求最终保留后面那次写入。顺序发射并不自动保证顺序完成：如果早发射的操作很慢，晚发射的操作很快，前者可能在后者之后覆盖寄存器，破坏结果。

Accel-Sim 的这一 scoreboard 模型把候选指令的输出也纳入冲突检查：目标已被未完成指令预留时，不允许再次预留。它用等待保持写入顺序，而不是在这里模拟 CPU 式寄存器重命名。真实芯片是否以及怎样消除名字相关，需要独立证据。

具体例子

A：慢 load 写 R2；B：把常量写 R2。若 B 先完成、A 后覆盖，最终 R2 会错误地变成 load 的值。

先预测将互不相关的输出分配到不同名字，可减少名字冲突，但可能增加寄存器数。

容易混淆

认为只要没有读旧值，就可以忽略两次写入顺序。

检验理解把 B 的目标改成 R3，消除的是哪类约束？

消除了 R2 上的 WAW；不自动消除 B 的输入依赖。

03

H06.03

WAR 风险与操作数读取时刻

#

WAR 风险取决于发射顺序，还是实际读数时刻？

最小状态
输入寄存器、读操作的锁存状态、后续覆盖操作。
变化规则
当输入仍会被读取时阻止覆盖；锁存或读取完成后才能释放保护。

WAR（write after read）要求后面的写不能破坏前面尚未取得的输入。关键事件是“操作数已被安全读取或保存”，不是仅看指令是否发射。若一个较早操作在后续阶段才使用寄存器内容，那么之后过早覆写就可能改变它原本应该读到的数据。

所引用的模拟器 scoreboard 注释明确不在该处处理 WAR，并以顺序发射解释模型假设；不能据此断言 NVIDIA 没有 WAR 控制。Volta 逆向论文描述了读依赖 barrier，用于保护某些操作所需输入，直到可以安全覆写。这与等待结果的 RAW 是不同方向。

具体例子

store [p]=R6 已发射，但假设尚未锁存 R6；接着 R6=0。若不保护读者，存出的可能是 0 而非原值。

先预测保持输入版本独立，比仅调整发射间隔更容易明确正确性。

容易混淆

把“前一条已经发射”当作“所有输入都已读取完成”。

检验理解如果 store 已把 R6 完整锁存到内部缓冲，后写还威胁这次读吗？

就该输入的 WAR 而言不再威胁，但内存顺序仍是另一件事。

H06.04

模拟器 scoreboard 的预留和释放

#

scoreboard 的预留和释放分别对应什么？

最小状态
按 warp 索引的 pending 集合和候选指令寄存器集合。
变化规则
预留加入、完成删除；交集非空则该候选不能越过依赖检查。

在已核对的源码里，每个 warp 有一个待写寄存器集合。reserveRegisters 遍历指令输出并插入，releaseRegisters 遍历输出并删除；checkCollision 则查询下一条指令使用的输入、输出、谓词及地址相关寄存器是否碰到这些项。集合表达的是尚未完成的写责任。

这个最小模型便于把等待原因画出来：寄存器存在于集合中，表示不能消费或再次写入；集合为空不表示 warp 必然能发射。还要沿 shader 的调用路径确认何时预留、何时释放，以及访存返回如何触发完成，不能仅凭函数名把释放时刻想成固定周期。

具体例子

W0 的集合是 {R4}，W1 的集合为空；两个 warp 都有名为 R4 的寄存器，但不是同一份线程状态。

先预测打印每次集合变化，可以定位漏释放、提前消费或重复预留。

容易混淆

把每 warp 的寄存器名集合当作整个 SM 的全局名字表。

检验理解为什么 W0 写 R4 不应直接阻止 W1 读自己的 R4？

寄存器状态按 warp/线程上下文区分，名字相同不等于存储对象相同。

H06.05

固定延迟指令的 stall 控制

#

固定延迟的等待为什么可以写进指令控制信息？

最小状态
生产者完成时刻、下一条允许发射时刻、独立指令位置。
变化规则
静态间隔必须覆盖依赖所需时间；中间独立操作并不消费未就绪值。

如果某类操作在指定条件下有已知的依赖间隔，编译器就能把消费者排到足够晚的位置，或使用机器指令控制信息保留必要间隔。这样做解决的是何时允许依赖指令继续，而不是声明运算单元在这段时间不能接收其他独立工作。

Volta 的逆向研究讨论了 SASS stall 控制字段；这里把它作为静态时序约束的例子，而不把具体位宽、数值与新架构对应。验证时要查看针对目标 SM 生成的最终 SASS、独立指令位置和正确性。CUDA 源码中的两行相邻，不保证机器码中也相邻。

具体例子

教学模型中 FMA 在 c0 发射、c4 可用；消费者不能在 c3 使用结果，但 c1-c3 可以安排其他允许发射的独立工作。

先预测同等 FMA 数量下，多条独立链通常比单链更能暴露吞吐能力。

容易混淆

把“依赖间隔 4 周期”误读成“整条流水线每 4 周期才能接一条”。

检验理解独立 FMA 能在前一条尚未完成时开始吗？

可以，前提是发射和管线接收能力允许。

H06.06

可变延迟操作的依赖 barrier

#

可变延迟为什么不能只靠一个固定等待数？

最小状态
跟踪项、在途生产操作、等待该项的消费者。
变化规则
生产操作完成才解除对应依赖，消费者不能靠平均时间猜测。

load 的完成时间可能随缓存命中、队列压力和数据路径变化。固定等得太短会读错，按最坏情况固定等又会浪费常见情况。因此实现需要某种完成跟踪，让后续消费者依赖“结果实际就绪”这个事件，而不只依赖时间流逝。

Volta 逆向论文把相关 SASS 信息解释为依赖 barrier：生产操作关联跟踪项，后续指令声明等待关系。这里的 barrier 属于指令依赖控制，不等于 __syncthreads 的线程集合 rendezvous，也不是自动提供跨线程内存发布的 fence。三者不能互换名称和语义。

具体例子

同一 load 在一次实验中命中 L1，在另一次中走到下层；消费者都必须正确，但允许开始的时刻可以不同。

先预测增加数据就绪前的独立工作，可能隐藏部分可变等待。

容易混淆

把 SASS dependency barrier 当成 CTA 同步屏障，推导出其他 warp 也已到达。

检验理解结果未到但已经等过一个经验平均延迟，可以开始消费吗？

不可以，平均延迟不是本次操作的完成证明。

H06.07

wait mask 如何等待生产者

#

wait mask 为什么是集合，而不是单个生产者编号？

最小状态
pending 位集与每条消费者的 wait 位集。
变化规则
仅当 pending & wait = 0 才通过这项依赖检查。

一条消费者可能同时需要多份结果，例如地址来自一个 load，而乘数来自另一个 load。若只有一个等待编号，就不能表达“这两个依赖都已满足”。位掩码是一种紧凑集合：每个位对应一个被跟踪的条件，消费者要求其选择的条件全部解除。

在教学模型中，pending mask 代表仍未完成的生产者，wait mask 代表消费者真正需要的生产者；两者按位与为零，才通过这项检查。这个模型解释集合关系，不承诺真实机器使用相同位数、分配策略或复用规则。屏障编号复用也不能提前让旧依赖失去身份。

具体例子

pending=0110，消费者 wait=0010 时仍等待；当第 1 位清除后，即使第 2 位尚未完成，这个消费者也可通过。

先预测等待集合越精确，不相关的长操作越不容易拖住消费者。

容易混淆

认为一个被跟踪操作完成就释放所有等待，或把 mask 当成单个整数编号。

检验理解wait=0101 时，只清除位 0 够吗？

不够，只要位 2 仍 pending，交集就不为零。

H06.08

yield 控制信息

#

yield 信息是在保证换 warp 吗？

最小状态
可发射候选集合、当前 warp、调度控制提示。
变化规则
先筛选合法候选，再讨论提示对选择的影响。

yield 控制信息影响调度倾向，但不能替代候选 warp 的就绪条件。另一个 warp 如果在等数据、同步或执行入口，即使当前指令提示让出，调度器也不能凭空制造一个可发射候选。因此，应把“偏好谁”与“谁有资格”分成两层分析。

Volta 逆向论文报告了 yield 与后续发射选择、操作数复用之间的关系。这属于特定二进制和微架构观察，不是 CUDA 程序可依赖的公平性协议。不要用它实现跨 warp 同步，也不要根据单个字段推断一个跨代固定的切换周期或通用调度策略。

具体例子

候选集合只有 W0 时，让出提示无法使正在等 load 的 W1 提前执行；有 W0/W1 两个候选时才出现选择空间。

先预测当没有其他候选时，修改选择偏好很可能没有收益。

容易混淆

把 yield 解释为强制公平调度，进而假设某个自旋 warp 必定及时得到运行。

检验理解yield 能解除另一个 warp 的 RAW 依赖吗？

不能。它影响选择倾向，不能改变数据是否就绪。

H06.09

wait、long_scoreboard、short_scoreboard 的区别

#

wait、long_scoreboard、short_scoreboard 应如何区分？

最小状态
消费者 PC、生产者路径、采样类别及同期 issue 活跃度。
变化规则
从消费位置反向追溯生产者，再用路径计数器检验具体假设。

先找到采样落在哪条 SASS，再沿数据来源寻找生产者。wait 对应固定延迟执行依赖；long_scoreboard 关联 L1TEX 路径结果；short_scoreboard 关联非 L1TEX 的 MIO 结果。名称中的 long/short 是工具分类，不是本次等待时间超过某阈值的判断。

同样的“下一条用不到数据”，可能由不同路径造成；相反，同一类别下也可能有不同根因。PC 样本不是全芯片统一停工时长，其他 warp 仍可能填满发射槽。优化应同时检查 issue 活跃度、相关管线或访存表现及端到端时间，而非只追求某项占比归零。

具体例子

ADD 消费 global load 的 R4 时出现 long_scoreboard，热点可能显示在 ADD；问题源头却可能是前面的访存模式。

先预测只有等待阻碍有效发射或关键路径时，减少它才更可能带来加速。

容易混淆

看到 short_scoreboard 就认定 bank conflict，看到 long_scoreboard 就认定 DRAM 带宽满。

检验理解等待样本减少但运行时间不变，可能正常吗？

正常；原先等待可能已被其他 warp 隐藏，或瓶颈位于别处。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

smsp__pcsamp_warps_issue_stalled_wait

SMSP 上被采样 warp 的固定延迟执行依赖等待。独立计算填充依赖间隔后，等待占比可能下降。

这是 PC 采样计数，不是全 SM 丢失周期；需同时检查 SASS、issue 活跃度与总时间。先用 ncu --query-metrics 核对。

[3]

smsp__pcsamp_warps_issue_stalled_long_scoreboard

等待 L1TEX 路径操作的结果；样本通常归在消费该结果的指令上。

不是“所有长延迟指令”，也不能单凭它证明 HBM 带宽饱和。

[3]

smsp__pcsamp_warps_issue_stalled_short_scoreboard

等待非 L1TEX 的 MIO 操作结果，可涉及 shared、特殊数学或动态分支。

不能直接解释成 shared bank conflict；需结合对应源指令和 Memory Workload Analysis。

[3]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

只改变

编写同等数量的 FP32 FMA：版本 A 只更新一个累加器，版本 B 在程序顺序中轮换多个独立累加器。

预计现象

若主要瓶颈是固定执行依赖，B 可增加可发射指令；达到管线吞吐上限后，继续增加独立链不再等比例提速。

记录什么

先反汇编确认链结构与指令数量，再记录时间、寄存器占用、NCU wait 采样和对应 pipeline 吞吐；对具体 GPU 执行 ncu --query-metrics 与 ncu --list-sections。

排除干扰

更多累加器增加寄存器需求，可能改变 occupancy；编译器可重排或消除计算；测量时固定工作量并保留最终输出。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
