01

H02.01

一个线程有哪些独立状态

#

同一 warp 的线程为什么还能保存不同变量和走不同分支？

最小状态
每线程寄存器、逻辑 PC、谓词与所属 warp。
变化规则
一次 SIMT 指令仅更新本次参与线程各自的状态。

每个 CUDA 线程有自己的寄存器值、线程索引和逻辑执行状态。SIMT 把适合一起推进的线程组成指令组，减少重复控制开销；共享指令不代表共享数据。两个 lane 使用同名寄存器时，通常读取的是各自线程的寄存器实例。

Volta 及之后的 Independent Thread Scheduling 维护每线程 PC 和调用栈，能够在子 warp 粒度分歧与汇合；更早架构用共享 warp PC 与 active mask 管理执行。程序的线程语义与某一代硬件控制状态的实现要分开，不能把所有 GPU 都画成32个独立 CPU。

具体例子

lane0 中 x=3、lane1 中 x=7；同一加法指令 x+=1 后分别得到4和8。若条件 x>5，两者也可以进入不同路径。

先预测同一指令可产生不同数据结果，分支条件也可因线程而异。

容易混淆

“同一条指令”意味着32线程拥有同一个寄存器值。

检验理解线程有独立 PC 是否表示32条不同指令可在同一周期发射？

不是。独立执行状态不取消 SIMT 分组、发射及执行资源限制。

H02.02

warp 指令与参与线程的关系

#

一条 warp 指令的32个 lane 是否一定都做有效工作？

最小状态
一条动态指令、32位参与集合与每线程谓词。
变化规则
指令发射后，仅 active 且谓词为真的线程提交该指令效果。

warp 是由连续线程编号组成的32线程逻辑组，但一次动态指令可以只有一部分线程参与。退出、控制流分歧及 block 尾部都会减少活动线程；指令本身的谓词还可能进一步关闭其中的结果更新。

分析时分别统计 warp 指令次数与实际线程指令次数。同样发射100条 warp 指令，平均8个线程做有效工作与32个线程做有效工作，对有用算术的贡献差四倍。不要据此自动推断时间差四倍，因为发射成本、指令类型和执行管线粒度仍可能相同。

具体例子

一个 warp 每次只让 lane0 执行加法，仍需要发射对应 warp 指令；它不能自动把剩下31个槽装入其他 warp 的线程。

先预测减少参与线程可降低有效工作，未必同比减少发射次数。

容易混淆

把 warp 指令数乘32，无条件当作有效标量计算量。

检验理解平均 pred-on 线程数为8，warp occupancy却很高，是否矛盾？

不矛盾。前者描述指令参与度，后者描述驻留 warp 数，分母不同。

H02.03

active mask 如何改变执行

#

active mask 记录的是“哪些线程”，还是“哪些硬件核”？

最小状态
固定 warp 身份、当前路径和参与 mask。
变化规则
控制流切换时更新参与集合；同步参与集合必须遵守相应 API 契约。

active mask 是针对逻辑 lane 的集合。某条路径执行时，它决定哪些线程参与当前动态指令；另一路线程的状态保留，待其路径被执行。mask 随控制流变化，并不是一张固定的物理 ALU 开关图。

编写 warp collective 时还要区分“此刻活动的线程”与“必须参与这次协作的线程”。__activemask() 给出当前执行位置的活动快照；它不自动定义完整参与协议。参与 mask 应从算法条件与合法同步流程推导，尤其不能把分支内部偶然同批到达当成同步保证。

具体例子

若预期 lane0–15 交换数据，参与集合应预先按条件构造，并确保这些未退出线程执行同一 collective；不能假定当前快照总是0x0000ffff。

先预测分支使 mask 变稀疏，但不会把空 lane 交给其他 warp。

容易混淆

用 __activemask() 替代同步，认为看到了同一 mask 就保证读写已经可见。

检验理解两个时刻的 active mask 不同，会改变线程的 warp 归属吗？

不会。mask 描述当前参与集合，warp 身份仍由线程分组决定。

H02.04

逻辑 lane 与物理执行宽度

#

32-thread warp 为什么不能直接等同于32个 ALU？

最小状态
逻辑32 lane、指令类型、物理处理宽度和流水阶段。
变化规则
按该管线实际宽度处理 lane 工作，并在规定接收间隔接纳后续指令。

warp 宽度描述逻辑并行组，物理执行宽度描述特定数据类型与管线每周期能处理多少 lane 工作。一次 warp 指令可能分多拍完成 lane 处理；多个指令也可能在管线中重叠，因此“几拍覆盖所有 lane”和“多久可发下一条”仍是不同量。

以官方 Volta 调度说明为例，相关算术指令的执行跨两周期，而 scheduler 可每周期发射独立指令。这是特定架构和操作类型的说明，不能外推到 FP64、MUFU、Tensor 或所有后继架构。讨论吞吐前必须写出 SM、SMSP、warp 和 scalar operation 的单位。

具体例子

教学模型每拍处理16个 lane，32-lane 指令需要两个 lane 批次；若内部流水化，下一条独立指令不一定必须等前一条结果完成。

先预测改变指令类型可能改变吞吐，即使 warp 数和mask完全相同。

容易混淆

把32线程 warp 推导成32结果在同一时钟完成。

检验理解warp size不变，FP64和FP32吞吐是否应相同？

不应。逻辑分组相同，但相应执行资源数量和速率可不同。

H02.05

CTA、warp、SM 的归属关系

#

一个 block 能否把自己的 warp 分到不同 SM 上？

最小状态
block 身份、其 warp 集合、SM 归属和块内共享资源。
变化规则
block 分配到SM后，其warp在该SM资源约束下各自推进。

通常的 CUDA thread block，也叫 CTA，是 SM 驻留与块内协作的基本单位。它的线程划为 warp，所有 warp 在同一 SM 上执行，从而共享该 block 的 shared memory 和块内 barrier。多个 block 可以同时驻留一个 SM，彼此保留独立的资源和同步状态。

warp 分配到 SM 内的调度子分区后，由相应 scheduler 推进；这种分配不意味着它脱离所属 block。Hopper 的 thread block cluster 进一步协调多个 block，它也不会把一个普通 block 拆成跨 SM 的几个 warp。理解层次有助于判断共享资源和同步范围。

具体例子

一个256线程 block有8个warp。它们可分给同一SM内不同scheduler，但并非各自任选8个SM。

先预测增大block会增加同一SM内的warp需求，而不会自动跨SM分摊。

容易混淆

把 thread block cluster 与跨 SM 拆分单个 CTA 混为一谈。

检验理解两个 block 恰好在同一 SM，能直接使用彼此的普通 shared memory 吗？

不能。普通 shared memory 的作用域和分配属于各自 block；DSM 是另一个显式机制。

H02.06

SM 子分区及资源共享边界

#

为什么同一 SM 内也可能出现一边忙、一边闲？

最小状态
scheduler归属、各SMSP候选集合及SM级共享资源。
变化规则
只在本scheduler拥有的warp中判定就绪和仲裁。

SM 不是所有资源都完全可互换的大池子。以 Volta 为例，四个 scheduler 各管理静态的一组 warp，并发射到其算术执行资源；NCU 用 SMSP 表达子分区作用域。shared memory 和部分缓存路径又在更高层共享，局部空闲与共享瓶颈可以同时出现。

因此要区分每个 SMSP 的可发射 warp 数、专用资源及共享资源。整 SM 平均有很多 warp，并不能证明每个 scheduler 都拥有足够 eligible warp。模拟器的 sub-core 配置有助于观察这一点，但其具体队列及 operand collector 划分仍是建模选择。

具体例子

教学SM有4个scheduler，各持有2个warp；若只有S0的两个warp就绪，其他scheduler不能在静态归属模型中直接抢走它们发射。

先预测相同总warp数，不同分区分布可能产生不同空泡。

容易混淆

把一个 SM 内所有 resident warp 视为任意 scheduler 随时可选的统一队列。

检验理解全SM平均 eligible=4，是否保证4个scheduler都能发射？

不保证。四个eligible可能集中在同一个子分区；还需要资源可用。

H02.07

block 到 SM 的分配

#

CUDA 是否保证 block 0 先运行、block 1 随后运行？

最小状态
待执行block队列、各SM剩余资源、已驻留block。
变化规则
有容量时接纳工作；完成后释放资源以允许后续block进入。

普通 grid 中的 block 分配顺序不是程序可依赖的正确性契约。硬件根据可用执行容量安排工作；只有资源充足的 SM 才能接纳新 block。没有任何要求说相邻 block ID 必须落到相邻 SM，也没有要求按 ID 顺序完成。

算法应让 block 独立完成工作，或使用合法的跨 block 协作机制。用全局标志自旋等待一个尚未被安排的 block，可能因所有驻留槽都被等待者占据而无法前进。把数据布局优化建立在猜测的 block-to-SM 映射上，也会导致跨设备表现不稳。

具体例子

教学SM只能驻留2个block；若B1、B2占满位置并等待尚未运行的B0，程序进展便依赖未获保证的调度。

先预测在不依赖顺序的正确程序里，改变block完成顺序不应改变结果。

容易混淆

拿一次日志中观察到的映射顺序，当作永久不变的硬件规则。

检验理解是否可以通过 blockIdx 直接推断物理 SM 编号？

不能。blockIdx是逻辑工作编号，SM分配是运行时安排。

H02.08

TPC / GPC 在整卡层次中的位置

#

TPC/GPC 在整卡结构里有什么用，是否等同 CUDA cluster？

最小状态
芯片层次、资源共享边界和指标单位。
变化规则
请求经过所属局部单元及共享路径；硬件层次并不自动成为软件索引。

GPC 和 TPC 是芯片组织层次，帮助理解 SM 之外的共享资源与请求路径。NCU 的硬件术语把 TPC 放在 GPC 内，TPC包含一个或多个SM及相关单元；GPC在整卡上重复。具体数量、缓存组织和图形功能随芯片型号变化。

CUDA thread block cluster 则是一个软件协作和调度概念，不应与这些缩写直接一一对应。阅读架构图时，先区分“物理包含关系”和“API可控制的合作范围”。指标名中的gpc、tpc、sm、smsp还提示不同聚合边界，整卡平均会隐藏局部竞争。

具体例子

某份架构图展示 GPC→TPC→SM，而程序只有 grid/block/thread 索引。这并不说明应用能通过这些索引指定某个TPC。

先预测局部共享路径饱和时，增加同一范围内SM工作不一定线性增加吞吐。

容易混淆

把一个GPC的SM数量当成CUDA cluster的固定大小。

检验理解看到 tpc 作用域的计数，能当作一个SM的计数吗？

不能。先确认该芯片TPC包含的资源与指标聚合方式。

如何在工具里观察？

ncu --list-sections
ncu --query-metrics

smsp__thread_inst_executed_per_inst_executed.ratio

每条warp指令的平均线程参与度，稀疏活动mask可能使它下降。

作用域为SMSP聚合；它不是occupancy，也不直接表示FLOPS利用率。

smsp__thread_inst_executed_pred_on_per_inst_executed.ratio

进一步统计谓词为真的线程参与度，用于区分活动线程与有效执行。

需结合SASS、指令类型和动态计数；完整设备支持用 --query-metrics 查询。

[6]

WorkloadDistribution

观察SM/SMSP之间工作分配差异，检查平均值是否掩盖偏斜。

section并不提供任意block固定映射的API契约。

[4]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

实验设计：保持工作量，改变 warp 内分支分布（未执行）

只改变

比较按warp分组的条件与同一warp内交错的条件；保持总有效计算、输入与block配置一致。

预计现象

warp内交错路径可能降低每条动态warp指令的有效线程数；不同warp各走单一路径则不构成warp内发散。

记录什么

先看SASS是否编译成branch或predication，再看SourceCounters、线程参与比和普通运行时间。

排除干扰

分支两侧工作量、编译器谓词化、寄存器数变化、负载不均与缓存访问变化。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
