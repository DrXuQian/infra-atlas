01

H16.01

atomic read-modify-write 的逻辑过程

#

atomic read-modify-write 的“不可分割”到底保证了什么？

最小状态
X、两个增量、操作类型与scope。
变化规则
每次合法原子操作把X从old转换为f(old)，并按接口返回old。

对于同一地址和相容作用域内的竞争访问，一次原子读改写在逻辑上整体生效：它取得旧值、计算更新、写回新值，其他参与者不能观察到一半更新。硬件并不需要把这三步暴露成三条普通load、add、store。

原子性只覆盖规定的数据宽度和操作对象。传统atomicAdd默认是relaxed顺序，不能单靠计数器自增就发布其他地址的数据。先确定类型、对齐、地址空间和scope，再讨论是否满足算法的同步需求。

具体例子

X=10，A执行atomicAdd(X,3)，B执行atomicAdd(X,2)。最终X=15；若A先发生，A取得10、B取得13。

先预测整数加法无溢出时总和可预测，返回旧值的分配顺序未必可预测。

容易混淆

把“计数器更新不会丢”误解为“此前所有普通store已对其他线程可见”。

检验理解两个线程用普通load/add/store加1，为什么可能只增加1？

它们可能都读到同一旧值，然后都写出旧值+1；缺少原子读改写的整体生效。

H16.02

多线程竞争同一地址

#

32 个线程同时加同一地址，为什么不等于32路独立计算？

最小状态
一个热点地址、竞争请求数、返回值依赖。
变化规则
同地址更新按某个合法序列生效，后续请求不能跳过前序状态变化。

不同线程的原子操作即使同时到达，也需要在该地址上形成相容的更新序列。它们竞争的是同一个存储状态，而不是32份互不相关的数据；增加warp只会增加排队来源，不能消除这个依赖。

串行化的范围不能直接扩大为“所有原子操作全局串行”。不同地址可以利用不同内部资源并行推进；同地址吞吐还受类型、是否返回值和请求合并等因素影响。只有观测具体工作负载，才能给出更新率。

具体例子

32个lane各加1到X，逻辑最终增加32。若每个lane下一条指令要用自己的old值，它还额外等待返回路径。

先预测竞争加重时，总请求数增加而单位时间有效更新数可能趋于平台。

容易混淆

用HBM总带宽预测热点计数器的最大更新率。

检验理解加倍线程数而更新率不变，是否说明GPU没有执行新增线程？

不说明。新增线程可能只是加入同一热点地址的等待队列。

03

H16.03

地址分布如何影响竞争

#

“分散到更多地址”一定能让原子操作更快吗？

最小状态
bin数、请求到bin的映射、缓存工作集。
变化规则
地址分片减少每个状态变量上的更新链，同时改变请求经过的共享资源。

把更新从一个bin分散到多个bin，减少了每个地址上的逻辑冲突，但请求仍共享LSU、cache、L2分区或shared原子资源。并行地址数只是可扩展性的条件之一，不是可实现带宽的直接公式。

地址分布还会改变局部性。极度分散的global更新可能触及更多cache line和sector，降低复用；shared直方图也可能遇到bank相关限制。因此应同时观察竞争程度、事务量和总耗时，寻找合适的分片粒度。

具体例子

比较同样一百万次更新落到1、32、4096个bin：前者热点强，后者竞争少，但工作集和访存流量也不同。

先预测增加bin数最初可能提高吞吐，随后被其他资源或流量限制。

容易混淆

把不同地址等同于不同物理原子执行单元。

检验理解两个版本原子请求数相同，运行时间为什么可能不同？

地址热点、局部性和资源分布不同，排队与服务成本就不同。

H16.04

shared 与 global atomic 的执行路径

#

shared atomic 与 global atomic 为什么不能只用“延迟大小”区分？

最小状态
两个地址空间、局部直方图和全局归并缓冲。
变化规则
将跨block竞争改为block内更新，再执行受控的全局合并。

shared atomic更新CTA共享的片上存储；global atomic面向全局地址，NCU硬件模型在L2侧描述了global原子执行资源。它们具有不同的地址空间、共享范围和可竞争资源，不能当作同一条路径只换个缓存命中率。

把全局直方图改成每个block一份shared直方图，会减少跨block热点，但新增初始化、CTA同步和最终global归并。速度取决于整个算法；shared容量和block驻留也会参与取舍，而不是shared版本天然更快。

具体例子

每个block先在shared里统计256个bin，再由有限线程归并到global；输入很小时，初始化和归并可能超过节省的原子成本。

先预测大输入高热点可能受益，小输入或大bin初始化成本可能抵消收益。

容易混淆

把shared atomic的block内原子性当成跨block共享同一个对象。

检验理解shared中累加正确，为什么最终global结果仍可能错？

可能缺少初始化/消费同步，或最终归并不是正确的原子/分区写回。

H16.05

返回旧值与不需要返回值的区别

#

不使用 atomicAdd 返回值，硬件是否还必须送回旧值？

最小状态
原子目标、旧值是否被消费、后续依赖。
变化规则
旧值不可观察时可选择无返回语义；需要旧值时必须保留结果路径。

PTX把带目标寄存器的atom与不返回旧值的red分开描述。若程序只关心更新结果、不消费旧值，编译器可能选择不返回结果的归约路径，从而减少返回数据和寄存器依赖；最终选择必须查看SASS。

这种变化不取消同地址更新的原子性，也不保证没有排队。反之，若旧值用来为输出分配唯一索引，就不能随意丢弃返回值。比较性能时要固定算法语义，否则测到的是不同工作而不是纯指令优化。

具体例子

计数counter+=1可以不需要old；压缩输出的pos=atomicAdd(counter,1)必须返回old给后续store使用。

先预测取消不必要的返回值可能降低依赖压力，但不会消除热点。

容易混淆

把源码里没有赋值的atomicAdd直接认定为某个固定RED opcode。

检验理解返回值未使用的版本更快，能否据此推断原子执行本身变快？

不能。差异可能来自返回路径、依赖链或编译器优化，需要反汇编和计数器佐证。

H16.06

CAS 重试

#

CAS 循环为什么会在竞争下做很多“无效工作”？

最小状态
expected、desired、内存当前值与成功标志。
变化规则
匹配则原子替换；不匹配则读回当前值并重新计算。

compare-and-swap仅在内存值等于预期值时写入新值，并返回比较时的旧值。线程根据观测值计算候选更新；若别的线程先修改对象，本次CAS失败，必须从返回的新观测值重新计算，再尝试。

一次算法更新可能对应多次CAS请求，因此应分开统计成功更新数和尝试次数。浮点实现还要处理NaN等表示问题；官方double atomicAdd示例用整数位表示比较，避免NaN不等于自身导致错误的循环判断。

具体例子

A、B都观察X=5并拟写6；A成功后X=6，B的expected=5失败，读回6后重算7，再成功。

先预测热点竞争增加时，尝试/成功比可能上升，吞吐未必随线程数增加。

容易混淆

CAS失败后直接重试旧的desired值，或用浮点NaN相等性判断是否成功。

检验理解成功更新100次却执行1000次CAS，意味着什么？

平均每次成功更新消耗10次尝试，竞争和重试流量显著。

H16.07

warp 聚合如何减少原子请求

#

warp 聚合怎样把32次原子更新变成更少的请求？

最小状态
参与掩码、同地址子组、总增量、组内rank。
变化规则
leader提交总更新，广播旧基址，组员用基址加前缀偏移。

先在参与线程中识别相同目标，计算总增量并选出leader，由leader执行一次原子操作，再把返回基址广播给组员。若需要每个线程自己的输出位置，还要根据组内前缀和构造独占区间，不能所有lane都用同一个old。

最多32倍减少只适用于一个完整warp都更新同一对象的理想请求计数。地址分组、shuffle、投票和掩码管理也有成本；分支中的参与集合必须一致。编译器可能已自动聚合，应先检查SASS再比较手写版本。

具体例子

5个活跃lane各申请1个位置：leader加5，返回base=40；按组内rank分别写40至44。

先预测同warp同地址比例越高，聚合越可能减少请求，但总耗时仍含组内协作。

容易混淆

把warp聚合解释成所有线程自动向任意不同地址合并为一次原子。

检验理解只有两个lane更新同一bin，理论原子请求最多减少几倍？

对这两个更新可由2次减到1次；其余不同bin还需要各自处理。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

MemoryWorkloadAnalysis（section）

比较 global/shared 的 atomic 与 reduction 请求及相应吞吐；聚合有效时，相同逻辑更新量对应的硬件原子请求应减少。

计数口径随 GPU 和 NCU 版本变化；先 ncu --list-sections 与 --query-metrics。请求减少不保证耗时同比下降。

[5]

SourceCounters（section）

定位实际执行的原子/归约 SASS 与返回结果的依赖使用点，检查编译器是否已做聚合。

PTX atom 不保证最终 SASS opcode 一一对应；不要仅看源码中 atomicAdd 的调用次数。

[5]

NCU 的 SM / SMSP、sum / avg、active / elapsed 与采样口径不可混用。若文档或设备没有公开对应计数器，就通过受控对照约束解释，不把间接变化写成硬件内部的直接读数。

ONE VARIABLE, ONE HYPOTHESIS

地址竞争与聚合对照（实验设计，未执行）

只改变

保持总更新次数、数据类型、grid和输入不变；分别更新单个bin、均匀分布bin，以及warp内按相同地址聚合。

预计现象

热点减少通常缓解同地址串行化；聚合收益应随同warp同地址更新比例变化，而非固定32倍。

记录什么

先验证所有bin总和；检查SASS和原子/归约请求，再用未被profiling扰动的CUDA event计时比较吞吐。

排除干扰

编译器自动聚合、shared初始化/归并成本、bin缓存局部性、返回值被优化掉、整数溢出及浮点求和次序。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
