01

H03.01

block 进入 SM 需要哪些资源

#

SM 还有空闲算力，为什么新 block 仍进不来？

最小状态
每block资源需求与SM各类可分配容量。
变化规则
所有资源约束都满足才准入；block结束后释放其保留资源。

block 的准入要同时满足多个容量约束：寄存器、shared memory、线程/warp数量以及block槽位。它们不是可以相互替代的资源。仅有空闲ALU不够；如果block所需的任一资源无法完整分配，通常就必须等待先前block结束释放。

可把理论驻留数理解为各类约束允许的block数的最小值，但真实计算还要包含分配粒度、分区和架构保留开销。应使用目标GPU的occupancy API或NCU计算器，而不是把所有芯片都套进同一组容量。此处先讨论普通block，不含cluster等额外协作限制。

具体例子

教学SM有64KiB shared memory，每block需24KiB；即使寄存器可放8个block，也只能同时放2个，剩余16KiB不足以接纳第三个。

先预测只优化非限制资源，理论驻留数可能完全不变。

容易混淆

认为只要计算利用率低，硬件就能无条件再塞更多block。

检验理解当shared memory已成为限制，减少一点寄存器一定提高驻留数吗？

不一定。若最小值仍由shared memory决定，驻留数不变。

H03.02

寄存器容量如何限制驻留

#

为什么每线程只多用几个寄存器，会影响整个 block 的驻留？

最小状态
RF容量、编译后每线程寄存器数、block大小及spill。
变化规则
资源分配按编译后的需求和架构粒度执行，超过容量则限制新block准入。

线程本地寄存器值需要片上存储，多个驻留warp共同消耗有限RF容量。一个block的粗略寄存器需求随线程数与每线程寄存器数增加，但最终分配必须按硬件粒度计算，而非简单把源码变量数相乘。编译器还可能复用寄存器或将值溢出到local memory。

降低每线程寄存器数有机会增加驻留block，却可能引入spill、额外指令或更少ILP。因此“寄存器越少越好”不是目标；正确目标是有效工作耗时更低。先查看编译器资源报告，再用occupancy API定位是否跨过真正的容量台阶。

具体例子

简化为64K个32位寄存器、256线程/block且忽略粒度：64寄存器/线程需16K/block，寄存器约束最多允许4个block。

先预测跨过寄存器限制台阶可能提升驻留，但运行时间需独立测量。

容易混淆

把C++局部变量个数当成最终寄存器数，或忽略一个64位值可能占多个32位寄存器。

检验理解把寄存器上限压低后 occupancy增加却变慢，可能原因是什么？

spill流量、更多重计算或ILP下降可能大于新增驻留warp的收益。

03

H03.03

寄存器分配粒度造成的台阶

#

资源分配为什么会形成台阶，而不是平滑变化？

最小状态
逻辑需求、分配粒度、向上取整后的allocated需求。
变化规则
每个分配单位向上取整，再检查block/SM可容纳数量。

硬件以一定粒度分配寄存器，需求通常要向上取整。多出来的几个逻辑寄存器可能使整个warp增加一个分配块；累积到block或SM后，原本能容纳的最后一个block就被挤出去。这正是寄存器压力常出现突变而非平滑变化的原因。

CC7.0的官方示例采用每warp256个寄存器的分配粒度，不能不加验证地用于全部架构。资源计算还需处理每block上限与子分区限制。优化时观察“allocated”与逻辑用量的差异，并围绕真实台阶做小范围扫描。

具体例子

CC7.0粒度示意：32寄存器/线程时每warp需1024；33时逻辑需1056，但向上取整成1280。差1个/线程会增加256个/warp的分配。

先预测靠近边界的微小改动，可能造成驻留warp数的离散跃迁。

容易混淆

按65536除以线程数与逻辑寄存器数所得的小数直接预测驻留。

检验理解33降到32为什么可能比40降到39更有影响？

前者可能跨过分配粒度边界；后者可能仍落在同一分配档位。

04

H03.04

shared memory 如何限制驻留

#

shared memory 换来数据复用，为什么有时反而拖慢 kernel？

最小状态
SMEM有效容量、每block静态和动态分配、缓冲stage数量。
变化规则
block准入占用整份shared memory预算，完成后才释放给其他block。

shared memory常按block保留，用于复用tile、减少全局流量或交换线程间数据。增加tile或stage会增加每block占用，因而可能减少同时驻留的block和warp。算法获得的复用收益，与丢失的延迟隐藏能力需要放在一起计算。

可用SMEM容量还受设备、每block上限、动态shared memory配置及L1/SMEM carveout影响。给kernel保留更多shared memory，并不等于该kernel自动产生更多并行工作。应该联合记录全局流量、SMEM占用、理论驻留和最终时间，避免只盯一个数字。

具体例子

教学容量96KiB：每block从24KiB增至40KiB，SMEM约束的驻留数从4降为2；若流量并未相应减少，新增缓冲可能得不偿失。

先预测增加stage可能提升重叠，也可能因驻留下降使延迟更难隐藏。

容易混淆

只凭数据放在片上就断言更快，不计算驻留、同步和搬运代价。

检验理解双缓冲比单缓冲慢，先看哪些变化？

看SMEM是否跨驻留台阶，同时检查复制计算是否真的重叠、同步是否正确。

H03.05

thread / warp / block 数量上限

#

寄存器和 shared memory 都够，为什么 occupancy 仍上不去？

最小状态
block/warp/thread三种容量上限及每block需求。
变化规则
取所有独立上限允许的block数的最小值；不足一个完整block的剩余容量不能利用。

SM还有最大线程数、最大warp数和最大resident block数等独立上限。小block可能先用尽block槽位，却未用完线程容量；大block可能因线程上限或剩余空间碎片而无法再加入一个block。资源需求很小不意味着驻留数量没有上限。

先查询实际设备属性，再把每block的ceil(T/32)个warp带入约束。不要混淆每block最大线程数与每SM最大驻留线程数；超过前者可能launch非法，碰到后者只是限制同时驻留数。不同compute capability的上限应分别记录。

具体例子

教学SM最多8个block、32个warp。每block1个warp，即使其他资源无限，也只有8个resident warp，理论occupancy为25%。

先预测在block槽位限制时，适度增大block可能提高resident warp数量。

容易混淆

认为block越小，必然越容易填满SM。

检验理解64个线程的block有几个warp？能否忽略block槽位？

它有2个warp；block槽位仍然可能先成为限制。

H03.06

不满一个 warp 的线程块

#

一个33线程 block 为什么需要两个 warp？

最小状态
block线程数T、ceil(T/32)个warp及尾warp参与集合。
变化规则
最后一个warp中超出T的lane没有线程，不参与指令。

block按连续线程编号分成32线程的warp，因此warp数是ceil(T/32)。33个线程形成一个满warp和一个只有1个有效线程的尾warp。尾warp仍是调度与资源跟踪中的warp，不能与另一个block的尾线程拼成一个满warp。

它造成的影响至少包括发射时有效线程比例降低，以及按warp分配资源带来的浪费。occupancy以warp为单位时可能看起来并不低，但有效lane工作仍很少。小规模问题可以用每线程处理多个元素、把工作打包或选择更合适的block尺寸改善；仍需保留越界保护。

具体例子

33线程/block共2个warp，逻辑64个lane位置里只有33个线程；这与64线程/block的2个满warp并不具有相同有效工作量。

先预测T从32增至33会新增一个warp，资源需求可能出现台阶。

容易混淆

认为多个33线程block的尾warp会自动合并成一个满warp。

检验理解为什么高warp occupancy仍可能伴随低有效线程比？

驻留warp数把尾warp算在内，而每条指令实际参与的线程可能很少。

H03.07

theoretical 与 achieved occupancy

#

theoretical occupancy 与 achieved occupancy 各自说明什么？

最小状态
理论驻留上限、运行时各SM的resident warp数量和统计窗口。
变化规则
block进入/离开改变resident数量；是否eligible由另一套条件决定。

理论occupancy由launch配置和资源上限计算：在有足够工作且允许的条件下，每SM最多能驻留多少warp。achieved occupancy则根据运行时resident warp的统计得到，受到grid大小、启动与排空、block寿命不均以及执行阶段变化影响。

两者都不是有效算力利用率，也不等于eligible warp比例。很多resident warp可以同时等待同一批内存；少量warp也可能凭足够ILP填满某条管线。理论高但实际低时先排查供给和尾部；实际高却发射差时再看依赖、同步或资源throttle。

具体例子

某配置理论可放64个warp，但整个grid只有一个256线程block；最多只有8个warp被提供给某个SM，其他SM甚至没有工作。

先预测grid不足或长尾会拉低实际驻留，但资源计算出的理论上限不变。

容易混淆

把achieved occupancy 80%解释成执行单元80%的峰值FLOPS。

检验理解occupancy更高但eligible更低，是不可能的吗？

可能。更多warp被驻留，但其下一条指令都在等待依赖或同步。

H03.08

block 生命周期与尾部效应

#

最后少数 block 为什么会拖住整个 kernel？

最小状态
待执行block数、每block剩余工作、SM空闲状态。
变化规则
block完成释放资源；若队列已空，该SM进入空闲直到grid结束。

block执行时间可能因输入、分支、缓存或竞争而不同。许多block已结束后，剩余少数block仍在某些SM上运行；全局工作供给不足以继续填满所有SM，形成tail effect。此时单个慢block可以决定kernel结束时刻。

同一block内部也可能出现部分warp先退出、其余warp继续推进，实际resident warp随时间减少。应区分“最后一波不足”和“每个block内部工作不均”，因为前者可通过更细的任务切分改善，后者可能需要改变工作映射。平均计数会把这些阶段混在一起。

具体例子

教学4个SM各接1个block，前三个在时刻10结束，第四个在时刻30结束。后20个时间单位只有一个SM工作，尾部占据总时间的三分之二。

先预测负载方差变大，即使总工作量不变，最后完成时间也可能上升。

容易混淆

看到整个kernel平均利用率低，就认定每个时刻都缺少warp或每个SM都慢。

检验理解增加同样的短block能消除已有长block的最终尾部吗？

不一定。必须考察长任务能否拆分、再分配，以及新工作是否改变关键路径。

OBSERVE, THEN EXPLAIN

如何在工具里观察？

以下是核对方向，不是已经采集的测量结果。先在目标 GPU 与 NCU 版本中查询名称和支持范围：

ncu --list-sections
ncu --query-metrics

launch__registers_per_thread

定位每线程寄存器需求是否随代码变化；再对照Occupancy计算器的限制资源。

不是实际RF吞吐；分配粒度和spill需要另查。

[4]

launch__shared_mem_per_block_allocated

读取按block实际分配的SMEM，用于判断缓冲stage是否跨驻留台阶。

包括分配取整；同时记录静态、动态、driver份额。

[4]

Occupancy / LaunchStats

联合比较理论与achieved occupancy、block大小和限制资源。

section先用 --list-sections查询；高驻留不保证高eligible或高吞吐。

[4]

launch__waves_per_multiprocessor

判断grid波次和部分尾波是否值得检查。

它是launch估算，不是每个SM的精确时间线，也不能独自证明负载均衡。

[4]

ONE VARIABLE, ONE HYPOTHESIS

实验设计：只增加动态 shared memory（未执行）

只改变

保持kernel指令和block大小不变，在合法范围内提高launch的动态shared memory参数，扫描驻留台阶。

预计现象

理论active blocks会在某些边界下降；只有工作负载依赖新增驻留并行性时，耗时才一定受影响。

记录什么

用cudaOccupancyMaxActiveBlocksPerMultiprocessor与NCU Occupancy核对；记录普通耗时和寄存器数。

排除干扰

shared memory carveout变化也可能影响L1；非法launch、grid不足、clock变化不能解释为occupancy效应。

这是可复现实验设计；本页未运行真实 GPU 或完整 Accel-Sim，也未报告实机性能数据。
